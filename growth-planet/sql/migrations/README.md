# Sprint 1 增量迁移

适用源：原六表结构。仅交付脚本，本次没有连接或修改现有业务数据库。

自动验证：`MigrationIT` 在独立 MySQL 容器中重建旧六表合成夹具，执行三个脚本，比较新建库与迁移库的列/索引，并检查历史保留和唯一键。它不替代真实数据副本的预检结果审查、迁移耗时评估和恢复演练。

## 执行顺序

1. 关闭入口并停写，备份六表、配置和应用，验证可恢复；记录表行数、旧状态分布和 `SHOW CREATE TABLE`。
2. 执行 `20260918_01_preflight.sql`。所有异常结果必须人工归属审查；禁止自动合并账号、丢弃历史记录或以修改 openid 绕过重复身份。
3. 在隔离副本执行 `20260918_02_expand.sql`，核对字段和两张基础表。
4. 执行 `20260918_03_cutover.sql`，部署新应用和匹配客户端。全部旧 token 失效；历史儿童绑定重新同意/审批，档案需家长重新确认。
5. 比较结构、行数和历史审计，执行接口、唯一约束、撤回并发测试。实际迁移耗时及元数据锁等待必须在预发布演练后登记。

## 风险与回滚

- SQL 不在应用启动时执行，不是可重复迁移框架。DDL 隐式提交；中途失败须查 `information_schema` 与执行记录，从失败语句人工恢复，不能整份重跑。
- 新唯一键包含逻辑删除记录；重复 openid、关系、档案及邀请码会阻断切换。活跃儿童只能有一个 PENDING/BOUND 家庭。
- 旧同意缺少申请证据，保持 NULL 申请字段隔离，不能赋予授权效力。旧代码覆盖掉的历史无法从现有行恢复，需从经批准的备份/审计查证。
- 切换会将旧儿童绑定设为 PENDING；它不删除旧档案，也不重新认可其采集依据。真实存量资料必须交合规处置，禁止直接带入演示环境。
- 回滚优先关闭写入口并部署兼容新结构的修复版本。不可回退旧的越权/撤回逻辑，不执行 DROP 新列/新表的逆向 DDL。
- 使用备份恢复时，需审批并重放切换后的撤回、注销和权利记录，避免恢复旧授权。原库与恢复库均应停写直至核验通过。
- Q-01、Q-07、保留期限、正式协议和字段目录未批准，不开放真实数据。
