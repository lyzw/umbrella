## 已完成批次

### 1. 首轮体验结构优化

已完成并持续保留的基础调整：

- 收敛儿童和家长一级导航，减少底部入口过载。
- 将勋章、日程等低频能力移入二级入口，同时保留可达路径。
- 家庭绑定拆分为申请、同意、绑定、建档等步骤，突出当前待办。
- 审批页默认聚焦“同意并记账”和“需要调整”，复杂调整内容按需展开。
- 菜品管理表单拆分为基础信息、营养口味和安全信息，增加过敏原本地化、图片预览和固定保存区。
- 钱包拆分为概览、流水、规则视图，降低首次进入的信息密度。
- 家务、勋章、日程等页面复用全局样式 token 和统一反馈结构。

### 2. 健康打卡基础闭环与安全边界

当前代码和测试已覆盖健康打卡的主要业务边界：

- 家长使用预设配置打卡项，保存时校验名称、排序、版本号和重复操作。
- 儿童按当天状态打卡，拦截重复点击、未知 item、每日上限和失败重试。
- 月历按上海月份计算，禁止进入未来月份。
- 页面切换、月份切换和页面隐藏后，迟到响应不能覆盖当前健康数据。
- 健康数据沿用同意状态和角色边界，不向写请求注入不必要的家庭字段。

仍不能将健康功能标记为完整交付，原因是系统字体放大、真实设备宽度、微信原生组件和端到端同意撤回流程尚未完成验收。

### 3. 儿童空餐单提醒

提交：`78e3bdf feat(miniprogram): add empty menu reminder`

- 儿童首页餐单为空时展示“提醒爸妈发布”入口。
- 服务端按儿童和上海业务日期幂等登记站内提醒。
- 成功、重复和失败结果分别展示，不将失败伪装为已提醒。
- 保留 `SUBSCRIBE=UNAUTHORIZED` 不等价于微信消息已送达的约束。

### 4. 导航与页面寻路

提交：

- `12d894a fix(miniprogram): prevent duplicate secondary navigation`
- `bc678dd docs(miniprogram): record navigation ownership`

- 增加二级页面实例级导航锁，连续点击不会重复压栈。
- 导航失败后释放锁，用户可以重试。
- 统一首页、菜单、确认单、家庭、通知、隐私等页面的二级入口。
- 对页面参数进行校验和 URL 编码。
- 隐私页统一返回家长“我的”模块。
- 增加重复点击、失败重试、返回归属和参数编码测试。

页面栈、系统返回键、锁屏恢复和真机返回行为仍需平台验收。

### 5. 主题语义与可访问性样式

提交：

- `6dbba88 style(miniprogram): centralize semantic theme tokens`
- `390d870 docs(miniprogram): record theme accessibility checks`

- 增加 `primary-shadow`、`positive-ink`、`warning-ink`、`danger-ink` 等语义 token。
- 主按钮、错误提示、危险按钮、状态徽标和勋章激活态改用语义变量。
- 导航组件在儿童和家长角色下分别提供主色、背景、阴影和按压态变量。
- 钱包趋势图按 `PARENT`/`CHILD` 使用绿色/蓝色主色，坐标轴和网格保持中性。
- 返回、偏好删除、配方行内操作的最小高度统一到 `44px`。
- 首页列表标题和登录角色说明允许长文本换行。
- 新增主题串色、触控尺寸和长文本静态断言。

本批只完成代码级和静态级优化，不代表真机对比度、读屏和系统字体放大验收完成。

## 发布前验收任务

### 开发者工具

- 儿童、家长双角色分别覆盖未授权、空数据、错误、长文本和重复点击。
- 覆盖 320、375、430px、平板宽度、全面屏安全区和键盘弹起。
- 直接打开二级页面、从首页进入、系统返回键和连续点击分别验证。

### 真机与弱网

- 验证弱网、断网恢复、请求结果未知、锁屏恢复、跨日和账号切换。
- 验证字体放大、读屏焦点、按钮触控区域、页面滚动和底部固定操作栏。
- 记录截图、设备型号、系统版本、基础库版本和复现步骤。

### 业务端到端

- 建家庭、记录同意、绑定、建档。
- 家长发布菜单、儿童提报、家长审批。
- 钱包发放、额度版本冲突、跨儿童切换。
- 健康打卡、同意撤回和敏感数据清理。
- 通知已读、餐单提醒、隐私导出和删除申请。

## 推荐实施顺序

1. 完成健康打卡 P0 收口及独立验证。
2. 实施页面状态与操作反馈统一，按核心页面分批提交。
3. 补齐主题剩余项、读屏语义和长文本真机验收。
4. 运行开发者工具、真机和双账号端到端验收，更新 [`docs/verification.md`](verification.md)。
5. 清理发布阻塞项后，再进行体验版或正式版流程。

## 变更与提交约束

- 继续按功能、测试、视觉和文档拆分提交。
- 不提交无关工作区改动，不回退用户已有改动。
- 不修改数据库字段、接口协议或敏感数据存储策略，除非新增明确的迁移说明和验收结果。
- 每批提交前至少执行 Node 测试、结构检查和 `git diff --check`。
- 真机未验证的内容只能记录为“待验收”，不能写成已完成。
