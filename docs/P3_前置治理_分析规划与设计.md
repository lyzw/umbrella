### 2.1 R4：SCHOOL 菜单的归属键 = 校名文本（全链路）

**写入侧**

| 位置 | 事实 |
|---|---|

| `CatalogService:1165-1167` | `menuKey(sourceType, ownerKey, date, mealType)` 的统一查询构造 |

**表结构**

- `life_menu_daily`（`sql/sprint3_catalog.sql:45-70`）：`owner_key VARCHAR(128) utf8mb4_bin NOT NULL`、`school VARCHAR(128)`；唯一键 `uk_source_owner_date_meal (source_type, owner_key, menu_date, meal_type)`。
- **`chk_menu_owner` CHECK 强制**：SCHOOL 分支要求 `family_id IS NULL AND school IS NOT NULL AND CHAR_LENGTH(TRIM(school)) > 0 AND owner_key = school`。
  ⇒ **改归属键必须先 `DROP CHECK` 再 `ADD CONSTRAINT`**，与 v006 的 `chk_medal_category` 同一范式；否则 CHECK 失败会被 `INSERT IGNORE` 静默降级为 warning（已被 P2 实测踩过）。
- 画像：`usr_child_profile.school VARCHAR(128)`（`sql/sprint1_schema.sql:57-72`），**无任何白名单校验**（见下）。
- 隐私导出：`PrivacyWorkflowService:154` 导出 `school` 文本；`ChildProfileReq.school`（`:20`）无约束。

**根因确认**

`ComplianceProperties.validateProfile()`（`:31-37`）只校验 `grade ∈ grades` 与 `allergies ⊆ allergens` 两个目录，**完全没有学校目录**。⇒ 校名是**自由文本**：改名、错字、同名分校即产生不同（或错误相同）的 `owner_key` → 跨校串单 / 同一实体菜单分裂。这正是 R4。

**v2 决策后的风险重分类**（学校菜单仅作展示）：

| 原风险 | 是否需要治理 | 说明 |
|---|---|---|
| (i) 展示风险：两侧手输校名逐字不一致 ⇒ **该校孩子看不到菜单** | ✅ 本期治理（R4-lite） | 比对见 `daily():296-298`、`recommend():659-661`，比对前仅 `trim()` |
| (ii) 数据/聚合风险：同名分校共键 → 跨校串单；改名 → 存量行孤儿；唯一键含文本 | ❌ 降级为「可接受残留」 | 无聚合、无校方权限、无跨表引用 ⇒ 不会产生"错误合并后被统计"的业务后果 |

**注意**：写入侧与读取侧的表单形态**不对称** —— 年级已是受目录约束的 `picker`（`pages/profile/index.wxml:8`），学校却是自由 `input`（`:9`，`maxlength="128"`）；ADMIN 发布侧同样只校验非空（`upsertSchoolMenu():190`）。这是 R4-lite 要闭合的正是这一处。

**判定链（现状，逻辑本身是对的）**

| 位置 | 事实 |
|---|---|
| `CatalogService.safetyStatus()`（`:1102-1112`） | 返回 `OFF_SALE` / `UNKNOWN` / `ALLERGY_CONFLICT` / `DECLARED`。`UNKNOWN` 的触发条件有**三个**：① 菜品 `allergen_status != 'DECLARED'`；② 菜品 `allergens` 不在合规目录内；③ **孩子档案 `allergies` 不在合规目录内**（fail-closed） |
| `CatalogService:322` | 孩子端 `canSelect = submittable && "DECLARED".equals(safety)` |

| `CatalogService.validateDish()`（`:1135-1152`） | 建菜只校验「分类存在且 ENABLED」+ `validAllergens(req.allergens)`，**不校验「上架必须已声明」** |
| `CatalogService.validAllergens()`（`:1154-1160`） | 要求 `catalogReference` 非空 + 每个过敏原在 `compliance.allergens` 目录内 + 去重；**允许空列表** ⇒ `allergens=[] + DECLARED` 是**合法且有语义**的「已声明不含过敏原」 |
| `DishReq`（`:24-31`） | 建菜**必须显式传** `allergens`（非空 List）、`allergenStatus ∈ {UNKNOWN, DECLARED}`、`status ∈ {ON_SALE, OFF_SALE}` |
| `CatalogService.applyDish()`（`:1179-1190`） | `allergenStatus` 直接取请求值，**不强制** `DECLARED` |
| 目录来源 | `application-dev.yml` 为合成目录（`PEANUT/MILK/EGG`、六个年级）；`application.yml:49-51` **未配置** ⇒ prod 未配置时 `validAllergens` 恒 false ⇒ 全员 `UNKNOWN`（设计上 fail-closed，但**无启动期提示**） |
| 孩子端文案现状 | `pages/menu/index.js` 的 `render()` 已有三态 badge（`allergyConflict` → '含过敏原，不可选择'；`allergenStatus !== 'DECLARED'` → **'过敏信息待确认'**；`status !== 'ON_SALE'` → '已下架'）。⇒ **并非「无文案」**，而是**文案不区分原因**：菜品未声明（等管理员）与档案过敏原失配（只能家长改）显示成同一句，用户不知道找谁处理。 |
| 预置菜品来源 | 只有 ADMIN 可建（`MenuController:39` `POST /api/admin/dish`）；**全仓 SQL 无 `INSERT INTO life_dish` 种子**（仅测试内插入）⇒ 生产只能靠人工逐条录入 |

**缺口三条（本期要解决的）**

1. **无补全抓手**：`queryDishes()` 只支持 `categoryId/status/keyword` 过滤，**没有 `allergenStatus` 过滤**，管理员无法列出「未声明」清单；也没有批量声明能力。
2. **提示不可执行**：`UNKNOWN` 的孩子端 badge 只有一句 '过敏信息待确认'，不区分「菜品未登记（等管理员补）」与「档案过敏原不在最新目录（需家长更新）」，也不说明「不影响标想吃、只影响点菜」⇒ 用户只知道"点不了"，不知道该做什么。
3. **无强制**：菜可以带着 `UNKNOWN` 长期 `ON_SALE` 上线，没有任何环节会拦。

## 三、方案设计

### 3.1 R4-lite：把校名从「自由文本」变成「目录值」

**方案收敛过程（D1 已确认取 B）**

原 R4 设计的是「改 `owner_key` 为 `school_id`」的强治理（新表 + ADMIN CRUD + 两列 + 存量改写 + CHECK 重建）。v2 决策把它的动因拆成两半之后，其中一半（校方聚合所需的稳定主体与权限边界）消失，方案随之收敛：

| 选项 | 做法 | 结论 |
|---|---|---|
| **B（本期采用）校名目录化** | `ComplianceProperties` 增 `schools: List<String>`（照 `grades` 抄）；`validateProfile` 与 `upsertSchoolMenu` 都增「校名在目录内」校验；小程序档案页学校由 `<input>` 改 `<picker>` | **推荐**。零迁移、无破坏性操作；两侧同源取值 ⇒ 逐字不一致从根上消失 |
| A 新表 `sys_school` + `school_id` | 稳定 ID、可改名不变、可承载校方角色 | **本期不做**（唯一必要动因随 P3-2 取消而消失） |
| C A+B 混合 | 表 + 目录两套真相 | **不做**（只做展示时无收益） |

**设计要点（B 方案，5 处动作 + 5 处明确不动）**

1. **配置**：`ComplianceProperties` 新增 `private List<String> schools = List.of();`。dev 按现有合成目录风格补三个校名（`application-dev.yml:18-25` 已有 `PEANUT/MILK/EGG` 六个年级的合成目录范式）。
2. **档案侧校验**：`validateProfile()`（`:31-37`）由「年级 + 过敏原」扩为「年级 + 学校 + 过敏原」，失配仍统一 `E400`，文案改为「年级、学校或过敏原不在发布目录」。**不新增错误码**。

### 3.2 R5：把「未声明」变成可运维、可解释的状态

四件事，彼此独立可分批：

**(a) 可运维：给管理员一个「未声明清单」**
`queryDishes()` 增加 `allergenStatus` 过滤（`UNKNOWN` / `DECLARED`），`GET /api/admin/dish?allergenStatus=UNKNOWN` 即可列出待补全菜品；`DishResp` 增量暴露 `allergenStatus`（若尚未暴露，编码时核对）。批量声明（D6）**推荐做成 ADMIN 侧逐条编辑**，不引入批量导入（避免把「批量点错」放大成安全事件）。

**(b) 可解释：孩子端不再静默**
`UNKNOWN` 时按钮文案由「不可点」改为显式提示（如「未登记过敏原，暂不可标记」），并给出「提醒家长」路径（家长端对应位置显示待补全原因）。**落点**：`pages/menu` 的菜品卡片与其三态文案（P1 已有三态范式可扩展）；后端无需新增接口，`DishResp.safetyStatus` 已返回（`:322`）。

**(c) 可强制：把「已声明」与「可上架」绑定**（D7，推荐采纳）
`applyDish` / `validateDish` 增加规则：`status='ON_SALE'` ⇒ 必须 `allergenStatus='DECLARED'`（`OFF_SALE` 允许 `UNKNOWN`）。这样「未声明」只能存在于下架态，**不可能悄悄对儿童可见**；同时保留草稿式录入体验。

**(d) 目录就绪 fail-fast**（D8，推荐采纳）
prod 未配置 `compliance.allergens` 时 `validAllergens` 恒 false、全员 `UNKNOWN`，且**没有任何启动期提示**。建议启动即校验：`collection-enabled=true` 且目录为空 ⇒ 启动失败并给出明确原因（当前是「上线后静默不可点」）。

**注意**：`UNKNOWN` 的第三个触发条件（孩子档案 `allergies` 不在目录内）不是菜品问题。家长填过敏原受 `validateProfile` 白名单约束，理论不会发生；但若目录变更后老档案失配，孩子会**整页不可点**。建议按 (b) 的同一文案机制区分提示（「档案中的过敏原已不在最新目录，请联系家长更新」）。

**(e) 与「测试数据管理后台」计划的交互（已存在的未跟踪计划文档）**
