家庭模型重构 · 规划与设计

从「单家长 + 单家庭」升级为「多家长 + 多学生 + 多家庭」——支持父母、祖辈（爷爷奶奶 / 外公外婆）、亲友共同组成一个家庭，并可凭邀请码加入；同一用户可同时属于多个家庭。

状态：已完成 · 阶段0-5全部落地 · 集成测试 225 用例全绿 已落地：邀请码表 / 枚举 / 加入改造 模块：FAMILY 2026-09-30 不分级 · 按码类型 · 家长免审/学生审
已确认的三项核心决策（来自你的拍板）：
  • 权限不分级：所有家长权限一致，仅靠「关系标签」区分称呼（爸 / 妈 / 爷爷 / 外婆 / 亲友…）。
  • 邀请码按类型：生成时区分「家长邀请码」「学生邀请码」，码本身锁定加入角色，杜绝越权。
  • 家长免审 · 学生需审：家长邀请码直连 BOUND；学生邀请码进入 PENDING，需家庭内家长审批。

N×M家庭 × 成员 自由组合，支持一人多家庭

一、需求边界

1.1 纳入范围

  • 多家长：父母、爷爷奶奶、外公外婆、其他亲友 / 监护人，均可作为「家长」加入同一家庭。权限等价，仅称呼不同。
  • 多学生：一个家庭可包含多名儿童（CHILD）。
  • 邀请码加入：家长与学生都通过邀请码加入；家长码免审直连，学生码需审批。
  • 多家庭归属：同一用户可同时属于多个家庭（例如孩子同时属于「父母家庭」与「祖辈家庭」；家长可管理多个家庭）。

1.2 明确不做（避免范围蔓延）

  • 家长内部权限分级（OWNER / GUARDIAN / MEMBER 细分）——本期不分级。
  • 邀请码「允许角色集合」——按码类型已足够，不引入集合语义。
  • 家长加入审批——已确认家长免审；仅学生需审。
  • 家庭合并 / 拆分等非核心生命周期操作——列后续；本期纳入「退出 / 移除成员 / owner 转移」（owner 转移接口与规则见第五节）。

二、角色模型：权限角色 与 关系标签 解耦

这是本次设计的核心思想——用两个维度描述成员，互不耦合：

维度字段取值作用
权限角色rolePARENT / CHILD（沿用现有二元）决定能做什么（鉴权）
关系标签relation_label父亲/母亲/爷爷/奶奶/外公/外婆/亲友/孩子（枚举化见下）仅展示称呼，无权限差异

落地含义：爷爷奶奶用「家长邀请码」加入 → role=PARENT（与家长权限完全一致），relation_label="爷爷/奶奶"。这样「祖辈是家长」的需求被自然满足，无需新增角色。

2.1 新增关系标签枚举 RelationEnum

FATHER("父亲"), MOTHER("母亲"),
PATERNAL_GF("爷爷"), PATERNAL_GM("奶奶"),
MATERNAL_GF("外公"), MATERNAL_GM("外婆"),
OTHER_GUARDIAN("亲友"), CHILD("孩子");

前端在加入 / 审批时选择其一；DB 仍存 VARCHAR(32)，新增 Java 枚举 + 字典接口下发候选值（与现有「过敏原字典」模式一致）。

2.2 新增邀请码类型枚举 InviteType

PARENT("家长邀请码"), CHILD("学生邀请码");

邀请码生成时即锁定类型；join 时按码类型决定写入的 role，加入者无法自行改变角色。

三、数据模型变更

3.1 usr_family（基本不动）

字段现状变更说明
owner_user_idNOT NULL保留仍指向创建者；多家长不等于多 owner，其他家长是 role=PARENT 的普通成员
invite_code / invite_code_expire单字段标记废弃保留列不删（降低迁移风险），后端不再读写；主路径改走新表

3.2 新增 usr_family_invite（邀请码表）

CREATE TABLE usr_family_invite (
  id               BIGINT      PRIMARY KEY AUTO_INCREMENT,
  family_id        BIGINT      NOT NULL,
  code             VARCHAR(6)  NOT NULL,                 -- 6位大写字母数字, 唯一
  invite_type      VARCHAR(8)  NOT NULL,                 -- PARENT / CHILD (锁定加入角色)
  creator_user_id  BIGINT      NOT NULL,                 -- 生成者(家长)
  status           VARCHAR(8)  NOT NULL DEFAULT 'ACTIVE',-- ACTIVE / REVOKED
  expire_at        BIGINT      NOT NULL,                 -- 毫秒时间戳, 建议默认 7d 可配
  max_use          INT         NOT NULL DEFAULT 0,       -- 0=不限制使用次数
  used_count       INT         NOT NULL DEFAULT 0,
  create_time      DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time      DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  delete_at        BIGINT      NOT NULL DEFAULT 0,
  UNIQUE KEY uk_code (code),
  KEY idx_family (family_id),
  CONSTRAINT fk_invite_family FOREIGN KEY (family_id) REFERENCES usr_family (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

支持一个家庭同时存在多个邀请码（一个家长码 + 一个学生码 + 可撤销 / 可过期 / 可限次），彻底取代原单字段方案。

3.3 usr_family_member（关键改造）

项现状变更
rolePARENT / CHILD保留二元，不分级
relation_label自由串建议收敛为 RelationEnum 候选值
effective_child_id（生成列）CASE WHEN role='CHILD' AND bind_status IN('PENDING','BOUND') AND delete_at=0 THEN user_id END保留生成列逻辑不变（仍依赖 role='CHILD'）
uk_effective_child（唯一键）全局唯一 → 强约束「一个 CHILD 同时只在一个家庭」删除该唯一键，放开多家庭；同家庭重复由 uk_family_user(family_id,user_id) 兜底
uk_family_user(family_id, user_id)保留——天然支持「同一用户跨多个家庭」，仅禁止同家庭重复
invite_id（可选）无新增，记录经哪个邀请码加入，便于审计 / 撤销溯源

3.4 迁移脚本（向后兼容）

-- 1) 放开多家庭: 删除基于生成列的全局唯一键
ALTER TABLE usr_family_member DROP KEY uk_effective_child;

-- 2) 新增邀请码表
CREATE TABLE usr_family_invite ( ... );  -- 见 3.2

-- 3) 旧单码迁移为新表(若旧码存在且未过期, 默认按 CHILD 类型补录)
INSERT INTO usr_family_invite (family_id, code, invite_type, creator_user_id, status, expire_at, max_use, used_count, delete_at)
SELECT id, invite_code, 'CHILD', owner_user_id, 'ACTIVE', invite_code_expire, 0, 0, 0
FROM usr_family WHERE invite_code IS NOT NULL AND invite_code_expire > UNIX_TIMESTAMP()*1000;

-- 4) 可选审计列
ALTER TABLE usr_family_member ADD COLUMN invite_id BIGINT DEFAULT NULL;

旧 usr_family.invite_code 列保留不删，避免历史数据 / 旧代码路径断裂；新版后端完全不读写它。

四、登录态与多家庭激活机制

当前 LoginUser.familyIds 已是 List<Long>，但处处用 firstFamilyId() 取第一个，隐含「单家庭」假设。多家庭下需引入请求级的「当前激活家庭」。

机制方案
激活家庭来源客户端在请求头携带 X-Family-Id: <familyId>；JwtInterceptor 解析后校验其 ∈ token 的 familyIds，写入 UserContext.activeFamilyId
回落策略未带头时回落 firstFamilyId()，保证旧调用兼容
替换范围全量将 firstFamilyId() / UserContext.familyId() 改为 activeFamilyId()，并在越界时抛 E009_FORBIDDEN
Token 内容不变（仅 family_ids + jti）；激活家庭是请求级上下文，不写入 JWT

五、接口规划（C 端 /api/mini）

接口方法角色说明
/family/createPOSTPARENT创建家庭。移除「仅一个家庭」E007 约束；写入 owner + 一条 PARENT/BOUND 成员
/family/invite-codePOSTPARENT入参 {inviteType, expireHours?, maxUse?}；生成并返回新码（写 usr_family_invite）
/family/invite-codesGETPARENT列出本家庭有效邀请码（含类型 / 状态 / 过期 / 使用次数）
/family/invite-code/revokePOSTPARENT撤销某邀请码（status=REVOKED）
/family/joinPOST已登录(任意)入参 {inviteCode, relationLabel?}。移除 requireChild；按码类型定角色：家长码→PARENT/BOUND（免审）；学生码→CHILD/PENDING（需审）。校验码有效/未过期/未撤销/未超限次
/family/bind-approvePOSTPARENT审批学生加入（保留；任意 PARENT 均可审批，非仅 owner）
/family/membersGET家庭成员返回本家庭全部成员（按 PARENT / CHILD 分组 + relation_label）
/family/myGET已登录返回「我所属的所有家庭」列表（多家庭入口）
/family/leavePOST成员主动退出；owner 不可直接退——须先 transfer-owner 转让，或解散家庭后再退
/family/remove-memberPOSTPARENT移除某成员。规则：可移除 CHILD 或另一 PARENT；不可移除 owner（需先转让）；移除后该成员在本家庭的绑定关系解除（不影响其在其他家庭的归属）
/family/transfer-ownerPOSTowner转让 owner。仅当前 owner 可调；入参 {targetUserId} 须为本家庭内 BOUND 的 PARENT；转让后原 owner 降为普通 PARENT，usr_family.owner_user_id 更新（手写乐观锁防并发，0 行 → E007）

六、鉴权改造点（ChildAuthorizationService）

// 旧: 须恰好 1 个 PARENT
members.selectCount(... role='PARENT' AND bind_status='BOUND') == 1
// 新: 至少 1 个 PARENT 即可(多家长)
members.selectCount(... role='PARENT' AND bind_status='BOUND') >= 1

// requireConsent: 旧"仅 owner 可作为 grantor"
// 新: 当前用户若是家庭内 BOUND 的 PARENT → grantorId=当前用户
//     若是 CHILD 本人 → 取家庭内任意 BOUND PARENT 作为 grantorId

// lockBoundChild / boundChild / lockChild:
//   ctx.firstFamilyId()  →  ctx.activeFamilyId()

同时 FamilyServiceImpl 中 createFamily 的「Sprint 1 仅支持一个家庭」E007 检查、joinFamily 的「已有其他有效家庭申请或绑定」E007 检查均须移除 / 放宽。

七、多家庭隔离与安全

  • familyId / ownerKey 等归属字段严禁客户端传入，一律从 activeFamilyId 派生。
  • activeFamilyId 必须 ∈ token 的 familyIds，否则 E009_FORBIDDEN——跨家庭 100% 隔离。
  • 菜单 / 心愿 / 零花钱 / 勋章等现有按 family_id 查询的逻辑保持；新增 / 改造接口都必须带 activeFamilyId 过滤。
  • 邀请码与家庭绑定：join 时按 code 反查 usr_family_invite 得 family_id 与 invite_type，再加入对应家庭。

八、风险与回滚点

  • R1 生成列唯一键删除：删 uk_effective_child 后，同家庭重复由 uk_family_user 兜底；需 IT 验证「同一孩子同一家庭不可重复」「不同家庭可共存」。
  • R2 权限扩散：多家长使审批 / 同意权从 owner 扩散到任意 PARENT，须回归 SecurityRegressionIT 与同意流程用例。
  • R3 激活家庭贯穿：遗漏 firstFamilyId() 替换处会误用旧家庭 → 必须全量替换并加 IT 断言。
  • R4 既有 IT 假设：FamilyFlowIT 等大量假设单家庭，需同步更新断言（一人多家庭、多家长审批）。
  • 回滚：迁移前全量备份；新代码兼容旧表（旧字段保留），可灰度；若回退，重建 uk_effective_child 即可恢复单家庭约束。
