## 二、代码事实核查（写设计前先对齐现状）

### 2.1 R6：`daily()` 读路径实际持有哪些锁

`CatalogService.daily()`（`:248-298`）是**纯展示路径**，但沿途对**三类行**加了排他锁：

| 位置 | 锁对象 | 说明 |
|---|---|---|
| `:262` `authorization.lockBoundChild(childId)` | 绑定关系 | 名称含 lock，需确认实现（待确认） |
| `:538` `completeProfile()` → `child_profile ... FOR UPDATE` | 孩子档案 | 读展示也锁档案 |
| `:267-268` `menuKey(...).eq("status","PUBLISHED").last("FOR UPDATE")` | 菜单行 | **主热点** |
| `:272` → `lockVisibleDishesByRef()` `:667`/`:676` | **菜单内每一道菜**（PRESET 逐条、FAMILY 逐条） | 一道菜一把锁，菜单越长锁越多 |

同样问题也存在于 **`menuMaintenance()`**（家长查看菜单维护页，`:224` 锁菜单、`:230` 锁全部菜品）——它同样只是展示。

对照：**写路径自己独立加锁**，不依赖读路径：
- `validateOrder()` `:476` 锁菜单、`:520` 锁菜品；
- `markFavorite()` → `lockDishByType()` `:433` 锁菜品；
- 发布菜单 `:189` 锁菜单。

**所以 `daily()` / `menuMaintenance()` 去锁，不会削弱任何写路径的并发正确性。** 这是 R6 可安全落地的依据。

### 2.2 R3：P0 已交付的接口能力边界

```
GET /api/child/want-eat?childId=&menuDate=&mealType=
→ WantEatResp { childId, menuDate, mealType, wantEat: [ {type, id} ] }
```
（`MenuController:120-126`，`CatalogService.childWantEat():393-408`）

**缺口**：① 只能查"某一天某一餐"；② 只返回 `{type,id}` **裸引用**，无菜品名/图/分类；③ **不含 `status`**；④ 无"过期/今日"区分；⑤ 无采购汇总。家长拿不到"这周孩子想吃啥、我买了没"。

### 2.3 「采购清单」的可行性缺口 ⚠️

`life_dish` 字段实测（`entity/Dish.java`）：
`id, categoryId, name, imageUrl, virtualPrice, calories, tags, allergens, allergenStatus, spiceLevel, status`

**没有「食材 / ingredients」字段**，`life_family_dish` 同构（由 `applyDish` 写入的字段范围亦印证）。
→ **"按食材聚合采购清单"在当前数据模型下不可实现**，只能做"**按菜品去重 + 出现天数计数**"的清单。要做真食材聚合，必须先给菜品加食材字段（含家长录入 UI），属独立工作量。

### 2.4 家长端 UI 现状

- `pages/menu/index` **同时服务 CHILD 与 PARENT**，但 PARENT 分支走 `loadParent()` → 是**菜单维护（编辑器）**，不是"看孩子想吃啥"。
- 首页 `pages/home/index` 的二级入口列表（日程/勋章/健康打卡/隐私…）是新增页面的既有挂载点。
- **当前不存在任何家长侧"想吃清单"页面**，需新建页面。

### 2.5 家长接口路径约定

项目现有家长接口一律 `GET|POST /api/parent/xxx`，`childId` 走 **query 参数**（如 `/child/preferences?childId=`），**不用路径变量**。
→ 原分析文档 §6.2 草案的 `/api/parent/child/{childId}/want-eat` **不符合本项目约定**，应改为 `/api/parent/want-eat?childId=&from=&to=`。

### 2.6 `status` 现状

`ChildWantEat.status` 字段与 `@Version` 乐观锁**已就绪**（`entity/ChildWantEat.java:29,33-34`），建表注释写明三态 `MARKED/ADOPTED/COOKED`。**P0 只写 `MARKED`，无任何流转接口。**

## 三、方案设计

### 3.1 建议分批：P1a（本期核心）与 P1b（体验与派生）

| 批次 | 内容 | 依赖 | 说明 |
|---|---|---|---|
| **P1a** | R3 家长按日清单（接口 + 家长新页） + R6 去 `daily()`/`menuMaintenance()` 展示锁 + status 流转 | — | 形成"孩子标记 → 家长查看 → 家长标记已买/已做"的**完整价值闭环** |
| **P1b** | 浏览体验收尾（分类聚合/菜品图/过敏原提示） + 派生「爱吃/常点」视图 + `favoriteDishIds` 处置 | P1a | 依赖 P1a 的聚合数据与页面骨架 |

**理由**：P1a 单独就能交付"家长看得见、能回应"，是 R3 的核心价值；P1b 是锦上添花且部分项（食材/过敏原）存在数据缺口，宜先落地 P1a 再评估。

### 3.2 P1a-1：家长按日想吃清单接口

**接口**
```
GET /api/parent/want-eat?childId={id}&from={yyyy-MM-dd}&to={yyyy-MM-dd}
权限：PARENT
鉴权：positive(childId) → authorization.lockBoundChild(childId) → authorization.requireParent(member.getFamilyId())
参数：from/to 必填；from <= to；区间跨度上限 31 天（超出 → E400），防大区间扫描
```

**响应（草案）**
```jsonc
{
  "childId": 12, "from": "2026-09-22", "to": "2026-09-28",
  "today": "2026-09-22",
  "days": [
    { "menuDate": "2026-09-22",
      "meals": [
        { "mealType": "LUNCH", "sourceType": "FAMILY", "menuId": 33,
          "items": [
            { "wantEatId": 5, "type": "FAMILY", "id": 7,
              "name": "番茄炒蛋", "imageUrl": "…", "categoryId": 2,
              "status": "MARKED", "expired": false,
              "allergyConflict": false, "disliked": true }
          ] }
      ] } ],
  "expiredCount": 3,     // menuDate < today 且 status=MARKED 的条数（"过期未处理"提醒）
  "summary": {           // 采购/烹饪清单：区间内按 (type,id) 去重
    "totalItems": 6,
    "dishes": [ { "type":"FAMILY", "id":7, "name":"番茄炒蛋",
                  "count":2, "dates":["2026-09-22","2026-09-24"] } ]
  }
}
```

**关键设计决策**
- **过期 ≠ 删除**：`menuDate < today` 的行**照常返回**（家长需要回看"上周孩子点了啥"），用 `expired=true` + 顶层 `expiredCount` 标记。原分析"过期自动不计入今天"通过**默认区间 `from=今天`** 实现，而非过滤掉数据。
- **`sourceType`/`familyId` 不进响应也不进入参**：由 `childId` 反查归属派生，遵守安全约束。
- **菜品信息补全**：按 `(dishType, dishId)` 批量查 `life_dish` / `life_family_dish`（FAMILY 带 `family_id` 隔离），缺失的菜品（已删除/下架）以 `name: null` + `missing: true` 占位返回，不静默丢行。
- **不加锁**：本接口是纯读，全部用普通 `selectList`，不引入 `FOR UPDATE`（避免重蹈 R6）。

### 3.3 P1a-2：status 流转（采纳反馈闭环）

**接口**
```
POST /api/parent/want-eat/{id}/status
权限：PARENT（必须是该行 child 的家长）；Body: { "status": "ADOPTED" | "COOKED" | "MARKED", "expectedVersion": 0 }
语义：ADOPTED=已采购/已安排，COOKED=已做，MARKED=回退为未处理
并发：沿用 `@Version` 乐观锁 + `requireUpdated`，版本不符 → E007(409)
```
- 复用项目既有乐观锁范式（`transition()` + `expectedVersion`，与确认单审批一致）。
- 越权：`wantEatId` 不属于本家庭的 child → 统一业务错误码，不暴露存在性。

> ⚠️ 若认为"家长标记已做"属于 P2 的「采纳反馈闭环（接勋章）」，可**本期只做只读展示**（`status` 返回但无写接口）。见 D4。

### 3.4 P1a-3：R6 去展示锁

**改动**：把读路径的 `FOR UPDATE` 换成普通查询，**不改 SQL 语义、不改接口契约**。

| 方法 | 现状 | 改法 |
|---|---|---|
| `daily()` `:267-268` | `menuKey(...).eq("status","PUBLISHED").last("FOR UPDATE")` | 去掉 `.last("FOR UPDATE")` |
| `daily()` `:272` | `lockVisibleDishesByRef(...)` | 新增只读版 `visibleDishesByRef(...)`（同逻辑、无锁），读路径改调它 |
| `daily()` `:538` | `completeProfile()` → `FOR UPDATE` | 新增只读版 `requireCompleteProfile(member)`，读路径改调它 |
| `menuMaintenance()` `:224`/`:230` | 菜单 + 全部菜品加锁 | 同上，改只读 |
| `:262` `lockBoundChild` | 待确认是否加锁 | 确认后决定是否同样提供只读版 |

**保留不动**（写路径，必须锁）：`publishMenu :189`、`validateOrder :476/:520`、`markFavorite → lockDishByType :433`。

**风险与兜底**
- 去锁后读到的可能是"即将被改"的快照 → **最终一致可接受**（菜单发布是家长低频操作，孩子看到旧菜单重进即可刷新）。
- 需补**并发回归测试**：一边循环 `daily()`，一边并发发布/下架菜品，断言 `daily()` 不抛异常且不阻塞（用超时断言即可表达）。
- 性能收益：放学高峰 N 次 `daily()` 从"串行排队"变为并行；每道菜一把锁的放大效应一并消除。

### 3.5 P1b-1：浏览体验收尾

菜单页已有 `mildOnly`、`favoritesOnly`、`keyword`、来源 tab。本期补：
- **分类聚合**：按 `categoryId` 分组 + 分类 chips（后端 `daily` 已返回 `categoryId`，纯前端；需 `parent/dish-category` 同款分类接口给 CHILD 端 → **待确认是否需要新增只读分类接口**）。
- **菜品图**：`DishResp.imageUrl` 已存在，补 wxml `<image>`（注意空图占位）。
- **过敏原提示**：`daily()` 已返回 `safetyStatus`/`allergyConflict`，补 UI 文案（"含过敏原"角标）。**R5（过敏原白名单缺失 → 全员 UNKNOWN）不在本期范围**，属独立安全合规项。

### 3.6 P1b-2：派生「爱吃/常点」视图

- **数据源**：`usr_child_want_eat` 历史行（P0 起积累）；存量 `favoriteDishIds`（无日期）作**冷启动种子**，仅当新表无数据时兜底。
- **算法**：近 30 天窗口内按 `(dishType, dishId)` 计数，**近期加权**（如 `weight = 1 / (1 + 距今天数/7)`），取 Top 6。
- **落点**：菜单页顶部「孩子常吃」快捷区（CHILD 端），点击 = 快速标记想吃。
- **接口草案**：`GET /api/child/frequent-dish?childId=&limit=6` → 复用 `dishResponse` 补菜品信息。
- **明确不做**：新增"手动持久收藏"入口（保持"爱吃是行为派生"这一产品原则）。

|---|---|

| B. 保留（推荐） | 已停止写入且 `@Deprecated`，无运行时成本；等 P1b 派生视图稳定、确认无冷启动依赖后再删 |

## 六、影响范围 / 回滚

- **接口**：新增 2 个（`GET /api/parent/want-eat`、`POST /api/parent/want-eat/{id}/status`）；旧 `GET /api/child/want-eat` 与 `POST /menu/mark-favorite` **契约不变**（向后兼容）。
- **数据**：P1a **无迁移**（status 字段与 version 已存在）。P1b 若选 D2-B 或 D7-A 才需要迁移。
- **小程序**：新增 `pages/want-eat`（家长入口挂在首页列表），需同步 `app.json` 与 `check.mjs` 页面数期望。
- **回滚**：P1a 全部为新增接口 + 去锁（无状态迁移），回滚 = 还原文件即可；已写入的 `ADOPTED/COOKED` 状态行回滚后不影响读，仅状态不展示。
