# P2 变更文档（编码前最终清单）

> 配套设计稿：`docs/P2_体验跃迁_分析规划与设计.md`。
> 已锁定决策：**全量 P2（不分批）** / 周计划做**周视图 + 批量发布** / 推荐用**规则加权 + 推荐理由** / 勋章按 **COOKED 触发 + COUNT 1/10/30**。
> 补充决策（本文档定稿，可随时改回）：批量发布**允许部分成功**（逐条独立事务），理由见 §三 C2。

---

## 一、改了什么 / 为什么

| 项 | 解决 | 一句话 |
|---|---|---|
| A. 采纳反馈闭环 | 激励 | 家长把想吃标为 `COOKED` 后按累计次数发勋章（新增 `category='MEAL'`），把"孩子的心愿被实现"变成可见成就 |
| B. 「今天吃什么」推荐 | 场景 | 在当天餐单内按"过敏硬过滤 → 忌口剔除 → 常吃加权 → 本周未吃加分 → 清淡偏好"打分，返回 Top N + 推荐理由 |
| C1. 家长周视图 | 周计划 | 一次查询返回 7 天 × 3 餐的发布状态（替代 21 次请求），空餐次占位不丢格 |
| C2. 批量发布 | 周计划 | 一次请求发布最多 21 条 (日期,餐次)，逐条独立事务、允许部分成功 |
| C3. 孩子周视图 | 周计划 | 一次查询返回整周各餐次是否有菜单 + 我标记了几道，用于周条与"提前挑选" |
| C4. 需求汇总 | 周计划 | **无新增**：复用 P1 `GET /api/parent/want-eat?from&to` |

**无破坏性变更**：3 个新读接口 + 1 个新写接口；既有 4 个端点契约不变；唯一 DDL 变动是 3 条 `INSERT IGNORE` 勋章种子。

## 三、接口契约（冻结）

### A. 勋章（无新端点）
```
触发：POST /api/parent/want-eat/{id}/status  body.status = COOKED 且乐观锁更新成功
计数：COUNT(usr_child_want_eat WHERE child_id=? AND status='COOKED')（逻辑删除自动排除）
发放：MedalService.award(...) —— 幂等键 (definition_id, child_id, ref_id=threshold)
      重复标 COOKED / COOKED→MARKED→COOKED 均不重复发
约束：MedalService.award 为 Propagation.MANDATORY，必须在 transitionWantEat 的写事务内调用
```

### B. 推荐
```
GET /api/child/recommend?menuId={id}&childId={id?}&limit={n?}
  权限 {CHILD, PARENT}；menuId 必填正数；limit 默认 3、>0 且 <=5（越界 400）
  CHILD：childId 缺省=本人，传他人 → 403；PARENT：childId 必填且须本家庭
  菜单校验（同 markFavorite）：存在 + PUBLISHED；FAMILY 家庭匹配 / SCHOOL owner_key 匹配
  加锁：无（只读路径：boundChild / requireConsentReadOnly / requireCompleteProfile / visibleDishesByRef）
打分（整数分，确定性）：
  硬过滤  过敏冲突 → 剔除；status != ON_SALE → 剔除
  软过滤  忌口 isDisliked → 剔除
  +2*n    近 30 天常吃次数 n（n 上限 5）      → reasons「近 30 天想吃 n 次」
  +2      本周（含今天）该孩子尚未标记过想吃    → reasons「本周还没吃过」
  +1      清淡偏好命中（tastes 含 清淡/少油/不辣，或 spiceLevel<=1）→ reasons「口味清淡」
  -2      spiceLevel>=3（重辣）
  截断    取 Top limit；同分按 dishId 升序（稳定）
返回：{ menuId, menuDate, mealType, dishes:[{type,id,name,imageUrl,categoryId,categoryName,score,reasons[]}] }
降级：前端请求失败静默不展示推荐卡，不影响菜单主流程
```

### C1. 家长周视图
```
GET /api/parent/menu-week?from=yyyy-MM-dd&to=yyyy-MM-dd
  权限 PARENT；from/to 必填；from<=to；跨度<=14 天（超出 E400）
  鉴权：requireRole("PARENT") + authorization.requireParent(firstFamilyId)（只读，不锁 family 行）
  实现：一次查区间内 FAMILY 菜单（source_type='FAMILY' AND owner_key=familyId AND menu_date BETWEEN）
  必返回区间内每一天 × 三餐格子（未发布 → menuId=null,status=null,dishCount=0，不丢格）
```

### C2. 批量发布
```
POST /api/parent/menu-daily/batch
  Body { "items": [ { "menuDate": "...", "mealType": "LUNCH", "dishIds": [{"type":"PRESET","id":"1"}], "status": "PUBLISHED" } ] }
  权限 PARENT + requireCurrentFamilyParent()（写路径，沿用现有加锁鉴权）
  items 1..21，超限 400
  逐条独立事务：每个 item 走 TransactionTemplate（方法本身 NOT_SUPPORTED 挂起类级事务）
  失败语义：单条失败不回滚整批 → 返回 { okCount, failCount, results:[{menuDate,mealType,ok,code}] }
  复用：validateMenu / upsertMenu 的校验链（DishRef 校验、ON_SALE 校验、乐观锁、审计）
  school 字段：批量接口不接受 school（FAMILY only），出现即 400
```

### C3. 孩子周视图
```
GET /api/child/menu-week?from=&to=&childId={id?}
  权限 {CHILD, PARENT}；CHILD childId 缺省=本人/传他人 403；PARENT childId 必填且须本家庭
  区间同 C1（<=14 天）；只读不加锁
  数据：FAMILY（本家庭）+ SCHOOL（档案 school 名），每格带 menuId/status/dishCount
  另附该孩子在每餐次已标记的想吃条数 wantEatCount 与 marked=true/false
```

## 四、影响范围 / 兼容性
- **破坏性变更：无**。既有 4 个端点（`mark-favorite`、`child/want-eat`、`parent/want-eat`、`parent/want-eat/{id}/status`）请求/响应契约不变。
- **数据库**：新增 `v006` 只做 `INSERT IGNORE`，可在生产直接执行；回滚只需把三条定义置 `status='DISABLED'`（无需改代码）。
- **测试库**：`application-test.yml` 必须登记 `v006`。
- **Sprint 1 既有勋章**：`category` 为 `CHORE`/`HEALTH`，新增 `MEAL` 不与之冲突；`MedalService.listAwards()` 按定义全量返回，前端平铺渲染 ⇒ **勋章页无需改动**。

## 五、回滚点
- 勋章：`UPDATE life_medal_definition SET status='DISABLED' WHERE category='MEAL'`（立即停发，代码可留）。
- 推荐 / 周视图：纯读端点，删除端点或用前端开关隐藏卡片即可，不影响既有流程。
- 批量发布：新端点，不使用即无影响；已发布的菜单行与单条接口发布的结果完全一致（同一 `upsertMenu` 路径）。
- 所有改动集中在 `CatalogService` / `MenuController` / 小程序菜单页 + 1 个新页，按文件还原即可。

## 七、实现偏差与最终定稿（编码后回填）

编号 D1~D6，按严重程度排序。

| # | 项 | 原设计 | 最终定稿 | 原因 |
|---|---|---|---|---|
| **D1** | `publishFamilyMenuBatch` 的事务边界 | 在类级事务内执行，每条 item 用 `REQUIRES_NEW` 提交/回滚 | **方法标 `@Transactional(NOT_SUPPORTED)`**（挂起类级事务）；鉴权单独放进一个短事务并立即提交，拿到 `familyId` 后逐条走 `upsertAuthorizedFamilyMenu(familyId, item)` | **自锁死**：`requireCurrentFamilyParent()` 会对家庭行 `FOR UPDATE`；若本方法仍在外层事务内，子事务会先**挂起外层事务**（外层行锁不释放）再去抢同一行 → 互等。实测表现为批量请求**永久挂起**，DB 侧可看到「一条 idle 事务持锁 + 一条 LOCK WAIT」 |
| **D2** | 批量条目的鉴权次数 | 每条 item 都调 `upsertFamilyMenu()`（内含鉴权） | 新增私有 `upsertAuthorizedFamilyMenu(familyId, item)`：复用 `validateMenu + upsertMenu`，**不再重复鉴权/锁家庭行** | 配合 D1；顺带把 21 次家庭行 `FOR UPDATE` 降为 1 次 |
| **D3** | `v006` 勋章种子 | 直接 `INSERT IGNORE` 三条 `MEAL` 分类定义 | 先 `DROP CHECK chk_medal_category` 再 `ADD CONSTRAINT ... CHECK (category IN (...,'MEAL'))`，然后插入 | v002 建表时把分类限定为四值，`MEAL` 违反 CHECK；而 **`INSERT IGNORE` 会把 CHECK 失败降级成警告静默跳过** → 种子"登记了却没生效"，勋章静默不发（本轮实测踩到） |
| **D4** | 勋章发放粒度 | （未明确写清） | `MEAL_COOKED_1` 无论达成多少次都**只有 1 枚**；累计达标只补发更高阈值那枚；`MEAL_COOKED_30` 未到阈值不发 | `MedalService.award` 的幂等键是 `(definition_id, child_id, ref_id = 阈值)`，重复达成不重复发。测试断言已按此修正（首版误写成 10 枚） |
| **D5** | `Item.version` 暴露 | 未列入 | `WantEatBoardResp.Item` 增补 `version` 字段 | 家长端状态流转要回传 `expectedVersion`，原响应没给，前端无法做乐观锁 |
| **D6** | 小程序快捷区/推荐卡 | 未明确两者关系 | **共用** `quickFavorite()` 的三态前置校验 | 推荐菜与常吃菜来源都是"可能不在今日餐单"的历史派生，复用同一校验（在今日餐单且 `selectable` 才发请求，否则只 toast） |

### 其他落地细节
- **部分成功语义落到前端**：`pages/menu-week` 失败项**保留勾选**，家长可直接再点一次重试；结果区逐条显示 `成功/待重试`。
- **增强区块一律静默降级**：菜单页的推荐卡与周条接口失败时只隐藏对应区块（`recommend=[]` / `week=[]`），**不阻断**菜单主流程。
- **周视图空餐次占位不丢格**：区间内每一天 × 三餐**必返回格子**（未发布 → `menuId=null, dishCount=0`），家长"哪几天还没排"一眼可见。
- **测试用例并入独立类**：`WantEatP2IT` 实际 **10 个用例**（原计划 12+，部分断言并入同一方法）；小程序新增 5 个用例。
