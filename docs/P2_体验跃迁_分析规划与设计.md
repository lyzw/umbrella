> 前置：P0「每日想吃」数据模型、P1「家长按日清单 + 状态流转 + 派生常吃 + R6 去锁」均已落地并通过全量回归（2026-09-22，**140 用例 / 25 类**）。

## 一、P2 范围复核

原分析文档 §五 P2 共三项，本稿逐项复核可行性：

| 原 P2 项 | 原定解决 | 现状 | 本稿结论 |
|---|---|---|---|
| 「提前挑选 / 周计划」（无交易版预点） | 场景 | ❌ 未做；但**关键前置已具备**（见 2.1/2.2：孩子已能对未来日期标记，家长已能对未来日期发布） | **本期主体（成本最高）** |
| 「今天吃什么」推荐 | 场景 | ❌ 未做；画像 + 历史 + 安全判定**全部现成**（见 2.5） | **本期（中等成本）** |
| 采纳反馈闭环（接勋章） | 激励 | ⚠️ P1 已交付 `status=COOKED` 写接口，**未接勋章** | **本期（低成本，收益明确）** |

**明确不做（防止范围蔓延）**：

| 项 | 出处 | 不做原因 |
|---|---|---|
| 多孩按日汇总采购清单 / 学校侧供餐量预测 | §五 P3 | P3 范畴，成本高、需要新的聚合口径 |
| `SCHOOL.owner_key` 改 `school_id`（R4） | §七 总表 | 独立数据迁移项，与体验主题无关 |
| 过敏原白名单缺失导致全员 `UNKNOWN`（R5） | P1 设计 2.x 遗留 | 属安全合规项，应独立立项 |
| `ChildProfile.favoriteDishIds` 删列 | P0/P1 遗留 | **建议保留**：该字段已参与合规导出契约（`GET /api/compliance/requests/{id}/download` 返回 `profile.favoriteDishIds`，`PrivacyWorkflowIT` 有断言），删列须同步改隐私契约，属独立合规改动。**如要删请单独说明，不并入 P2。** |

## 二、代码事实核查（写设计前先对齐现状）

### 2.1 孩子标记「想吃」**不限制未来日期**

- `CatalogService.validateDateAndMeal()`（`:859-864`）只校验 `date` 年份合法（1000–9999）与 `mealType ∈ {BREAKFAST, LUNCH, DINNER}`，**没有任何"不得早于今天/晚于今天"的限制**。
- `CatalogService.markFavorite()`（`:314`）对菜单的校验只有三条（`:321-325`）：菜单存在、`status = PUBLISHED`、`(menuDate, mealType)` 与请求一致。
- ⇒ **孩子对"下周任何一天任意餐"标记想吃，只要该菜单已发布，当前后端就能写。** 周计划不需要新的数据模型。

### 2.2 家长发布菜单**已支持任意日期**

- `POST /api/parent/menu-daily`（FAMILY，家长）：`CatalogService.upsertFamilyMenu()`（`:174-182`）→ `upsertMenu()`（`:184+`），落库键为 `(source_type, owner_key, menu_date, meal_type)`，`status` 由请求给 `DRAFT` / `PUBLISHED`。
- `POST /api/admin/menu-daily`（`MenuController:72-75`）→ `upsertSchoolMenu()`（`:171`）：SCHOOL 菜单由管理端发布，`owner_key = school`。
- 小程序家长端菜单页已带 `<picker mode="date">`（`pages/menu/index.wxml:4`）+ `publish()`（`pages/menu/index.js:240-252`），**手工逐日发布下周菜单今天就能做**（一周 = 21 次发布）。

### 2.3 周计划两侧的真实缺口

| 缺口 | 现状 | 影响 |
|---|---|---|
| 「区间菜单概览」查询 | `GET /api/parent/menu-daily`（`readParent():116-129`）与 `daily()` 都是**单日单餐** | 家长要看"整周哪几天发了/空了"需 21 次请求；孩子同理 |
| 批量发布 | 只有单条 `upsertMenu`，且每条都带 `FOR UPDATE` + 乐观锁 | 家长发一周要 21 次往返，任一条失败需人工回补 |
| 孩子端周视图 | 菜单页日历选择器是裸日期（无周条/无"哪天已发菜单"提示） | 孩子不知道下周哪几天有菜单可挑 |

### 2.4 勋章基础设施（现有范式可照搬）

- 表：`life_medal_definition(code, name, description, icon, category, condition_type, threshold, sort_order, status)` + `life_medal_award`（`sql/v002_chore_medal.sql:49+`）。
- 已有种子：`CHORE_FIRST/CHORE_10/CHORE_STREAK3`（`v002_chore_medal.sql:97-101`）、`HEALTH_STREAK_3/7/14/30`（`v004_health_check.sql:41-46`）——**均用 `INSERT IGNORE`，可重复执行**。
- 发放入口：`MedalService.award(childId, familyId, code, refId, consecutiveCount)`（`MedalService:74-99`）：
  - **幂等**：同一 `(definition_id, child_id, ref_id)` 只发一次（`:81-86`）；COUNT/STREAK 类 `refId = threshold`，故"每人每阈值一次"。
  - **`Propagation.MANDATORY`**（`:74`）：**必须在已持有相关行锁的事务内调用**，不能从只读路径直接调。
  - 内部自带审计 `MEDAL_AWARD`（`:95-97`）。
- 现有调用范式（两处，结构一致）：
  - `ChoreService.awardChoreMedals(member, confirmedCount, currentStreak)`（`:215-231`）：按 `category='CHORE'` 拉全部启用定义，`COUNT` 比累计数、`STREAK` 比连续数，命中即 `award(...)`。
  - `CheckService.awardHealthMedals(member, streak)`（`:219-232`）：`category='HEALTH'` 且 `condition_type='STREAK'`。
- ⇒ P2 的"接勋章"= **新增一个 category + 一个 `awardMenuMedals(...)` + 在写事务里调用**，无新机制。

### 2.5 推荐所需数据**全部现成**

| 能力 | 位置 |
|---|---|
| 过敏冲突判定 | `CatalogService.allergyConflict(dish, profile)`（`:815-818`）：`dish.allergens ∩ profile.allergies` |
| 忌口判定 | `CatalogService.isDisliked(dish, profile)`（`:820-825`）：忌口词命中菜名或 `tags` |
| 常吃派生（30 天加权） | `CatalogService.frequentDishes(childId, limit)`（P1 已交付，权重 `1/(1+daysAgo/7.0)`） |
| 画像字段 | `ChildProfile`：`allergies` / `dislikes` / `tastes`（`:34-41`） |
| 菜品属性 | `Dish`：`calories` / `tags` / `allergens` / `spiceLevel` / `categoryId` |

### 2.6 小程序现状（改造落点）

- 菜单页 `pages/menu/index.{js,wxml,wxss}`：`role` 分流（`read()` 孩子 / `readParent()` 家长）；日期选择器 `index.wxml:4`；`checkout`（确认单）限 `menuDate === today`（`index.wxml:96`、`index.js:282`）；P1 已加分类 chips + 「孩子常吃」快捷区。
- 家长想吃看板 `pages/want-eat/*`：已有日期区间（默认今天起 7 天）+ 状态按钮 + 采购汇总。
- 勋章页 `pages/medal/*`：列表**平铺，不渲染 `category`**（`index.wxml:14-18`）⇒ 新增 category **不需要前端改动**。

### 2.7 写路径的事务与锁（调用勋章时必须遵守）

- `CatalogService` 为**类级 `@Transactional`**；`transitionWantEat()` 是写路径，走 `lockBoundChild` + 手写乐观锁（`UpdateWrapper.eq("version", before)` + 显式自增，0 行 → `E007`）。勋章调用点应放在该写事务内（满足 `MANDATORY`）。
- R6 约定（P1 定稿）：**新增读接口一律走只读变体**（`boundChild` / `requireConsentReadOnly` / `visibleDishesByRef` / `requireCompleteProfile`），不带 `FOR UPDATE`。本稿新增的周视图 / 推荐均为读接口，照此执行。

## 三、方案设计

### 3.1 分项 A：采纳反馈闭环（接勋章）

**触发点**：家长把孩子标记的想吃改为 `COOKED`（"今晚做了你标记的 XX"）→ 发勋章。

**设计**
1. 新增迁移 `sql/v006_want_eat_medal.sql`：
   - `INSERT IGNORE INTO life_medal_definition` 三条，`category = 'MEAL'`、`condition_type = 'COUNT'`：
     - `MEAL_COOKED_1`  「心愿达成」  首个孩子想吃被做出来  🌟  threshold 1
     - `MEAL_COOKED_10` 「小小心愿官」累计 10 次想吃被做  🍽 threshold 10
     - `MEAL_COOKED_30` 「餐餐有回应」累计 30 次想吃被做  🏆 threshold 30
   - 必须同步登记进 `application-test.yml` 的 `schema-locations`（P0 踩过坑：漏登记 → 测试库无数据）。
2. `CatalogService` 新增 `awardMenuMedals(FamilyMember member)`：
   - 统计口径：`SELECT COUNT(*) FROM usr_child_want_eat WHERE child_id = ? AND status = 'COOKED' AND delete_at = 0`（逻辑删除已自动过滤）。
   - 按 `category='MEAL'` 拉启用定义，`count >= threshold` 即 `medalService.award(childId, familyId, code, (long) threshold, 0)`。
   - 结构照抄 `ChoreService.awardChoreMedals`，幂等由 `award()` 保证 ⇒ **重复点 COOKED / 回退再标都不会重复发**。
3. 调用位置：`transitionWantEat()` 内、乐观锁 `update` 成功之后、**仅当目标状态为 `COOKED`** 时调用。
4. 前端：无需改动（勋章页平铺展示）。可选增强（列入"待确认"）：返回体里带 `newMedals` 让家长端 toast "孩子获得勋章「心愿达成」"。

**风险**：`transitionWantEat` 的越权/并发分支较多，勋章统计必须放在 update 成功之后，否则会把失败的流转也算进去。

### 3.2 分项 B：「今天吃什么」推荐

**端点**（建议 A 案，理由是复用当天已发布菜单的现有鉴权与可见性规则）：

- `GET /api/child/recommend?menuId={id}&limit={n≤5}`，`@RequireRole({CHILD, PARENT})`
  - 复用 `markFavorite` 的同一套归属校验：菜单存在 + `PUBLISHED` + FAMILY 家庭匹配 / SCHOOL `owner_key` 匹配。
  - 只读路径（`requireConsentReadOnly` + `visibleDishesByRef`），不加锁。

**打分规则（确定性、可解释，不引入外呼）**

| 步骤 | 规则 |
|---|---|
| 1 硬过滤 | `allergyConflict(dish, profile)` 为真 → **直接剔除**（安全红线，不可被分数覆盖）；`status != ON_SALE` → 剔除 |
| 2 软降权 | `isDisliked(dish, profile)` 为真 → 剔除（与菜单页"忌口"语义一致，如希望只降权不剔除，见决策 D3） |
| 3 正分 | 近 30 天常吃加权分（复用 `frequentDishes` 的权重公式） |
| 4 变化分 | 该菜品"本周（含今天）尚未被该孩子标记过想吃"→ 加分（避免推荐天天一样） |
| 5 偏好分 | `profile.tastes` 含清淡类词、或菜品 `spiceLevel` 低 → 加分；`spiceLevel` 高 → 减分 |
| 6 截断 | 取 Top `limit`（默认 3），同分按 `dishId` 升序稳定排序 |

**返回**：`{ menuId, menuDate, mealType, dishes: [{ type, id, name, imageUrl, categoryName, score, reasons: ["上周想吃 3 次", "本周还没吃过"] }] }`

**降级**：前端请求失败静默不展示（与 P1「常吃快捷区」同一策略：不阻断主流程）。
**落点**：孩子端菜单页顶部「今天吃什么？」卡片 → 点"加入想吃"复用 `markFavorite`（**注意**：推荐项已限定在当天菜单内，不存在 P1 快捷区那种"不在今日餐单 → 404"的问题，但仍建议复用 P1 的 `quickFavorite()` 前置校验逻辑以防菜单被家长改版）。

### 3.3 分项 C：周计划（提前挑选）

拆成 4 个可独立验收的子项：

**C1 家长周视图查询**
`GET /api/parent/menu-week?from={date}&to={date}`（`@RequireRole(PARENT)`，区间 ≤ 14 天，familyId 由鉴权派生）
→ `{ days: [{ menuDate, meals: [{ mealType, menuId, status, dishCount }, ...] }] }`
- 只读、不加锁；未发布的餐次返回 `menuId=null, status=null`（**不丢格子**，与 P1 want-eat board 的"不丢行"原则一致）。
- 一次 SQL 取区间内全部 FAMILY 菜单（`source_type='FAMILY' AND owner_key=familyId AND menu_date BETWEEN ?`），避免 21 次往返。

**C2 批量发布**
`POST /api/parent/menu-daily/batch`，body：
```json
{ "items": [ { "menuDate": "2026-09-28", "mealType": "LUNCH", "dishIds": [{"type":"PRESET","id":"1"}], "status": "PUBLISHED" } ] }
```
- **逐条独立结果**：返回 `{ results: [{ menuDate, mealType, ok, code? }], okCount, failCount }`；单条失败不回滚整批（家长最痛的是"21 次里第 13 次失败后要重来"）。
- 上限：`items ≤ 21`（一周 7×3），超限 400。
- 复用现有 `upsertMenu` 的校内私有逻辑（同一把 `DishRef` 校验、`ON_SALE` 校验、乐观锁），不新写一套发布逻辑。
- ⚠️ **待确认**：整批是否共用一个事务。建议**逐条独立事务**（`TransactionTemplate`），理由：批量发布允许部分成功，且避免长事务持锁。

**C3 孩子周视图**
`GET /api/child/menu-week?from&to&childId?`（`@RequireRole({CHILD, PARENT})`，孩子默认本人）
→ `{ days: [{ menuDate, meals: [{ mealType, menuId, sourceType, dishCount, wantEatCount, marked }] }] }`
- `marked` = 该餐次是否有本人的想吃记录（用于周条上的小圆点）。
- 只读、不加锁。点击某格 → 复用现有单日流程（`daily()` + `markFavorite`），**不新增写接口**。

**C4 家长需求汇总**：**已具备**，直接复用 P1 `GET /api/parent/want-eat?childId&from&to`（按日期×餐次分组 + 菜品去重采购汇总 + 过期计数）。

**小程序改造**
- 家长端：菜单页加"周"视图（7 天 × 3 餐格子：已发布/草稿/空，多选后"批量发布"）；或独立页 `pages/menu-week`。看板页复用现有区间切换即可。
- 孩子端：菜单页顶部加周条（`<picker mode="date">` 之上），非今天/明天时顶部提示"这是 9/28 的餐单，现在先挑好，到时家长再确认"——**避免与"确认单仅限今天"产生心智冲突**（`checkout` 仍限今天，不改）。

### 3.4 明确不动的既有契约

- 「确认单」（`life_menu_confirm` / `canSubmit`）语义与"限今天"不变；「每日想吃」保持"按日按餐的意愿标记，不等于下单"。
- `markFavorite` 的入参契约不变（仍要求 `menuId` + `menuDate` + `mealType` + `dishType`）。
- R6 只读/写路径的分离约定不变。

## 四、待确认决策点

| # | 决策 | 选项 | 推荐 |
|---|---|---|---|
| **D1** | 分批方式 | A 分 P2a（勋章闭环 + 推荐）/ P2b（周计划）/ B 一次做完三项 / C 只做闭环 + 推荐，周计划延后 | **A**：P2a 成本低、可当天验收；P2b 有前端新页，独立验收更稳 |
| **D2** | 周计划范围 | A 周视图 + 批量发布（C1+C2+C3）/ B 只做周视图，发布仍逐条调老接口（零新写接口）/ C 只做批量发布接口，前端下一批 | **A**：批量发布是家长侧真实痛点（21 次往返） |
| **D3** | 推荐算法尺度 | A 规则加权 + 推荐理由（3.2 全表）/ B 只按常吃 Top N（复用 `frequentDish`，零新算法）/ C 接大模型生成推荐 | **A**：可解释、零外呼成本；C 引入外呼与合规评估，不建议 |
| **D4** | 勋章触发与阈值 | A `COOKED` 触发 + COUNT 1/10/30 / B `ADOPTED`（家长采纳）触发 / C 两套 code 都要 | **A**：与"家长真的做给孩子吃了"这一正向时刻对齐，ARPU 语义最强 |

**另需你确认（非选项）**：C2 批量发布**是否允许部分成功**？本稿推荐"允许"（逐条独立事务）；若你要求"要么全成、要么全败"，实现会更简单但家长回补成本更高。

## 六、影响范围 / 回滚

| 层 | 预计改动 |
|---|---|
| 迁移 | 新增 `sql/v006_want_eat_medal.sql`（仅 `INSERT IGNORE` 种子，**无 DDL**，可安全重复执行） |
| 后端 | `CatalogService`（+推荐、+周视图、+批量发布、+`awardMenuMedals`）、`MenuController`（+4 个端点）、新增 3~4 个 DTO |
| 测试 | 新增 `WantEatP2IT`；`CatalogFlowIT` 不动 |
| 小程序 | `pages/menu/*`（周条 + 推荐卡）、可能新增 `pages/menu-week/*`（家长周视图）、`app.json` 注册、`pages.test.js` |
| 文档 | 本文 + 编码后回填「实现偏差」 |

**回滚点**：v006 只加种子数据，回滚只需 `UPDATE life_medal_definition SET status='DISABLED'`（不改代码即可停发）；新增端点均为只读或附加写，删端点不影响既有 P0/P1 流程。
