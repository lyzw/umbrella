# 亲子餐食「每日想吃」逻辑梳理与优化分析（v2 修订）

> 修订说明：
> - v1（已作废）误把"点选"当"外卖下单交易"对标美团，前提错误。
> - v2 校正为 **「亲子协同的每日想吃偏好收集 + 餐食规划工具」**。
> - **本次（v2.1）关键澄清**：想吃是**每日的、按天按餐的当天选择**，**不是**"我喜欢这道菜"的持久标注。下面所有分析以"每日想吃"为核心原语展开。

---

## 一、业务模型澄清（产品真相）

### 1.1 角色与核心动作

| 角色 | 职责 |
|------|------|
| **家长 PARENT** | 维护菜单来源（学校餐单由后台/家长维护；家庭菜单由家长加入菜谱）；查看孩子**某天某餐**的「想吃」清单；据此采购、烹饪 |
| **学生 CHILD** | 对着**某一天某一餐**的菜单，挑选"今天想吃这些菜" |

**核心动作 = 标记「每日想吃」**：孩子看着"今天/明天午餐的菜单"，选自己当天想吃的几道。
它不是下单，也不是"我永远爱吃这道"的收藏标签，而是**绑定到具体日期与餐次的当天意向**。

### 1.2 两个必须区分的概念（避免误把想吃做成持久标注）

| 概念 | 性质 | 数据落点（现状/建议） |
|------|------|---------------------|
| **每日想吃** | **临时、按日按餐**："9/22 午餐我想吃红烧肉+青菜" | 应带 `(childId, menuDate, mealType, dishRef, sourceType)` |
| **持久画像** | 长期稳定：忌口 `dislikes`、口味 `tastes`（清淡等） | 已是 `ChildProfile` 长期字段，**这两样才适合持久存** |
| **爱吃/常点（派生）** | 从历史每日想吃**归纳**出的稳定偏好 | **不应是手动持久标注**，应为派生视图（见第五节） |

> 关键边界：**"想吃"会过期**（过了那天就不再是"今天想吃"）；"忌口/口味"不过期。把它当成扁平持久列表，恰恰是把两种不同寿命的数据混在了一起。

### 1.3 两个菜单来源（差异只在"谁来维护目录"）

- **SCHOOL（学校餐单）**：后台/家长提前按日按餐发布，作为"给小朋友提前挑选的机会"。孩子对着当天/近几天的餐单标记每日想吃。
- **FAMILY（家庭菜单）**：家长把菜品加入菜谱并按日编排后，孩子从中挑选当天想吃的；方便家长后续查看与烹饪。
- 二者在"孩子按日标记想吃"上完全同构，区别只在菜品目录维护方。

### 1.4 价值闭环（围绕"某一天"）

```
家长/后台发布「9/22 午餐」菜单
        ↓
孩子浏览，标记「9/22 午餐想吃：红烧肉、青菜」
        ↓
家长查看「孩子 9/22 午餐想吃清单」
        ↓
家长据此采购食材、安排烹饪
        ↓
（可选）标记「今晚做了你标记的 XX」→ 给孩子正向反馈
```

### 1.5 真实亲子相处模式 → 产品启示

| 真实场景 | 产品该怎么做 |
|---------|------------|
| 孩子常说"我不知道今天想吃啥"、选择困难 | 引导式：分类浏览、图片、"今天吃什么"随机/智能推荐 |
| 家长每天追问"今天想吃啥"很累 | **按日收集**：家长一次看"今天/明天每餐孩子想吃啥" |
| 孩子口味稳定，有些"常点" | 「爱吃/常点」作为**派生视图**（从历史每日想吃归纳），而非新增手动持久标注 |
| 忌口、过敏、健康饮食 | 持久画像 `dislikes`/`tastes` 过滤（已有基础，需补过敏原） |
| 多孩家庭 | 每个孩子的每日想吃天然独立，家长侧"多孩按日汇总" |
| 孩子标记后石沉大海 | 「采纳反馈」：家长标记"已做/将做"，形成正向激励（可接勋章） |

## 二、现有实现梳理（代码 / 数据事实）

### 2.1 「想吃」的存储 —— 与"每日"意图不匹配（核心缺口）

- 现状位置：`usr_child_profile.favorite_dish_ids`（`ChildProfile.favoriteDishIds`，`List<Long>`），**每个孩子一条扁平、持久的 dishId 列表**。
- 迁移：`sql/sprint3_catalog.sql` 通过 `ALTER ... ADD COLUMN favorite_dish_ids JSON NOT NULL DEFAULT (JSON_ARRAY())` 增加。
- **问题**：这条列表是"持久收藏"语义，**没有 menuDate / mealType / sourceType**，无法表达"9/22 午餐想吃"。它把"每日想吃"错误地实现成了"永久爱吃"。这正是当前实现与产品意图最大的错位（见 R2）。

### 2.2 关键接口

| 接口 | 权限 | 作用 |
|------|------|------|
| `POST /api/menu/mark-favorite` | CHILD 本人 | 对某 dishId 标记/取消，幂等；字段仅 `dishId` + `favorite`(bool) |
| `GET /api/child/preferences` | PARENT（指定 childId） | 返回 `dislikes` / `tastes` / **`favoriteDishIds`（原始 ID 列表）** |
| `GET /api/menu/daily` | CHILD / PARENT | 取某日某餐菜单，菜品带 `isFavorite` 高亮 |

> 代码事实：`markFavorite` 只存裸 `dishId`，不区分 PRESET/FAMILY，也不带日期（`:298-320`）。
> 注意：`dislikes`/`tastes` 是**正确的**持久画像字段；问题只出在把"想吃"也持久扁平化了。

### 2.3 菜单展示逻辑 `daily()`（`:246-296`）

- `sourceType` 仅接受 `SCHOOL` / `FAMILY`。
- `owner_key`：`FAMILY` 用 `familyId`；`SCHOOL` 用 `profile.getSchool()`（**校名文本**，见 R4）。
- 菜品 `favorite` 高亮：
  ```java
  .favorite("PRESET".equals(ref.getType()) && favorites(profile).contains(ref.getId()))
  ```
  ⚠️ **只对 `PRESET` 类型高亮**（R1）：FAMILY 私有菜即使已标记想吃也不显示。
- `canSubmit`/`canSelect`：仅 `CHILD + FAMILY + 当天` 为真；SCHOOL 永远只读 + 想吃（与小程序"学校餐单仅供查看和标记想吃，不会创建确认单"一致）。

### 2.4 菜单数据模型

- `life_menu_daily`：`source_type` + `owner_key` + `dish_ids`(JSON，`DishRef{type:PRESET|FAMILY, id}`)，**天然是按日按餐**的（带 `menu_date` + `meal_type`）。
- `life_dish`（公共）+ `life_family_dish`（家庭私有，带 `family_id` + `visibility`）。
- 引用统一用 `DishRef` 避免 PRESET/FAMILY 两条序列撞号。
- **矛盾点**：菜单本身是"按日按餐"的，但"想吃"却被存成"孩子终身扁平列表"——同一业务里粒度不一致。

## 三、对标美团：借鉴「按天选择 · 发现 · 偏好」层

美团对我们最有价值的**不是**"购物车/支付/骑手/交易闭环"，而是它帮用户**按场景低成本地记录"某顿想吃什么"**的能力。

| 美团能力（非交易侧） | 对应我们 | 可借鉴点 |
|---------------------|---------|---------|
| 「预点 / 提前点餐」按日期选 | **每日想吃**（无交易版） | 周末提前选好下周每天每餐想吃的，最贴合你的描述 |
| 「今天吃什么」智能推荐 | 今日推荐 | 基于历史每日想吃 + 忌口 + 营养引导，缓解选择困难 |
| 分类 / 图片流 / 清淡筛选 | 菜单浏览 | 分类聚合、菜品图、忌口过滤 |
| 「常点」 | **派生**的爱吃视图 | 从历史每日想吃归纳，**不是**手动持久标注 |
| 「已售罄 / 估清」 | 家长标记"今天不做这道" | 给孩子实时反馈 |

**明确 NOT 借鉴**：下单支付、骑手配送、商家接单、满减——本系统是家庭/校园内的按日偏好协同。

## 四、已确认的问题与风险（均有代码事实支撑）

### R1（✅ 已修复 2026-09-21）「想吃」高亮只对 PRESET 菜品生效
- 位置：`:286`。原现象：家庭菜单含 `FAMILY` 私有菜时，孩子标记的想吃不显示高亮。
- 根因：当时 `favoriteDishIds` 仅存裸 `dishId`，而 `life_dish`(PRESET) 与 `life_family_dish`(FAMILY) 是两条独立自增序列，裸 id 会撞号；直接去 PRESET 限制会误命中另一序列的同号菜品。
- 修复（已落地）：`favoriteDishIds` 改为类型化 `"TYPE:ID"` 字符串（与菜单 `DishRef` 约定一致），高亮对所有来源生效；新增 `resolveDishType`/`lockDishByType` 支持 FAMILY 菜品，并兼容历史裸数字数据与旧调用。小程序同步放开 FAMILY 菜品的想吃按钮与本地高亮。`CatalogFlowIT` 15/15 通过。

### R2（核心错位）「想吃」被实现成持久扁平列表，丢失"每日"语义
- 当前 `favoriteDishIds` 是 per-child 终身列表，**无法回答"孩子 9/22 午餐想吃啥"**，也混淆了"今天想吃"与"一直爱吃"。
- 这是当前实现与"每日想吃"产品意图之间最大的断层，也是后续"按日视图/周计划"做不出来的根因。

### R3（家长视图缺口）家长入口只返回原始 dishId 列表
- `GET /api/child/preferences` 返回 `favoriteDishIds: ["11","42"]`，**未映射到具体日期/餐次/被采纳状态**。
- 家长真正想要的是："9/22 午餐孩子想吃 A、B；其中 C 我已买/已做"——需要**按日按餐聚合**视图（且过期日期的想吃应不再计入"今天"）。

### R4（数据风险）SCHOOL `owner_key` 用校名文本
- 位置：`:264`。同名学校会共用 `owner_key` → 跨校串单。建议改 `school_id`。

### R5（安全/过滤）过敏原白名单缺失 → 全员 `UNKNOWN`
- 菜品过敏原未维护时 `safetyStatus=UNKNOWN`，孩子无法标记想吃（`canSelect` 要求 `DECLARED`）。需补齐过敏原与"未知即提示家长"兜底。

### R6（性能）`daily()` 展示查询使用 `FOR UPDATE` 行锁
- 位置：`:266`。纯展示路径加排他行锁，放学高峰会串行阻塞。建议去掉，仅在写事务中锁。

### R7（✅ P0 决策已定 2026-09-21：确认单保留）
- 用户确认：`life_menu_confirm` / `canSubmit`（FAMILY+当天）的「下单 / 确认单」能力**予以保留**，不做删除。
- 与"每日想吃"的关系：两者并存——「想吃」是孩子的按日偏好标记（无需下单），「确认单」是家长侧的另一套既有能力（保留原语义）。产品文案上需持续区分两者，避免用户心智混淆。

## 五、优化建议（按优先级，贴合亲子场景）

### P0 — 定位澄清（决策项，先做）
1. 确认 `life_menu_confirm`/`canSubmit` 的「下单」能力是否保留、语义是什么（R7）。
2. **确认"想吃"以「每日按餐」为原语**（R2）——这是后续所有按日视图/周计划的前提，也是数据模型改造的方向。

### P1 — 低成本高收益（建议优先排期）
- **[R1] 修「想吃」高亮 bug**：去掉 `PRESET` 限制，让 FAMILY 私有菜的想吃也可见。
- **[R3] 家长「按日想吃清单」聚合视图（核心价值）**：以"日期 + 餐次"为主轴展示孩子想吃；
  显示「已采纳 / 已烹饪」状态；过期日期的想吃自动不计入"今天"；支持一键生成当日采购清单。
- **[R2] 数据模型升级为「每日想吃」**：把扁平 `favoriteDishIds` 改为按 `(childId, menuDate, mealType, dishRef)` 存储（见第六节方案 B，本次升级为首选）。
- **[R6] 去掉 `daily()` 展示查询的 `FOR UPDATE` 行锁**。
- **浏览体验强化**：分类聚合 + 菜品图 + 忌口/清淡筛选（已有 `mildOnly`/`dislikes` 基础，补 UI 与过敏原）。

### P1（派生，非新增标注）「爱吃 / 常点」视图
- **明确：不新增"手动持久收藏"功能**。基于历史每日想吃做频数/近期加权归纳，在菜单顶部给出"孩子常吃"快捷区，降低选择成本。
- 这样"爱吃"始终是**真实行为的派生**，不会出现"标了爱吃但今天不想吃"的矛盾。

### P2 — 体验跃迁（依赖 P0-2）
- **「提前挑选 / 周计划」**：周末由后台或家长发布下周每天每餐的菜单 → 孩子逐日标记想吃 → 家长看到"下周每日需求汇总"。这正是美团「预点」的**无交易**版本，最贴合你的描述。
- **「今天吃什么」推荐**：基于历史每日想吃 + 忌口 + 营养做引导式推荐。
- **采纳反馈闭环**：家长标记"今晚做了你标记的 XX" → 正向激励（接勋章/成长模块）。

### P3 — 规模化（可选）
- **多孩按日汇总采购清单**：家长端把多个孩子某天的想吃合并去重，按食材聚合。
- **学校侧按日需求聚合（供餐量预测）**：对 SCHOOL 菜单按菜品汇总"想吃"人数，供食堂/家长估算分量（类校园预订，但无交易）。

## 六、数据模型 / 接口改动草案（给研发参考）

### 6.1 「每日想吃」存储模型（解决 R2，推荐方案 B）

新增 `usr_child_want_eat` 表（**替代**扁平 `favoriteDishIds` 的"想吃"语义；`dislikes`/`tastes` 仍留在 `ChildProfile` 作为持久画像）：

```
usr_child_want_eat (
  id            BIGINT PK,
  child_id      BIGINT,
  menu_date     DATE,          -- 哪一天
  meal_type     VARCHAR,       -- BREAKFAST/LUNCH/DINNER
  source_type   VARCHAR,       -- SCHOOL / FAMILY
  dish_type     VARCHAR,       -- PRESET / FAMILY（DishRef 类型）
  dish_id       BIGINT,        -- DishRef id
  status        VARCHAR,       -- MARKED / ADOPTED(家长已采纳) / COOKED(已烹饪)
  created_at    DATETIME,
  UNIQUE (child_id, menu_date, meal_type, dish_type, dish_id)
)
```

- 优点：天然支持 R2/R3 的按日按餐聚合与"采纳"状态机；过期日期的想吃查询时直接 `menu_date >= 今天` 过滤即可。
- 迁移：把存量 `favoriteDishIds` 按"无日期"归档为历史常吃素材（用于派生"爱吃"视图），新写入全部走新表。
- 若暂不愿新建表，方案 A（给 `favoriteDishIds` 元素加 `{dishId, type, markedAt, mealType?}`）只解决了"类型/时间"，**仍无法表达 menuDate 归属**，不推荐作为终态。

### 6.2 家长「按日想吃清单」接口草案（解决 R3）
```
GET /api/parent/child/{childId}/want-eat?from=2026-09-22&to=2026-09-28
→ 按 menuDate + mealType 分组的想吃清单（仅返回 menuDate 在范围内的）
→ 每项含 dish 信息、sourceType、status(标记/已采纳/已烹饪)
→ 附带「当日采购汇总」（按食材去重，仅含 MARKED/ADOPTED 项）
```

### 6.3 R1 修复说明（已实现 2026-09-21）
原拟"去掉 PRESET 限制"的纯 ID 命中会因 PRESET/FAMILY 撞号引入误命中，故改为**类型化存储**：
- `ChildProfile.favoriteDishIds`：`List<Long>` → `List<String>`（元素为 `"TYPE:ID"`，如 `"PRESET:11"` / `"FAMILY:5"`）。
- `daily()` 高亮：`.favorite(typedFavorites(profile).contains(ref.getType() + ":" + ref.getId()))`，对所有来源生效。
- `markFavorite`：新增 `resolveDishType`（客户端可传 `dishType`，未传按菜品存在性推导）与 `lockDishByType`（FAMILY 查 `life_family_dish` 并带 `family_id` 隔离）；`typedFavorites` 兼容历史裸数字（按 PRESET 兜底），**无需数据迁移**。
- 小程序：`pages/menu/index.wxml` 按钮放开为 `role === 'CHILD'`（不再限 PRESET）；`index.js` 调用携带 `dishType` 并以 `sourceType + ':' + dishId` 同步本地高亮。
- 测试：`CatalogFlowIT` / `PrivacyWorkflowIT` 断言已更新为类型化 key；`MarkFavoriteReq` 新增可选 `dishType`（旧调用向后兼容）。
