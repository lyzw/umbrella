一、文档范围与设计基础

1.1 设计目标回顾（来自功能规划）

  • 主角：11 岁六年级儿童。能独立图文点按，不擅长长表单；对游戏化、勋章、动画敏感；自我保护意识弱，需家长护栏。
  • 家长护栏优先：无真实支付，消费走「虚拟零花钱（虚拟消耗额）」记账；对外联系 / 位置 / 内容发布需家长授权或审批流。
  • 大字号 + 强图标 + 语音辅助：降低识字与输入门槛。
  • 即时正反馈：每完成一件事给予勋章 / 动画 / 进度。
  • 隐私合规：最小化采集、家长明示同意、可撤回、可导出 / 可删除。
交互设计基线：移动优先，从 320px 验证起；正文对比度 ≥ 4.5:1，大字号与 UI 组件 ≥ 3:1；动效仅作用于 transform / opacity，时长 0.2–0.3s。
术语统一（采纳 R-15）：本文档所有金额符号 ¥ 均表示虚拟消耗额（虚拟零花钱记账单位，非真实货币）。UI 文案建议统一为「虚拟币 / 积分」或保留 ¥ 但明确标注「虚拟」，避免与真实支付混淆。

1.2 文档覆盖边界

本文档以 P0 地基 + P1 小当家·点餐（首期 MVP / V0.0.1） 为深耕对象，给出可直接落地的页面结构、操作路径与状态定义；对 P2–P4 给出核心模块的交互框架与差异点。后台以「配置 + 审核 + 风控」为主，本文描述其与两端的触点（见 3.10）。

V0.0.1 范围锚定（采纳 R-02/R-06/R-13 等）：V0.0.1 仅上线「点餐」主链路（展示 + 提报 + 家长护栏 + 虚拟记账）+ 必要的登录/家庭绑定/额度设置最小集；其余模块按阶段渐进开放，未开放入口采用「占位·敬请期待」，避免儿童误入空功能。

3.1 微信登录 + 儿童档案（含 onboarding）

页面结构
  • 启动页 → 微信授权按钮（唯一主操作）
  • 欢迎页（角色选择：我是孩子 / 我是家长）
  • 最小账号与绑定申请：未同意不展示或保存儿童档案表单
  • 家长针对 childId/applyId 明示同意（见 3.3）
  • 家庭绑定成功后，由家长填写档案；儿童仅维护非安全偏好
操作路径（首次）
  1. 系统启动调 wx.login 拿 code → 后端 code2Session 换取 openid，建最小账号会话
  2. 儿童点登录 → 首次选择 CHILD；不自动获取昵称/头像
  3. 儿童输入邀请码 → 最小绑定申请，等待家长同意与审批
  4. 家长完成同意与绑定 → 创建档案；BOUND 且 COMPLETE 后展示入学勋章
边界：未登录只看公开演示；未同意不采集儿童档案、草稿或行为埋点。最小账号标识仍可能属于个人信息，处理依据与替代流程须通过 Q-01。已绑定但档案未完成时引导家长补全；家长只读预览不得绕过 CHILD 授权。

3.3 家长身份确认 + 授权（合规同意流）

设计闸门：声明、身份核验、监护关系核验分别留痕，最低强度由合规确认。

Q-01：微信登录、明示同意和自报年龄只能记录 SELF_ATTESTED，不能证明身份或监护关系。VERIFIED 仅用于有证据的核验流程；最低核验强度批准前，不开放儿童真实数据采集，不能默认后置核验。
  1. 家长进入「监护关系确认」→ 展示《儿童个人信息处理同意书》（可展开全文）
  2. 家长独立勾选「我已阅读并同意」（不可与登录合并）
  3. 系统校验自报年龄为18–120整数，仅记录声明，不据此认定监护资格
  4. 系统按 childId、applyId、协议版本保存 SELF_ATTESTED；若接入核验，身份与关系证据分别验证后才可写 VERIFIED
  5. 家长可随时在「安全与权限」撤回同意 → 子账号相关采集能力即时降级
异常：自报年龄不在18–120整数范围、声明不完整或证据核验失败，明确原因并提供「换账号/联系客服」，不得静默通过。年龄校验本身不证明监护资格；所有同意操作留痕。

3.8 菜单确认 / 提报（家庭）— 核心流程 已修订 R-01

3.9 菜单确认状态追踪 & 就餐偏好 & 消费记录

  • 状态机：PENDING可转COMPLETED、REJECTED或CANCELLED；复核中仅PENDING展示标记，不持久化APPROVED。审批与记账同事务，失败保持PENDING；改后重提创建新ID并关联原单。
  • 偏好持久化：儿童只改dislikes/tastes；过敏仅家长维护，UNKNOWN或命中过敏原禁止提交/审批，不喜欢只提示。「我爱吃」长期保存，重复标记幂等。
  • 消费记录：儿童端「零花钱」流水按场景（点餐/任务/奖励）着色；家长端「消费看板」汇总按日/周/月切换（U-G-09 流水明细屏）。

3.10 后台触点（菜单配置，采纳 R-11 / U-G-11）

后台管理菜品和SCHOOL学校菜单，仅展示/标记想吃，canSubmit=false。家长在自己账号配置FAMILY家庭菜单，才走儿童提报→家长审批→原子记账；来源/家庭/日期/餐段由服务端校验（Q-08）。

「改一改」保存替代建议并驳回原单，不覆盖明细；儿童确认后以新ID提交。U-G-06是历史问题编号，首版不作营养达标判断，只展示有来源信息，缺失显示「暂无数据」。

统一状态语言，降低儿童认知负担。所有列表/详情页均遵循下表；业务状态（待确认/复核中/已记账/已驳回）见第三、五、九章。

状态触发界面表现儿童友好要点

分层反馈原则：轻操作 → Toast；重要变更 → 站内通知 + 订阅消息；监护相关 → 站内+本人订阅；短信后置；成就 → 动画庆祝。
机制适用形式时效
Toast点按成功/失败、记账结果顶部/中部轻提示，2s 消失，不打断即时
站内通知中心全部系统事件聚合铃铛红点 + 列表（已读/未读）持久
订阅消息家长复核、到点提醒、确认完成微信服务通知模板（须先引导授权，3.5）即时推送
家长短信兜底审批超时、关键安全提醒短信（可选/兜底，V0.0.1 后置，R-04）兜底
勋章/动画任务完成、连续打卡、兑换成功弹出庆祝动画 + 音效（可关）即时激励
进度反馈成长树、连续天数、预算使用进度条/浇水动画持续
家长护栏反馈一致性：儿童端提交超额/敏感动作后，仅见状态（「已告诉爸妈，等确认」），不显示「被拦截/拒绝」等负面词；驳回原因由家长以温和语言在确认单内说明，保护儿童情绪。

六、主要用户场景

场景 A：孩子首次使用 —— 登录到家庭绑定

  1. 儿童以独立账号建立最小登录上下文→首次选择CHILD；家长只读预览不能代登或提交（Q-07）
  2. 系统Q-01通过后开放最小绑定流程；此时不采集档案、行为埋点或本地档案草稿
  3. 儿童「加入家庭」输入家长给的 6 位邀请码 → 提交申请
  4. 家长在本人账号查看绑定申请，针对childId/applyId/协议版本明示同意，记录SELF_ATTESTED而非核验成功
  5. 家长最低核验门槛满足且有效同意后批准绑定，再填写儿童档案；过敏信息仅家长编辑
  6. 系统绑定后双方通知中心显示「家庭已连通」；BOUND且档案COMPLETE才展示入学勋章

场景 B：孩子首餐 —— 确认菜单到记账（首期核心，已按 R-01 修订）

  1. 儿童Tab「点餐」→ 浏览今日菜单（大图卡 + 营养标签）→ 标记「想吃」
  2. 儿童点「去确认今日菜单 →」→ 勾选菜品/份量/备注（忌口自动带入）
  3. 系统生成待家长确认单（预览显示「预计扣减后余额（待爸妈同意）」，此时未扣减）
  4. 家长收到审批卡片，额度内一键「同意」
  5. 系统最新规则校验后同事务提交扣款、额度、流水、审批、COMPLETED及通知事件；儿童刷新显示「已记账」和余额，不输出营养达标结论

场景 C：超额异步复核（护栏核心，已按 R-01 修订）

  1. 儿童选了超单日上限的套餐 → 点提交
  2. 系统不实时拦截 → 进入「待家长确认」（非实时拦截），暂挂起不扣减
  3. 家长收到「孩子想点一份超预算的餐」审批卡片
  4. 家长查看明细 → 「放行」（显式确认）/「改一改」（推送替代建议）/「拒绝」
  5. 系统若放行→家长同意后扣减并通知「爸妈同意啦」；若拒绝→孩子见温和说明「今天先选便宜点的好不好？」

场景 D：家务得奖励（P2 动机闭环，标注为 P2 示意）

  1. 儿童「任务」Tab（P2 开放）→ 领「整理书桌」→ 完成后拍照打卡
  2. 家长审批卡片确认「完成」
  3. 系统零花钱 +5 + 颁发「整理小能手」勋章 → 动画庆祝
  4. 儿童去「奖励兑换中心」用积分换「多看 30 分钟动画」（虚拟权益，家长确认）

场景 E：合规 —— 家长撤回同意与数据导出

  1. 家长「设置-安全与权限」→ 撤回某类采集同意
  2. 系统按授权锁提交顺序阻止新写入（E-010），取消敏感通知重试，保留权利请求入口
  3. 家长本人重新鉴权→创建导出工单→查看处理进度→READY时鉴权下载（24h有效，过期410）
  4. 家长删除二次确认→创建工单→人工审核保留例外并清理主库/缓存/导出文件，恢复备份后重放删除记录；1工作日受理、15工作日办理为待批准服务目标

动效遵循克制原则，仅动画 transform/opacity（GPU 加速）；检测到系统「减弱动态效果」偏好时自动降级为无动画。游戏化适度，设使用时长提醒防沉迷。视觉皮升级（毛玻璃、渐变微光、Lottie 弹簧动效、2.5D 插画）属《高保真 UI 设计方案》范畴，不在本交互文档。

八、无障碍检查清单（WCAG 2.2 AA）

  • 待验收：正文项目目标 ≥4.5:1；关键蓝色白字用 #1d4ed8、绿色白字用 #15803d。旧 #3b82f6 白字约3.68:1，不能宣称达标。
  • 待验收：语义化 HTML（header/nav/main/button），禁止仅以颜色传达状态——状态均配图标 + 文字（如「复核中」配时钟图标）。
  • 待验收：原生 button 优先；HTML 必要时用合法 role 并实现键盘行为，小程序使用平台语义。静态原型不证明读屏可用。
  • 后续P2：语音辅助：关键菜品/任务支持「朗读」；输入支持语音转文字，降低识字门槛（朗读功能 P2 可选，R-08）。
  • 待验收：所有可操作目标 ≥44×44px，包括列表份量微调；这是项目设计标准。
  • 待验收：动画可关闭；重要提示不依赖颜色与声音单一通道。
  • 待验收：错误文案儿童可懂，提供明确下一步行动。

9.2 合规交互配套

  • 儿童敏感个人信息：最小化采集、明示同意、可撤回、可导出/删除（第三章已覆盖，隐私指引明示「儿童个人信息」特殊处理并加密留痕）。
  • 监护人同意：按3.3分别记录声明与核验证据，Q-01未通过不开放真实儿童数据。
  • 虚拟货币/实物兑换：首期仅虚拟权益，规避经营资质风险（3.9/P2）。
  • UGC 安全：读后感/AI 对话标「审核中/通过才公开」，机审+人审、违规处置与未成年人保护词库（第三章）。
