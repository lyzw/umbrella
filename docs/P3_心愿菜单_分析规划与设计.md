### 1.1 原文四条 → 拆解

## 二、现状核查（代码事实）

### 2.1 可选菜谱现状

- **家庭私有菜品**：`life_family_dish`（`sql/v002_family_dish.sql:8`），`status IN ('ON_SALE','OFF_SALE')`、`allergen_status IN ('UNKNOWN','DECLARED')`；家长在 `pages/dish-manage`（首页「我的 → 我的菜品」）维护，后端 `FamilyDishController`（`/api/parent/family-dish`）。
- **平台预置菜品**：`life_dish`（`sql/sprint3_catalog.sql:19`），ADMIN 维护；家长读接口 `GET /api/parent/dish`（`MenuController:84-90`）。
- 分类表 `life_dish_category` **两表共用**（`life_family_dish.category_id` 外键指向它）→ 分类维度天然统一。
- **缺口**：儿童端**没有任何**菜谱目录读接口（`/parent/*` 均为 PARENT 角色）。→ 需新增儿童侧只读目录接口（§四 4.3 接口 1）。

### 2.2 「每日想吃」现状（本次要复用的载体）

- 表 `usr_child_want_eat`（`sql/v005_child_want_eat.sql`）：`child_id / family_id / menu_date / meal_type / source_type / dish_type / dish_id / status / version`，唯一键 `(child_id, menu_date, meal_type, dish_type, dish_id, delete_at)`。
  - `meal_type` / `source_type` 均 `VARCHAR(16) NOT NULL` 且**无 DB CHECK**（只有列注释）→ 可安全承载新取值（本设计用 `meal_type='ALL'`、`source_type='WISH'`）。
  - **唯一键含 `delete_at`**（软删后可重新标记）；**不含 `source_type`**。
- 接口：`POST /menu/mark-favorite`（`CatalogService.markFavorite():336-398`，**强制菜必须命中当天菜单 typed refs**，否则 404）、`GET /child/want-eat`、`GET /parent/want-eat`（按日 board）、`POST /parent/want-eat/{id}/status`、`GET /child/frequent-dish`。
- `status = MARKED/ADOPTED/COOKED` 是**家长采纳流转**语义，与"提交/撤回"无关 → 本设计**不复用该列**表达提交状态，提交状态放在新的头表。

### 2.3 通知中台（F-011）现状

- 写入口 `NoticeService.recordEvent(eventKey, eventType, familyId, childId, receiverId)`（`NoticeService.java:29-56`）：
  - `@Transactional(propagation = MANDATORY)` → **必须由已开启事务的调用方在同一事务内调用**（`NoticeCenterFlowIT:79-98` 有断言）。
  - `eventKey` 须匹配 `[A-Za-z0-9:_-]{1,128}`、`eventType` 须匹配 `[A-Z0-9_]{1,32}`、三个 id 必须为正。
  - 一次调用写 **2 行**：`IN_APP`（`PENDING`，家长站内可读）+ `SUBSCRIBE`（`UNAUTHORIZED`，待家长授权）；同 `(event_key, receiver_id, channel)` 幂等跳过，若 `eventType/familyId/childId` 不一致 → `E012`。
- 站内箱 `NoticeCenterService`（`channel=IN_APP` + `receiver_id=当前用户`）；`NoticeResp{ id, eventType, familyId, childId, read, createTime, subscriptionNoticeId, subscriptionStatus }` —— **不含 menuDate/menuId**。
- 订阅投递三闸门：`deliveryEnabled` + `platformApprovalReference` 非空 + `templates` 命中（`NoticeDeliveryService:47-49`）；当前 `application.yml` **无 notice 段** → 真实投递未开闸，IN_APP 保底可用。
- 小程序通知页文案映射 `pages/notices/index.js:4-6`（6 个 eventType），条目**无跳转** → 需补 `WISH_SUBMIT` + 跳转。

### 2.4 家庭级「设置」现状

- `usr_family`（`sql/sprint1_schema.sql:23`）只有 `family_name / owner_user_id / invite_code / invite_code_expire`，**无任何设置字段**；项目也不存在通用家庭设置表。
- 同类先例：`life_allowance_rule`（家长为家庭钱包配置额度规则，独立表 + version 乐观锁，`sql/sprint2_schema.sql:18`）→ 本设计照此新建独立设置表。

### 2.5 必须复用的项目范式

| 范式 | 位置 / 来源 | 本设计如何遵循 |
|---|---|---|

## 四、定稿设计

### 4.1 数据模型（`sql/v007_wish_menu.sql`，纯增量）

```sql
-- 1) 家长配置（无行 = 默认 5 / 开启）
CREATE TABLE usr_family_setting (
  id                   BIGINT  PRIMARY KEY AUTO_INCREMENT,
  family_id            BIGINT  NOT NULL,
  wish_menu_max_dishes TINYINT NOT NULL DEFAULT 5,
  wish_menu_enabled    TINYINT NOT NULL DEFAULT 1,
  version              INT     NOT NULL DEFAULT 0,
  create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  delete_at   BIGINT   NOT NULL DEFAULT 0,
  UNIQUE KEY uk_family_setting (family_id, delete_at),
  CONSTRAINT fk_setting_family FOREIGN KEY (family_id) REFERENCES usr_family (id),
  CONSTRAINT chk_setting_max CHECK (wish_menu_max_dishes BETWEEN 1 AND 10),
  CONSTRAINT chk_setting_enabled CHECK (wish_menu_enabled IN (0, 1))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='家庭级设置';

-- 2) 心愿菜单提交单（一天一份；DRAFT 不需要——无提交单即"未提交"）
CREATE TABLE life_wish_menu (
  id             BIGINT NOT NULL AUTO_INCREMENT,
  child_id       BIGINT NOT NULL,
  family_id      BIGINT NOT NULL,
  menu_date      DATE   NOT NULL,
  status         VARCHAR(16) NOT NULL COMMENT 'SUBMITTED/WITHDRAWN',
  max_dishes     TINYINT NOT NULL COMMENT '提交时快照的家长上限（回看当时口径）',
  dish_count     INT NOT NULL DEFAULT 0,
  submit_version INT NOT NULL DEFAULT 0 COMMENT '每次提交 +1；通知幂等键的第二段',
  submit_time    DATETIME DEFAULT NULL,
  create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  delete_at   BIGINT   NOT NULL DEFAULT 0,
  version     INT      NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  UNIQUE KEY uk_wish_child_date (child_id, menu_date, delete_at),
  KEY idx_wish_family_date (family_id, menu_date),
  CONSTRAINT fk_wish_family FOREIGN KEY (family_id) REFERENCES usr_family (id),
  CONSTRAINT chk_wish_status CHECK (status IN ('SUBMITTED','WITHDRAWN'))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='儿童心愿菜单提交单（每天一份）';

-- 3) 明细复用想吃表：加"被收编到哪张心愿单"
ALTER TABLE usr_child_want_eat ADD COLUMN wish_id BIGINT NOT NULL DEFAULT 0;
ALTER TABLE usr_child_want_eat ADD KEY idx_want_eat_wish (wish_id);
```

**`wish_id` 语义**：`0` = 未收编（普通想吃标记）；`>0` = 已被该心愿单的**上一次提交**收录（撤回后**保留**，用于回显「上次提交了哪些」，便于撤回改选）。

**心愿目录标记写入的取值**：`meal_type='ALL'`（心愿菜单不分餐次）、`source_type='WISH'`（无菜单上下文）。两列均 `VARCHAR(16) NOT NULL` 且无 CHECK，无需 DDL 变更。

### 4.2 状态与锁定规则

```
(无提交单) ──提交(1..上限)──▶ SUBMITTED ──撤回──▶ WITHDRAWN ──再提交(version+1)──▶ SUBMITTED
     ▲                                                                                │
     └─────── 锁定期间：标记增删一律 E400；重复提交按"版本→状态"判为 E007 或 E400 ────────┘
```

| 状态 | 标记增删 | 提交 | 撤回 | 家长查看 |
|---|---|---|---|---|
| 无提交单 / `WITHDRAWN` | ✅ | ✅ | ❌（无提交单→E404/E400） | 400 文案"孩子还没提交" |
| `SUBMITTED` | ❌ E400 | ❌ E400 | ✅ | ✅ 展示清单 |

- 锁定判定的**唯一依据**是头行 `status='SUBMITTED'`（不需要给明细打锁标记）。
- 锁定生效范围 = 该 `(childId, menuDate)` 当日全部想吃行 → 因此 `markFavorite`（现有接口）在该日也会被拒写（§五 修改项）。

### 4.3 接口契约（新增 9 个端点，新建 `WishMenuController`）

**儿童侧（`@RequireRole CHILD`）**

```
1. GET  /api/child/wish-catalog?menuDate&sourceType=FAMILY|PRESET&categoryId&keyword&page&pageSize
   → PageResp<{ dishId, type, categoryId, categoryName, name, imageUrl, spiceLevel, virtualPrice,
                allergenStatus, allergyConflict, disliked, selectable, marked }>
   FAMILY → life_family_dish[family_id=登录派生家庭, status=ON_SALE]
   PRESET → life_dish[status=ON_SALE]
   两表各自分页（UI 双 Tab），不做跨表合并分页；marked = 该 (childId, menuDate) 已标记。

2. GET  /api/child/wish-menu?menuDate
   → { menuId?, childId, menuDate, today, status: NONE|SUBMITTED|WITHDRAWN, enabled, maxDishes,
       dishCount, submittedCount, canSubmit, canEdit, locked,
       items: [{ type, id, name, imageUrl, categoryName, categoryId, spiceLevel,
                 mealTypes:[...], submitted, missing, safetyStatus, allergyConflict, disliked }] }
   items = 该日想吃行按 (type,id) 去重后的候选池；菜品信息批量预取（避免 N+1）。
   missing=true 占位不丢行（菜品下架/删除后仍可见并可移除）。

3. POST /api/child/wish-mark     { menuDate, type, id, selected }
   → 同 2 的响应体
   校验：enabled；窗口 [today, today+6]；未锁定；type ∈ {PRESET,FAMILY}；菜在售且对孩子可见
        （FAMILY 必须属于登录派生家庭）；allergenStatus='DECLARED' 且无过敏冲突（否则 E400）
   写：selected → 该 (childId,menuDate,'ALL',type,id) 无行则插入；false → 软删

4. POST /api/child/wish-menu/submit   { menuDate, refs:[{type,id}], expectedVersion }
   → 同 2 的响应体
   校验：enabled；窗口；refs 去重后 1..maxDishes（超限 → **E-014** 独立错误码，见变更文档 §八 偏差 1）；
        每个 ref 必须能在该日想吃行中匹配到未删除行（否则 E400）；
        **每个 ref 必须仍可安全提交**（在售 + 过敏信息 DECLARED，fail closed，见偏差 4）；
        版本判定先于状态判定（陈旧 expectedVersion → E007；版本一致但已提交 → E400，见偏差 3）
   写：头行懒创建/更新（SUBMITTED, submit_version+1, version+1, max_dishes 快照, dish_count=refs.size()）
       先把该日所有行 wish_id 清 0，再把选中行 wish_id 置为 menuId
   同事务 recordEvent（§4.5）

5. POST /api/child/wish-menu/withdraw { menuDate, expectedVersion }
   → 同 2 的响应体；SUBMITTED → WITHDRAWN（保留 wish_id 供回显）
```

**家长侧（`@RequireRole PARENT`）**

```
6. GET  /api/parent/wish-menu?childId&menuDate      → 同 2（额外含 childId）
7. GET  /api/parent/wish-menu/list?childId&from&to  → { childId, from, to, today,
       items:[{ menuId, menuDate, status, dishCount, maxDishes, submitTime, expired, items:[...] }] }
       （≤31 天；过期照常返回并标 expired，不静默丢行）
8. GET  /api/parent/wish-setting                    → { maxDishes, enabled, version }
9. PUT  /api/parent/wish-setting { maxDishes, enabled, expectedVersion } → 同上；乐观锁不符 E007
```

**入参安全铁律**：`familyId` / `childId`（儿童侧）/ `ownerKey` / `sourceType`（菜单上下文）**严禁客户端传入**，一律由登录上下文与家长鉴权派生；`type+id` 仅用于定位菜品，归属由服务端校验（FAMILY → `family_id = 派生家庭`）。越权统一 `E009`，不暴露数据存在性。

### 4.4 事务与并发

| 场景 | 路径 | 锁 |
|---|---|---|
| 读（1/2/6/7/8） | `authorization.boundChild(childId)` + `requireConsentReadOnly(member)` + `requireCompleteProfile(member)` | **不加行锁**（R6） |
| 写（3/4/5/9） | `authorization.lockBoundChild(childId)` + `requireConsent(member)` + `completeProfile(member)` | 家庭/儿童/关系/同意 加锁 |
| 头行懒创建 | 先 `selectOne(... FOR UPDATE)`；无则 `INSERT`，捕获 `DuplicateKeyException` 后重查 | 唯一键 `uk_wish_child_date` |
| 乐观锁 | `wish_menu.version` / `family_setting.version`：`UpdateWrapper.eq("version", before).setVersion(before+1)`，0 行 → `E007` | 手写范式 |
| 明细收编 | 单条 `UPDATE ... SET wish_id = ? WHERE child_id = ? AND menu_date = ? AND delete_at = 0`（先清后置两条） | 无循环子事务 |

### 4.5 通知设计（R3）

```java
// 提交成功、同一写事务内：
notices.recordEvent("wish:" + menu.getId() + ":" + menu.getSubmitVersion(),
                    "WISH_SUBMIT", menu.getFamilyId(), childId, family.getOwnerUserId());
```

- 接收人 = 家庭创建家长（`usr_family.owner_user_id`），与 `ConfirmService.recordEvent(confirm,"SUBMIT",ownerUserId)` 同款。
- `eventKey` 含 `submit_version` ⇒ 每次有效提交是一条新事件；重复提交被 `expectedVersion` 拦在 `E007`，不会产生重复通知；`uk_event_receiver_channel` 再兜一层幂等。
- `WISH_SUBMIT` 满足 `[A-Z0-9_]{1,32}`。
- 家长在站内通知中心立即可见；`SUBSCRIBE` 行为 `UNAUTHORIZED`，等 `notice.templates.WISH_SUBMIT` 配置 + 家长授权后才可能投递（**沿用 F-011 现状，本期不开闸**）。
- **`NoticeResp` 契约不变更**：小程序通知页补文案 + 点击跳转 `pages/menu`（家长角色，默认第一个孩子 + 今天 + 自动定位心愿菜单区块）。

### 4.7 安全与合规

- 儿童只能操作**自己**的、落在窗口内的心愿菜单；家长只能读**自己家庭成员**的（`boundChild` + `requireParent`）。
- 心愿菜单属儿童行为数据 ⇒ 读写**必须校验 PROFILE 同意**（`requireConsent` / `requireConsentReadOnly`），撤回后一律 `E010`。
- 上限在服务端强校验（客户端计数仅为体验）。
- 审计：`audit.record("WISH_MARK" | "WISH_SUBMIT" | "WISH_WITHDRAW" | "WISH_SETTING_UPDATE", ...)`。
- 过敏安全：`allergenStatus != 'DECLARED'` 或 `allergyConflict` 的菜**不可加入**；但与 want-eat board 的"不丢行"原则一致，**目录里照常返回并置灰**，不静默隐藏。

## 七、风险与回滚

| 风险 | 说明 | 缓解 |
|---|---|---|
| 上限调小后已有标记超限 | 家长从 5 改 2，孩子已标记 4 道 | **不静默删行**；提交时校验失败 → **E-014**（独立错误码，客户端按码提示「已超出上限，请先调整」） |
| PRESET/FAMILY 撞号 | 两表独立自增 | 全链路 `type+id`；想吃表唯一键含 `dish_type` |
| 通知重复 | 重复提交 / 网络重放 | `expectedVersion` → `submit_version` 入 eventKey → `uk_event_receiver_channel`，三重幂等 |
| 软删后重新标记撞唯一键 | 移除后重新加入同一道菜 | 唯一键含 `delete_at`；移除走软删 |
| 想吃表新增 `meal_type='ALL'` / `source_type='WISH'` 污染既有视图 | 家长「孩子想吃」看板会多出"未指定餐次"分组 | 前端补标签（§4.6）；board 不丢行原则本身要求返回它们；`frequentDishes` 含这些行属合理增益 |
| 放宽菜谱范围后 `markFavorite` 契约被绕 | 新增独立通路 `wish-mark`，**不改** `markFavorite` 的"必须在当日菜单内"校验 | 两条通路并存，语义分离；测试分别覆盖 |
| 迁移漏登记 | Testcontainers 无表 → 整片 500 | §五 第 9 条 |
| 回滚 | 需快速退出 | `DROP TABLE life_wish_menu, usr_family_setting` + `ALTER TABLE usr_child_want_eat DROP COLUMN wish_id, DROP KEY idx_want_eat_wish` + 通知页文案回退；`wish_id` 为默认 0 的增量列，**既有接口零破坏** |
