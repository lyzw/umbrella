一、需求与目标

原始需求：菜品的创建，增加食材、做法等信息维护。

交付范围（V1.1 已确认）：在菜品录入与展示链路上补齐配方信息 —— 食材清单（名称 + 用量）、做法步骤（有序文本）、小贴士、烹饪时长、份量、难度；覆盖预置菜品（运营后台）与家庭菜品（家长端小程序）两侧，并在小程序「孩子想吃」页提供查看入口。

本期必须达成说明
预置菜品配方维护运营后台可录入、修改、清空并完整回显六项配方信息。
家庭菜品配方维护家长在小程序菜品管理页同样可维护配方。
C 端可查看家长在「孩子想吃」清单中可展开查看该菜的食材与做法。
契约向后兼容不传新字段的既有调用方一行都不用改。

目标之外：不做食材用量单位字典与营养换算、不做成本核算、不做配方版本历史、不做「配方完整度」强校验闸门（不使用配方缺失阻断上下架）。

二、现状调研（已核实事实）

以下结论均来自代码与脚本实读。

调研项核实结果
是否已有配方能力 完全没有。ingredient / 食材 / 做法 / cookStep 在后端 Java、SQL、后台前端代码中零命中；仅小程序两处说明文案出现过「烹饪」「不含食材用量」。
life_dish 列 id, category_id, name, image_url, virtual_price, calories, tags, allergens(JSON), allergen_status, spice_level, status, create_time, update_time, delete_at。无配方字段。
life_family_dish 列 与上表同构，另有 family_id / visibility / review_status / reject_reason / version。同样无配方字段。
两表自增序列 相互独立，故裸 dish_id 在跨表场景会撞号 —— 这是既有 DishRef = {type:"PRESET"|"FAMILY", id} 存在的原因。任何跨两表引用的新表都必须携带类型判别列。
JSON 字段既有先例 Dish.allergens 用 @TableField(typeHandler = JacksonTypeHandler.class) + 实体 @TableName(autoResultMap = true)，运行正常；DDL 侧有 CHECK (JSON_TYPE(allergens) = 'ARRAY') 先例可复制。
清空字段的落库前提 imageUrl / calories / tags 均标注 updateStrategy = FieldStrategy.ALWAYS。不标注时 MyBatis-Plus 默认策略会跳过 null/空值，「清空配方」写不进库。必须复制该写法
请求体严格模式 DishReq 与 FamilyDishReq 都用 @JsonAnySetter 拒绝未知字段 → 反序列化抛错被包成 HttpMessageNotReadableException，统一返回 E-400「参数不合法」。推论：后端必须先于前端上线。
软删与唯一键的既有约定 软删用 delete_at BIGINT DEFAULT 0，且唯一键必须包含 delete_at（先例：usr_child_want_eat 的唯一键含该列），否则软删后重插会撞唯一键。
权限模型 预置菜品走 菜品库 的 view / create / edit / delete；家庭菜品走 C 端家长鉴权。均无需新增 AdminResource，也不需要动播种逻辑。
迁移脚本约定 生产迁移写 sk-growthplanet-start/sql/vNNN_xxx.sql（含回滚注释），同内容追加进 sql/growth_planet.sql（测试汇总，application-test.yml 只登记它 + v008_admin.sql）。最新编号为 v010。
产品侧现成缺口 小程序「孩子想吃」页原文写着「采购汇总仅按菜品去重，不含食材用量」。本期的食材结构化正是补齐该缺口的前置条件。

三、已确认选型（V1.1 变更）

决策项你的选择影响
存储形态 混合式：食材走子表 + 做法走 JSON 新增 life_dish_ingredient 结构化子表（可聚合、可索引，为「按食材采购清单」铺路）；做法、小贴士等展示型文本保留在主表 JSON / 标量列。
字段范围 食材 + 做法 + 小贴士 + 烹饪时长 + 份量 + 难度 预置与家庭两张菜品表各新增 5 列（做法/小贴士/时长/份量/难度），食材落到子表。
作用范围 预置菜品 + 家庭菜品 需同步改 FamilyDish 实体、FamilyDishReq、家庭菜品写路径，以及小程序 dish-manage 表单。
C 端展示 小程序「孩子想吃」页加查看入口 新增 C 端只读配方端点（懒加载），并在想吃清单中提供展开面板。
工作量提示（如实告知）：这四项组合后，范围约为「仅预置菜品 + 全 JSON 存储 + 不做 C 端」最小方案的 3 至 4 倍，其中新增风险集中在三处 —— 跨两表的食材子表归属完整性、家庭菜品写路径的回归面、小程序 WXML 渲染无法被 Node 测试覆盖。因此本文档把实施切成 A（后端）→ B（运营后台前端）→ C（小程序） 三批，每批独立验证、独立提交，避免一次改动过大难以定位问题。
补一个我替你定了的子选择：食材子表采用单表 + owner_type 判别列（PRESET / FAMILY），而不是预置、家庭各建一张表。理由：两表结构完全相同、字段永不对称演化；单表让「批量装配食材」「按食材聚合」只需一条 SQL，而拆两表会让每个查询、每个测试都分叉。这与既有 DishRef 用类型判别列表达「两套独立序列」的思路一致。若你更希望物理隔离成两张表，请在确认时说明，我会改第四、六章。

四、数据模型设计

4.1 迁移脚本 sql/v011_dish_recipe.sql

新增该文件（含回滚注释），并把同内容追加到 sql/growth_planet.sql 末尾。

-- =====================================================================
-- v011_dish_recipe：菜品配方信息（食材子表 + 做法 / 小贴士 / 时长 / 份量 / 难度）
-- 目标：预置菜品与家庭菜品同时支持配方维护，为「按食材聚合采购清单」预留基础。
-- 回滚：
--   ALTER TABLE life_dish DROP CHECK chk_dish_cook_steps, DROP CHECK chk_dish_cook_minutes,
--         DROP CHECK chk_dish_servings, DROP CHECK chk_dish_difficulty;
--   ALTER TABLE life_dish DROP COLUMN cook_steps, DROP COLUMN cook_tips,
--         DROP COLUMN cook_minutes, DROP COLUMN servings, DROP COLUMN difficulty;
--   ALTER TABLE life_family_dish DROP CHECK chk_fdish_cook_steps, DROP CHECK chk_fdish_cook_minutes,
--         DROP CHECK chk_fdish_servings, DROP CHECK chk_fdish_difficulty;
--   ALTER TABLE life_family_dish DROP COLUMN cook_steps, DROP COLUMN cook_tips,
--         DROP COLUMN cook_minutes, DROP COLUMN servings, DROP COLUMN difficulty;
--   DROP TABLE IF EXISTS life_dish_ingredient;
-- =====================================================================

-- ① 食材清单：预置 / 家庭共用一张表，owner_type 判别
--    注意：life_dish 与 life_family_dish 自增序列独立，故 (dish_id) 单独无法定位；
--    跨表无法建外键，归属完整性由服务层保证（见六章）。
CREATE TABLE life_dish_ingredient (
  id          BIGINT      NOT NULL AUTO_INCREMENT,
  owner_type  VARCHAR(16) NOT NULL               COMMENT 'PRESET=预置菜品 FAMILY=家庭菜品',
  dish_id     BIGINT      NOT NULL               COMMENT 'owner_type 对应菜品表的主键',
  name        VARCHAR(32) NOT NULL               COMMENT '食材名称',
  amount      VARCHAR(32) DEFAULT NULL           COMMENT '用量（自由文本：200g / 适量）',
  sort        INT         NOT NULL DEFAULT 0     COMMENT '展示顺序，0 起',
  create_time DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  delete_at   BIGINT      NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  UNIQUE KEY uk_dish_ingredient_order (owner_type, dish_id, delete_at, sort),
  KEY idx_dish_ingredient (owner_type, dish_id, delete_at),
  CONSTRAINT chk_ingredient_owner CHECK (owner_type IN ('PRESET', 'FAMILY')),
  CONSTRAINT chk_ingredient_sort  CHECK (sort >= 0 AND sort < 30)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='菜品食材清单（预置/家庭共用）';

-- ② 做法与轻量配方属性：预置菜品
ALTER TABLE life_dish
  ADD COLUMN cook_steps   JSON         NOT NULL DEFAULT (JSON_ARRAY()) COMMENT '做法步骤（有序文本数组）',
  ADD COLUMN cook_tips    VARCHAR(500) DEFAULT NULL                    COMMENT '烹饪小贴士',
  ADD COLUMN cook_minutes INT          DEFAULT NULL                    COMMENT '预计烹饪时长（分钟）',
  ADD COLUMN servings     TINYINT      DEFAULT NULL                    COMMENT '份量（人份）',
  ADD COLUMN difficulty   VARCHAR(16)  DEFAULT NULL                    COMMENT '难度：EASY/MEDIUM/HARD',
  ADD CONSTRAINT chk_dish_cook_steps   CHECK (JSON_TYPE(cook_steps) = 'ARRAY'),
  ADD CONSTRAINT chk_dish_cook_minutes CHECK (cook_minutes IS NULL OR cook_minutes BETWEEN 1 AND 1440),
  ADD CONSTRAINT chk_dish_servings     CHECK (servings IS NULL OR servings BETWEEN 1 AND 20),
  ADD CONSTRAINT chk_dish_difficulty   CHECK (difficulty IS NULL OR difficulty IN ('EASY','MEDIUM','HARD'));

-- ③ 做法与轻量配方属性：家庭菜品（列定义与约束同上，仅表名/约束名副缀不同）
ALTER TABLE life_family_dish
  ADD COLUMN cook_steps   JSON         NOT NULL DEFAULT (JSON_ARRAY()) COMMENT '做法步骤（有序文本数组）',
  ADD COLUMN cook_tips    VARCHAR(500) DEFAULT NULL                    COMMENT '烹饪小贴士',
  ADD COLUMN cook_minutes INT          DEFAULT NULL                    COMMENT '预计烹饪时长（分钟）',
  ADD COLUMN servings     TINYINT      DEFAULT NULL                    COMMENT '份量（人份）',
  ADD COLUMN difficulty   VARCHAR(16)  DEFAULT NULL                    COMMENT '难度：EASY/MEDIUM/HARD',
  ADD CONSTRAINT chk_fdish_cook_steps   CHECK (JSON_TYPE(cook_steps) = 'ARRAY'),
  ADD CONSTRAINT chk_fdish_cook_minutes CHECK (cook_minutes IS NULL OR cook_minutes BETWEEN 1 AND 1440),
  ADD CONSTRAINT chk_fdish_servings     CHECK (servings IS NULL OR servings BETWEEN 1 AND 20),
  ADD CONSTRAINT chk_fdish_difficulty   CHECK (difficulty IS NULL OR difficulty IN ('EASY','MEDIUM','HARD'));
唯一键为什么是 (owner_type, dish_id, delete_at, sort)：sort 入键保证同一菜品的展示顺序不重复（并发写入不会产生两个 sort=0）；delete_at 入键遵循既有软删约定，使「软删旧行 → 插入新行」不会相撞。漏掉 delete_at 会让每次编辑菜品直接报唯一键冲突。
为什么 cook_steps 用 JSON 而不进子表：做法是有序纯文本，没有「按步骤内容聚合」的场景，进子表只增加装配成本而无查询收益；食材则明确有「按名称聚合采购」的二期待验证需求，所以两者分治 —— 这正是混合式选型的用意。

4.2 食材子表写入策略

每次保存菜品时整体替换该菜品的食材集合，与菜品主表写入同一事务：

软删旧行UPDATE life_dish_ingredient SET delete_at = UNIX_TIMESTAMP()*1000 WHERE owner_type=? AND dish_id=? AND delete_at=0
批量插入新行按请求数组下标写入 sort=0,1,2…；一次批量 insert，不做逐条循环
菜品软删时级联删除菜品的同时把其食材行一并软删，避免"菜没了食材还在"的悬挂数据

不做「差量比对」更新：配方条目量级为个位数，整体替换的代码与心智成本都远低于差量算法，收益为零。

4.4 响应为什么这样切分

数据放在哪理由
时长 / 份量 / 难度DishResp 平铺各只有几字节，列表页可以直接显示「30 分钟 · 2 人份 · 简单」。
食材条数 / 步骤数DishResp 平铺让列表用极小代价显示摘要，无需为列表额外查询子表。
食材明细 / 做法步骤 / 小贴士DishResp.recipe（可空）做法与小贴士是长文本。若平铺，GET /api/admin/dishes（20 条）与菜单类响应会被显著撑大，且前端无法区分「本响应没带」与「这道菜确实没配方」——recipe=null 与 recipe.ingredients=[] 语义精确分开。

5.2 小程序 C 端（新增 1 个只读端点）

GET /api/mini/dishes/{type}/{dishId}/recipe
  type   : PRESET | FAMILY
  dishId : 对应菜品 id

200 -> Result<DishRecipeResp>
  { "code": "0", "data": {
      "ingredients": [ { "name": "猪肉", "amount": "200g" } ],
      "cookSteps":   [ "猪肉切薄片…", "热锅冷油…" ],
      "cookTips":    "给孩子吃可以少放辣椒。",
      "cookMinutes": 20, "servings": 2, "difficulty": "EASY" } }
要点设计
为什么单独一个端点 想吃清单页一次可能列出十余道菜，把做法长文本塞进清单响应是纯浪费。做成按需懒加载：用户点开某道菜才请求，清单保持轻量。
鉴权与隔离 安全红线 需 C 端 token，登录角色为家长或孩子均可（只读、非敏感）。type=FAMILY 时必须校验该菜品的 family_id 等于当前登录用户所属家庭，不等则按「不存在」处理 —— 归属字段一律从鉴权派生，绝不接受客户端传入的 familyId。
下架菜品能否看 沿用既有可见性规则：家庭菜品按现有 visibility / review_status 判定；预置菜品下架则返回 E-404。与「想吃清单里本来能看到什么」保持一致，不额外放宽。
错误码 不新增，复用 E-400 / E-404。

六、服务层设计

6.1 写入（预置与家庭共用一套逻辑）

步骤说明
① 校验validateRecipe 统一校验六个字段（规则见 6.3），预置与家庭菜品共用，避免两套规则漂移。
② 主表写入applyRecipe(dish, req) 填充做法/小贴士/时长/份量/难度（归一化：空串→null，null→空数组）。
③ 食材替换replaceIngredients(ownerType, dishId, items)：软删旧行 + 批量插入新行，同一事务。
④ 审计沿用现有 DISH_CREATE / DISH_UPDATE 审计记录，不新增审计类型。

owner_type 的传递是这部分最容易出错的地方：预置路径固定传 PRESET，家庭路径固定传 FAMILY，不允许由请求参数决定 —— 否则客户端可通过构造参数把食材写进别人的菜。

ingredients[].name去空白后非空，≤ 32 字，忽略大小写与首尾空白后不得重复E-400「食材名称不能为空」/「食材名称重复：猪肉」
ingredients[].amount可空，≤ 32 字E-400「食材用量最长 32 字」
cookSteps可选，≤ 20 步；每步去空白后非空、≤ 300 字E-400「第 3 步做法不能为空」
cookTips可空，≤ 500 字E-400「小贴士最长 500 字」
cookMinutes可空；填写时 ∈ [1, 1440]E-400「烹饪时长需在 1 至 1440 分钟之间」
servings可空；填写时 ∈ [1, 20]E-400「份量需在 1 至 20 人份之间」
difficulty可空；∈ {EASY, MEDIUM, HARD}E-400「难度取值不合法」
与在售的关系不设闸门配方缺失不阻断上下架
关键取舍：六个字段全部可选、且不参与「在售」闸门。既有的 R5-c 红线（在售必须先声明过敏原）是为了儿童安全；配方缺失不构成安全风险。若把配方也设为在售必填，存量菜品将无法上下架，属于自伤型约束。配方完整度只在前端做提示（见 7.4）。

七、运营后台前端（批次 B）

7.1 表单结构

  • 编辑抽屉宽度由 420px 提升到 760px —— 食材行内编辑与步骤卡片需要横向空间。
  • 表单分为三组，用 el-divider 分隔：基础信息（现有字段，位置顺序不动）、配方信息（食材 / 做法 / 小贴士）、烹饪属性（时长 / 份量 / 难度）。

7.2 食材编辑（结构化行列表）

  • 每行：序号（只读）+ 名称输入（32）+ 用量输入（32）+ 上移 / 下移 / 删除。
  • 底部「添加食材」按钮；达 30 条时 disabled 并提示上限。
  • 不使用 allow-create 的 tag 输入 —— 历史教训：过敏原下拉曾因「无候选项 + 允许盲输」让用户反复踩校验失败（上一批已移除 allow-create）。行列表把名称与用量显式分开，没有格式歧义。

7.3 做法编辑（有序步骤卡片）

  • 每步一张卡片：序号 + 多行文本框（300 字，带字数统计）+ 上移 / 下移 / 删除；底部「添加步骤」，上限 20。
  • 提交前若存在空白步骤，提示先删除该步 —— 与后端「不接受空步」对齐。

7.4 其它

  • 列表新增「配方」列：显示「食材 5 · 步骤 4」；无配方显示 —；数据来自 ingredientCount / stepCount，不需额外请求。时长/份量/难度可合并进同一列显示。
  • validateForm() 追加前置校验：食材名称必填/不重复、步骤非空、各长度与范围上限与后端一致。目标仍是把报错提前到本地。
  • openEdit 走 GET /dishes/{id}（含 recipe）。回填必须归一化：data.recipe || { ingredients: [], cookSteps: [], cookTips: null } —— 上一批刚因「多解一层 data」导致页面整片 TypeError，新增字段取值一律先兜底再绑定。
  • 可选（不阻塞交付）：配方为空时在表单顶部给一条浅色提示「建议补齐食材与做法，便于家长照做」。

提交collectRecipe() 做本地校验 + 归一化：空行（食材无名称 / 步骤空白）直接丢弃，用户不必把空行删干净；名称忽略大小写去重、长度与容量上限、时长 1–1440、份量 1–20，文案与后端一致。
编辑回填edit() 改为：先同步填基础信息与列表摘要，再懒加载 GET /api/mini/dishes/FAMILY/{id}/recipe 回填完整配方（含时长 / 份量 / 难度）。回填前校验 formDishId 未变，避免用户已关表单或改编辑别的菜时错填。
列表摘要卡片新增「配方：食材 N · 步骤 M · 30 分钟 · 中等」，全部取自列表响应已有字段，不为每行发配方请求。
want-eat 看做法每条想吃记录加「看做法」按钮，点击懒加载 GET /api/mini/dishes/{type}/{dishId}/recipe，页内展开面板显示时长/份量/难度、食材表、有序步骤、小贴士；加载中占位、失败给重试入口。已加载结果按 type:dishId 缓存，折叠再展开不发第二次请求。
缓存失效换孩子、换周区间、页面隐藏三种场景显式清空 recipeStates —— 否则会串显示上一个孩子 / 上一周的菜。
缺失菜品missing=true（菜品已下架 / 删除）的条目不提供「看做法」入口，省一次必然 404 的请求。
与本文档 8.x 的三处偏差
  1. 配方明细的错误处理不走页面级错误条：加载失败只写本条目的 recipeStates[key] = { status: 'error', message }，在面板内展示并可重试；仅 401 / E-010 仍交给 ui.run 统一跳登录 / 家庭页。理由是页面级 error 条会让「一道菜的配方没加载出来」看起来像整页故障。
  2. 家庭菜品表单的新增分组顺序（8.1 只说「表单新增」）：配方组放在「营养与口味」之后、「安全信息」之前，过敏原仍是最后一组。
  3. 保存时的空行丢弃（8.1 未涉及）：后端不接受空名称 / 空步骤，前端在提交时静默丢弃整行空白，而不是让用户为「填了一半」吃 E-400。
一个必须知道的数据语义：配方是整体替换语义 —— 后端把「不带 ingredients」与「ingredients: []」都归一化为空，因此任何一次不携带完整配方的保存都会清空原有食材与做法。这正是 edit() 在配方明细加载失败时必须明确警示「保存会覆盖原有配方」的原因；小程序端不存在「只改某一条食材」的局部提交。
验证边界（不夸大）：本机未安装微信开发者工具（wcc / wcsc 二进制不存在），因此 check.mjs --native 无法运行，WXML / WXSS 的原生编译未验证。作为替代，本次额外做了两项定向核对：① 两个页面模板中 {{ }} 引用的标识符全部在 script 中存在（剔除字符串字面量后零缺失）；② <view> / <block> 标签闭合平衡。但 WXML 实际渲染、滚动、textarea 与底部固定操作条的遮挡关系、以及真机下的输入体验必须由你在开发者工具 / 真机确认，不计入「已自动化验证」。
