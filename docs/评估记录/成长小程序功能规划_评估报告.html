一、现有功能概要

1. 产品定位

面向 11 岁六年级儿童 的生活与学习小程序，从"孩子自主点餐"起步，逐步扩展到生活自主与学习成长两大版图；明确不做真实支付，消费走"虚拟零花钱"记账 + 家长额度护栏。

2. 角色模型

三角色：儿童端（主角）、家长端（监护人）、后台（运营）；另设"能力中台"（账号/支付网关/通知/AI/数据看板）。

3. 架构与模块（三层）

  • 儿童端 8 模块：点餐、零花钱、家务、健康打卡、课表/作业、错题本/阅读、成长树/勋章、AI 小问号
  • 家长端 6 模块：家庭绑定、支付与额度、审批流、看板、内容白名单、安全权限
  • 后台 5 模块：餐厅菜品、任务/书单库、勋章/活动、内容审核、数据风控

4. 演进路线（Roadmap）

P0 地基（1–2 月）→ P1 点餐 MVP（2–4 月）→ P2 生活自主（5–8 月）→ P3 学习成长（9–12 月）→ P4 智能激励（13–18 月）。含优先级矩阵（儿童价值×家长意愿/依赖）。

5. 技术与合规

Java 21 + Spring Boot 4.1.1 + MyBatis-Plus + MySQL 8.0 + Redis；虚拟零花钱记账；隐私最小化采集、家长明示同意、内容审核、沉迷提醒等合规要点已原则性列出。

二、问题诊断（四维度）

严重度标识：高 影响功能能否成立 / 上线 / 合规；中 影响体验、动机或可行性；低 体验细节或长期可扩展性。

维度一 · 功能完整性与覆盖度

严重度问题诊断说明
已澄清履约 / 接单方（非问题）用户澄清：食堂非真实营运——学校端仅展示当日菜单，家庭端由孩子向父母确认当日菜单，无需商户接单履约。原"缺履约侧"高优先级问题不成立，已关闭。
高缺监护人"二级角色"仅"家长"单一监护人，未覆盖隔代教养（祖辈代确认）、双亲分工等常见家庭结构；审批委托/代确认机制缺失。
已澄清即时联系 / SOS / 异常告警（非问题）用户澄清：本产品为微信小程序、非原生 App，设备级安全求助能力（一键联系、SOS、异常告警）不在小程序范畴，无需。原"缺即时联系/安全能力"中优先级问题不成立，已关闭。
中虚拟零花钱"出口"缺失钱只能被扣（点餐），缺乏有意义的兑换/使用出口（如兑换屏幕时间、家长确认的真实小奖励）。仅有"扣减"无"消费意义"，长期激励存疑。
中儿童 UGC 缺落点阅读"读后感语音/文字"、AI 对话等属用户内容，但其存储位置、可见范围、审核流转未定义；与"儿童端不做裸露社交"的边界模糊。
低新手引导 / 空状态 / 无障碍缺失11 岁儿童首次使用缺引导、空状态、错误态设计；无障碍（色弱、阅读障碍友好）未提及；缺反馈与帮助入口、数据导出/账号注销。

维度二 · 用户流程与交互逻辑合理性

严重度问题诊断说明
高P1 点餐依赖 P2 钱包P1 明确"从虚拟零花钱余额扣减"，但钱包/额度被划在 P2。P1 上线时钱包不存在，自相矛盾，点餐无法独立闭环。
中家长审批可用性（已缓解）设计澄清后，学校菜单仅为展示、无需审批，家庭菜单确认是预期的亲子互动，原"点餐实时确认瓶颈"已大幅缓解。但家务奖励、购物审批、内容白名单仍依赖家长实时确认，且微信订阅消息有触发/额度限制，建议对这类非紧急审批采用"额度内自动 + 异步复核"机制。
中通知过度依赖订阅消息订单/课表/作业/健康多场景提醒全压在"微信订阅消息"，但订阅消息有触发前提与额度上限；缺站内通知中心与（面向家长的）短信兜底。
中跨端绑定流程含糊P0 儿童做"微信登录+儿童档案"、家长做"家庭创建与绑定"，但两设备如何关联（邀请码/扫码/验证码）未定义，P0 跨端协作不清。
中跨模块联动仅描述无机制"健康打卡连点餐做营养均衡提示""零花钱来自任务"等联动只写目标未写数据流与触发逻辑，落地时易变成摆设。
低异常态/弱网态缺设计订单超时、网络中断、多孩并发下单与额度隔离等边界场景未覆盖；错误恢复路径缺失。

维度三 · 功能优先级划分

严重度问题诊断说明
高钱包能力应前移虚拟余额与额度护栏是 P1 点餐的地基，应归入 P0/P1 横向基础而非 P2，否则首期无法交付（同维度二 F1）。
中横向能力未单列优先级"通知中台""安全/审批基础设施""内容审核"是跨阶段使能项，应作为 P0 横向能力 明确定义，而非埋在各阶段表格里。
中优先级矩阵未量化公式"价值×意愿/依赖"未给出实际数值打分，结论靠主观描述；建议补齐评分与排序，便于评审与说服 stakeholders。
中MVP 未切分P1 列出 7 项功能但未标注 Must/Should/Could，首期范围模糊，不利于控制工期与验收。
低工期与技术风险P0（1–2 月）含登录/家庭/画像/框架/导航/安全偏乐观；OCR、AI 等高风险能力应早期做技术 spike，即便交付放到 P3/P4。

维度四 · 潜在业务场景遗漏

严重度问题诊断说明
已澄清履约侧 / 商户端（非问题）用户澄清：食堂非真实营运，学校端展示当日菜单、家庭端由孩子向父母确认菜单，无需商户运营后台。原"商户端完全缺失"高优先级问题不成立，已关闭。
高真实激励兑换机制缺失虚拟零花钱需兑换成孩子真正在意的东西（屏幕时间、兴趣班课时、家长确认的真实小礼物），否则"赚钱→花钱"动机闭环断裂。
已澄清家长↔儿童安全沟通通道（非问题）用户澄清：小程序非 App，无需安全求助/联系通道；亲子沟通可由现有审批流与家长端看板承载，非必需独立功能。原"亲子安全消息"建议已移除。
中教师 / 学校角色脱节课表、作业"来自学校"，但教师角色与家校互通仅列为 P4 可选，与业务事实脱节；建议提升为学校对接模块。
中合规未落地《儿童个人信息网络保护规定》要求可验证的监护人同意、年龄识别、数据留存期限与删除，文档仅原则性声明，无落地机制（年龄认证方式、同意留痕、删除流程）。
中商业模式 / 可持续性未定义无真实支付前提下，谁付费、如何可持续（家长订阅？学校 B2B？广告？）完全空白，影响长期投入决策。
低内容来源 / 季节场景 / 退出过渡书单/任务库/知识百科的内容生产与版权来源未说明；校历/假期场景、消费/学习趋势告警、12→13 岁年龄过渡与数据迁移未考虑。

3.2 优化方向（流程与机制）

  • 审批从"实时确认"转"额度内自动 + 超额异步复核"：在校午餐等场景，额度内的点餐/任务由系统自动放行并留痕，家长事后在"待复核"列表批量确认；仅超额/敏感动作才实时介入。降低家长负担、保住护栏。
  • 钱包能力前移：将"虚拟余额 + 额度规则 + 扣减流水"下沉为 P0/P1 地基，点餐直接复用，避免跨阶段依赖债务。
  • 横向能力单列：通知中台、安全/审批引擎、内容审核作为 P0 使能项，先建能力后接入各模块。
  • 量化优先级矩阵：给"儿童价值/家长意愿/技术可行/依赖"打 1–5 分，按公式算数值并排序，输出可评审的优先级清单。
  • MVP 切分：P1 标注 Must（点餐浏览/下单/额度扣减/状态追踪）与 Should/Could，控制首期范围。
  • 合规落地化：明确年龄识别方式（家长身份证+人脸或运营商三要素）、同意留痕表、数据留存与删除 API、儿童数据单独存储。
  • 商业模式画布：尽早明确付费方（家长订阅 / 学校 SaaS / 增值内容），指导功能取舍。

3.4 上线前"必须修复"清单（Must-Fix）

① 履约侧（已澄清关闭）：用户确认食堂非真实营运——学校端仅展示当日菜单，家庭端由孩子向父母确认当日菜单，无需运营端/接单方，原"假闭环"问题不成立。
② 钱包前移（仍必改）：虚拟余额与额度必须随 P1 一同上线，消除 P1 依赖 P2 的矛盾（P1 菜单确认仍关联虚拟零花钱护栏）。
③ 审批可用性（仍必改）：将"全量实时确认"改为"额度内自动 + 异步复核"；学校菜单展示本就无需审批，家庭菜单确认是预期的亲子互动，重点优化家务/购物等其余审批面的体验。
结论：这是一份高完成度的规划草稿，方向正确、结构专业。经设计澄清，"履约侧缺失"已不成立（食堂非营运，学校展示菜单、家庭确认菜单）。剩余核心风险为 钱包时序矛盾 与 审批可用性 两项，以及 合规/商业模式的落地空白、激励出口与二级监护人等覆盖度缺口。修正优先级（钱包前移、审批降频）并补入激励兑换、二级监护人、合规落地等能力后，即可进入 P0/P1 的 DDL 与工程骨架设计。
