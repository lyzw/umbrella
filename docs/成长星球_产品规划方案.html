三、产品定位

3.1 一句话定位

「成长星球」是陪伴 6–12 岁儿童的生活与学习自主力养成平台：以「孩子自主决策 + 家长虚拟额度护栏」的模拟记账模式，在零真实支付风险的前提下，培养孩子自我管理、理财意识与学习习惯。

3.2 产品愿景与使命

维度内容
愿景让每个孩子在"安全的试错空间"里，长出自驱力与责任感。
使命用游戏化激励 + 家长护栏，把"吃饭/家务/作业"等日常小事，变成孩子可感知的成长里程碑。
首期 Mission（V0.0.1）跑通"孩子确认今日菜单 → 家长额度护栏 → 虚拟记账 → 正向反馈"的最小闭环，验证三角色模型。

3.3 价值主张（三方）

角色核心价值
儿童（主角）能自己做主（选菜/任务），每完成一件事获得勋章与动画正反馈，成就感强、操作门槛低（大字号+强图标+语音）。
家长（监护人）零真实资金风险地了解孩子偏好与消费；额度护栏 + 异步复核掌握全局；成长看板一目了然。
后台运营配置菜单/任务/勋章、内容审核与风控，支撑多家庭规模化运营。

3.4 命名与品牌策略

  • 产品品牌：成长星球（Umbrella，可后续品牌化）。
  • 首期模块昵称：小当家·点餐（降低儿童认知门槛，具象化"我是小当家"）。
  • 术语统一：规划/交互文档中存在"点餐/下单/确认菜单"混用，本方案起统一为"今日菜单确认"（动作）、"确认单"（数据对象），避免儿童误认为真实交易。

4.1 用户角色总览

角色典型用户核心诉求使用终端

家长（监护人）父母 / 祖辈（二级监护人）护栏、知情、激励孩子微信小程序（家长端，同程序按角色路由）

4.2 核心用户画像

👦 小宇（主角·11 岁）

  • 能力：能独立阅读图文、点按操作；不擅长长表单与复杂设置。
  • 敏感点：对游戏化、勋章、动画敏感；自我保护意识弱，需家长护栏。
  • 痛点：想自己决定吃什么，但平时都是家长安排；渴望"被信任"。
  • 场景：午饭前用手机浏览今日菜单 → 选几样 → 告诉爸妈 → 等确认 → 看到"已完成"很开心。

👩 小宇妈妈（监护人）

  • 能力：熟悉微信，关注孩子安全与习惯养成。
  • 敏感点：担心真实支付风险、不良内容、孩子沉迷。
  • 痛点：想培养孩子自主但怕"乱花"；没时间盯每顿饭。
  • 场景：收到"孩子想确认今日菜单"提醒 → 一眼看金额与备注 → 一键同意 → 偶尔超额时再斟酌放行。

4.3 核心使用场景（概览）

场景角色简述对应阶段
首次登录到家庭绑定儿童+家长微信登录→建档→邀请码绑定→监护人同意P0
首餐菜单确认儿童+家长浏览菜单→确认→家长同意→虚拟记账→正反馈P1

五、核心设计原则

  1. 家长护栏优先：不做真实支付，消费走"虚拟零花钱"记账；对外联系/位置/内容发布经家长授权或审批流；儿童端不做裸露的聊天/社交/定位。
  2. 大字号 + 强图标 + 语音辅助：正文基准 16px（大于常规 14px），关键操作支持语音与图片，降低识字与输入门槛。
  3. 即时正反馈：每完成一件事给予勋章/动画/进度，强化自主感与成就感。
  4. 本地化与个性化：学校/家庭场景、口味忌口偏好、适龄理财引导、多语言可选。
  5. 隐私合规：遵循儿童个人信息保护法规，最小化采集、家长明示同意、可撤回、可导出/可删除。
  6. 儿童情绪保护：儿童端仅见状态（"已告诉爸妈，等确认"），不显示"被拦截/拒绝"等负面词；驳回原因由家长以温和语言说明。

十、技术架构概览

后端：Java + Spring Boot + MySQL（具体版本见审查文档 R-10，需确认 GA 与依赖兼容）。ORM 用 MyBatis-Plus；API 风格 RESTful + JWT（child/parent 分权）。

数据库：MySQL 8.0；通用字段 create_time / update_time / delete_at（delete_at 为 BIGINT 删除时间戳，默认 0，替代布尔 deleted，支撑"删了还能重建"）；枚举用 VARCHAR 在 Java 控制。缓存/会话用 Redis；通知用微信订阅消息 + 可选 MQ 解耦。

小程序端：微信小程序原生 或 Taro/uni-app（Vue/React 跨端）。前端非 Java，属独立工程。

支付与安全：不做真实支付，结算走虚拟零花钱记账 + 额度护栏；儿童对外动作走审批流；内容经后台审核；隐私最小化采集 + 家长明示同意。

十一、风险与合规

风险

  • 虚拟消费合规：仅虚拟记账 + 额度护栏，儿童端无真实支付能力；超额异步复核（非实时拦截）。
  • 隐私采集红线：位置/人脸/OCR 需家长同意，可撤回。
  • 内容安全：AI 与 UGC 需审核。
  • 沉迷：游戏化适度，设使用时长提醒。
  • 儿童微信账号与未成年保护合规（见审查 R-09）。

应对

  • 审批流 + 额度双控，家长全可见。
  • 可验证监护人同意 + 年龄识别；儿童数据单独存储。
  • 最小化采集 + 明示同意留痕 + 可导出/可删除。
  • 后台内容审核 + 敏感词/图像风控。
  • 成长类激励替代纯消耗型玩法；兑换中心补动机闭环。

十二、关键假设与待确认项

已做假设：微信小程序（非原生 App）；三角色；通用场景（不限定城市）；不做真实支付、食堂非真实营运——学校端仅展示当日菜单、家庭端由孩子向父母确认/提报，点餐与任务均为虚拟零花钱记账。

待确认项（详见《审查与修改建议》及 PRD 第十五章）：

  • A1：家长"可验证监护人核验"（实名/运营商三要素）是否纳入 V0.0.1，或后置为增强项？
  • A2：家长短信兜底通道在 V0.0.1 是否实现（涉及短信服务商与手机号采集）？
  • A3：儿童端底部 5 Tab 在 P0 的渐进显隐规则？
  • A4：菜单"价格"统一约定为"虚拟消耗额"，是否需独立于未来真实货币体系？
  • A5：技术栈具体版本（Spring Boot 4.1.1 是否 GA）待确认。
