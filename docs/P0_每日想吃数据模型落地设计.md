# P0 落地设计：每日想吃（按天按餐的想吃标记）

> 配套文档：`docs/亲子餐食想吃标记逻辑梳理与优化分析.md`（本设计取代其中 P0-2「想吃带时间维度」的方案 B 草稿，给出可编码的精确方案）。
> 状态：**设计稿，待确认**。确认后按本稿编码，不猜测式实现。

---

## 0. 一句话目标

把「想吃」从 `ChildProfile.favoriteDishIds` 的**扁平终身收藏**，改造为**按 `(childId, menuDate, mealType)` 结构化存储**的每日想吃记录。与已保留的「确认单」（`life_menu_confirm`，FAMILY+当天的数量提交）**并存、互不影响**。

---

## 1. 需求边界（做 / 不做）

### 1.1 做（本 P0）
- 新增 `usr_child_want_eat` 表，想吃记录带 `menu_date` + `meal_type` 维度。
- 孩子标记/取消「想吃」落新表，且**必须绑定当前正在浏览的 (menuDate, mealType)**。
- `daily()` 的 `favorite` 高亮改为查新表（按 child+date+meal），证明"每日"语义。
- 家长新增只读接口，可按「某天 / 某天某餐」查询孩子的想吃清单。
- 提供数据迁移（仅建表，**不**把旧收藏灌入每日行，避免污染每日想吃）。
- 配套集成测试：证明想吃按天按餐隔离。

### 1.2 不做（留给 P1 / P2，本稿只占位）
- P1：家长「按周聚合 + 已采纳/已烹饪状态 + 一键采购单」视图（R3）、「常吃/常点」派生视图（替代旧 `favoriteDishIds` 列）。
- P2：想吃 → 采纳(ADOPTED) → 已烹饪(COOKED) 状态流转（接勋章）、「今日吃什么」推荐、学校供餐预测。
- 本稿在表中**预置** `status` 列（MARKED/ADOPTED/COOKED）与 `source_type` 列，避免后续再迁移。

### 1.3 明确保留（不动）
- **确认单**（`life_menu_confirm`/`life_menu_item` + `canSubmit` + `quantity`/`checkout`）：FAMILY+当天的"数量提交"。
- `ChildProfile.dislikes` / `tastes`：真正的长期偏好，留在 profile。
- `MarkFavoriteReq.dishType` 推导逻辑、`resolveDishType`/`lockDishByType`：继续复用（想吃落库前仍需按菜品存在性推导类型并加锁）。

## 2. 概念澄清（避免再次混淆）

| 概念 | 本质 | 维度 | 当前实现 | 改造后 |
|---|---|---|---|---|
| **每日想吃**（♥） | 孩子"今天这顿想吃这个"的**意向/提前挑选** | 按天按餐 | `favoriteDishIds` 扁平终身 ❌ | `usr_child_want_eat` ✅ |
| **确认单**（数量+提交） | 孩子"今日家庭餐实际要吃这些"的**提交** | FAMILY+当天 | `life_menu_confirm` | 不动 |
| **长期偏好**（忌口/口味） | "永远不爱吃/爱吃的口味" | 终身 | `dislikes`/`tastes` | 不动 |
| **常吃/常点**（派生） | 从历史想吃派生的"常点"视图 | 派生 | 无 | P1 由旧 `favoriteDishIds` 列派生 |

> 关键：**想吃 ≠ 收藏**。孩子 9/22 午餐想吃的菜，9/23 不应再默认高亮。旧实现把"每日想吃"误当"终身收藏"，这是 R2 核心缺口，本稿修复。

## 3. 数据模型（方案 B-final）

### 3.1 新表 DDL（`sql/vXXX__create_child_want_eat.sql`）

```sql
CREATE TABLE usr_child_want_eat (
  id          BIGINT       NOT NULL AUTO_INCREMENT,
  child_id    BIGINT       NOT NULL,
  family_id   BIGINT       NOT NULL,
  menu_date   DATE         NOT NULL,
  meal_type   VARCHAR(16)  NOT NULL            COMMENT 'BREAKFAST/LUNCH/DINNER',
  source_type VARCHAR(16)  NOT NULL            COMMENT '菜单来源 SCHOOL/FAMILY（标记时的菜单上下文）',
  dish_type   VARCHAR(16)  NOT NULL            COMMENT '菜品类型 PRESET/FAMILY（与 DishRef 一致）',
  dish_id     BIGINT       NOT NULL,
  status      VARCHAR(16)  NOT NULL DEFAULT 'MARKED' COMMENT 'MARKED/ADOPTED/COOKED',
  create_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  delete_at   BIGINT       NOT NULL DEFAULT 0,
  version     INT          NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  UNIQUE KEY uk_child_date_meal_dish (child_id, menu_date, meal_type, dish_type, dish_id),
  KEY idx_family_date (family_id, menu_date, meal_type),
  KEY idx_child_date (child_id, menu_date)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='儿童每日想吃标记';
```

**设计要点**
- 唯一键 **不含 `source_type`**：同一道菜（dish_type+dish_id）在同一天同一餐只算一次想吃，避免"学校标记一次、家庭再标记一次"重复。
- `source_type` 仅作**上下文/运营**记录（孩子是在学校餐单还是家庭餐单上标的），不进唯一键。
- `family_id` 冗余存储，便于家长按家庭聚合查询（与项目"跨家庭隔离"约定一致），无需 JOIN 成员表。
- `status` 预置三态，P2 直接复用；P0 只写 `MARKED`。
- 软删除 `delete_at` + 乐观锁 `version`，与项目既有实体约定一致。

### 3.2 实体 `ChildWantEat.java`

```java
@TableName("usr_child_want_eat")
@Data
public class ChildWantEat {
    @TableId(type = IdType.AUTO) private Long id;
    private Long childId;
    private Long familyId;
    private LocalDate menuDate;
    private String mealType;
    private String sourceType;
    private String dishType;
    private Long dishId;
    private String status;
    private LocalDateTime createTime;
    private LocalDateTime updateTime;
    private Long deleteAt;
    @Version private Integer version;
}
```

### 3.3 Mapper `ChildWantEatMapper.java`

MyBatis-Plus 基础 CRUD + 两个自定义方法：
- `List<ChildWantEat> selectByChildDateMeal(@Param("childId") Long, @Param("menuDate") LocalDate, @Param("mealType") String)` —— mealType 可空（查全天）。
- `int deleteByUniqueKey(...)` —— 按 (childId, menuDate, mealType, dishType, dishId) 物理删除（想吃取消不需要软删历史，简单删行即可）。

## 4. 接口设计

### 4.1 改造：`POST /api/menu/mark-favorite`（孩子标记/取消每日想吃）

**请求 `MarkFavoriteReq`（扩展）**
```java
@NotNull @Positive Long dishId;
String dishType;                 // 可选，PRESET/FAMILY，未传仍按存在性推导
@NotNull Boolean favorite;       // true=标记, false=取消
@NotNull LocalDate menuDate;     // 新增：绑定日期
@NotNull String mealType;        // 新增：绑定餐次
```
> `sourceType` 不要求前端传（避免客户端伪造归属）；后端从当前 `daily()` 上下文不可得，故**由调用方经 `daily()` 已确定的菜单来源推导**——改为在 `markFavorite` 入参补 `sourceType`（后端从鉴权派生 family，再按菜单归属 FAMILY/SCHOOL；若不确定可默认 FAMILY）。详见 §6 决策点 D2。

**响应 `WantEatResp`（新 DTO，替代旧 `ChildPreferencesResp.favoriteDishIds` 的想吃语义）**
```java
Long childId;
LocalDate menuDate;
String mealType;
List<DishRef> wantEat;           // 该 (child,date,meal) 下当前所有想吃（DishRef={type,id}）
```
> 小程序收到后**直接重拉 `daily()`** 刷新 `favorite` 高亮（权威来源是新表），避免本地状态耦合。

### 4.2 新增：`GET /api/child/want-eat`（家长/本人查看想吃清单）

```
GET /api/child/want-eat?childId=xx&menuDate=2026-09-22[&mealType=LUNCH]
RequireRole: CHILD(本人) / PARENT
→ WantEatResp（mealType 省略=返回当天三餐）
```
> P0 仅单日查询；"按周聚合"是 P1 的 R3 视图，本稿不实现，但 `idx_child_date` 索引已为周查询预留。

### 4.3 不动
- `GET /api/child/preferences`：仍返回 `dislikes`/`tastes` + 旧 `favoriteDishIds`（此时为新用户空列表 / 历史种子）。P1 再用新接口 + 常吃派生视图取代其"想吃"部分。

**`daily()` 高亮改造示意**
```java
Set<String> want = wantEatRefs(childId, menuDate, mealType);   // 如 "PRESET:11","FAMILY:5"
...
.favorite(want.contains(ref.getType() + ":" + ref.getId()))
```

**`markFavorite()` 重写示意**
```java
public WantEatResp markFavorite(MarkFavoriteReq req) {
    LoginUser ctx = requireRole("CHILD");
    validate(req);                                  // 现含 menuDate/mealType 非空
    FamilyMember member = authorization.lockBoundChild(ctx.getUserId());
    authorization.requireConsent(member);
    ChildProfile profile = completeProfile(member);
    String type = resolveDishType(req, member);
    String sourceType = "FAMILY";                   // 见 D2
    if (req.getFavorite()) {
        lockDishByType(type, req.getDishId(), member.getFamilyId());
        wantEats.insertOrIgnore(new ChildWantEat(ctx.getUserId(), member.getFamilyId(),
            req.getMenuDate(), req.getMealType(), sourceType, type, req.getDishId(), "MARKED"));
    } else {
        wantEats.deleteByUniqueKey(ctx.getUserId(), req.getMenuDate(), req.getMealType(), type, req.getDishId());
    }
    audit.record("WANT_EAT", ...);
    return WantEatResp.builder().childId(...).menuDate(req.getMenuDate()).mealType(req.getMealType())
        .wantEat(wantEatRefs(...)).build();
}
```

## 9. 风险与缓解

| 风险 | 缓解 |
|---|---|
| R-A 旧客户端未传 `menuDate`/`mealType` 调用 `mark-favorite` 报错 | 入参加 `@NotNull` 校验；小程序同步发版；旧调用方升级前会 400，需协调发版顺序 |
| R-B `daily()` 多一次 want_eat 查询的并发 | `uk_child_date_meal_dish` 命中主键前缀，单行/少量，无 `FOR UPDATE`（读已标记无需加锁），影响可忽略 |
| R-C 同一菜 PRESET/FAMILY 撞号 | 唯一键含 `dish_type`，且 `resolveDishType` 已分流转 PRESET/FAMILY 表加锁，不会串 |
| R-D 旧 `favoriteDishIds` 列残留 | 仅停止写入，不删列；P1 前不影响任何功能（家长偏好页返回空/种子） |

## 10. 待你确认的决策点（D）

- **D1（默认采纳）**：本稿方案（新表 + 每日维度 + 确认单并存）是否 OK？
- **D2（source_type 取值）**：`mark-favorite` 的 `source_type` 怎么定？
  - 选项 A：前端/调用方传入当前菜单 `sourceType`（最准，但需客户端带，且不可信字段应由后端派生——见 §4.1 注）；
  - 选项 B（推荐）：后端按 `menuDate`+`mealType` 反查孩子当天该餐的已发布菜单 `source_type` 自动填入（权威、不可伪造）；
  - 选项 C：暂不记 `source_type`（列留空/NULL），P2 运营需要再补。
- **D3（接口命名）**：新增家长查询接口用 `GET /api/child/want-eat`（推荐）还是并入 `preferences`？
- **D4（发版顺序）**：小程序与后端需同步发版（R-A），是否接受「后端先上、小程序随后」的短暂 400 窗口，还是双写兼容过渡？
