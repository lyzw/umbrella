一、背景与后台核心目标

成长星球是面向 6–12 岁儿童的「生活与学习自主力养成平台」，以家长虚拟额度护栏 + 孩子自主决策的模拟记账模式运转（无真实支付风险）。载体为微信小程序，已落地首模块「小当家·点餐」并扩展到零花钱、家务、勋章、日程、健康打卡、奖励、监护人委托等域，且已规划学校/学生场景与心愿菜单。

当前 C 端功能已较完整，但缺乏统一的管理与运营入口：菜品/菜单/任务/奖励等内容靠代码或数据库直改，用户与家庭的异常无统一处置台，合规隐私（监护人同意、数据出口）与操作审计无系统化支撑。运营后台正是为补齐这一能力。

后台四大核心目标

1. 内容可控
菜品/菜单/任务/奖励/勋章等内容的统一配置、审核与上下线，保障未成年人内容安全。
2. 业务可观测
家庭、孩子、虚拟币流水、餐食确认单等关键指标一眼可见，支撑运营决策。
3. 风险可管
用户/家庭异常处置、内容风控、超额与异常流水告警、隐私工单闭环。
4. 合规可审
监护人同意留痕、数据导出/删除工单、后台操作全审计，满足未成年人保护要求。

二、后台用户角色

后台用户（运营侧）与 C 端用户（家长/孩子/学生/教师）是两套体系。后台通过 RBAC 控制运营人员能看/能改什么；C 端用户由「用户与权限管理」模块查询与处置，但不在后台直接以家长身份操作。

超级管理员
系统最高权限：角色与权限模型维护、全局配置、审计查看、所有模块读写。
运营管理员
日常内容配置（菜品/菜单/任务/奖励/勋章）、业务数据查询与人工干预、看板查看。
内容审核员
UGC（家庭私有菜、心愿菜单）机审+人审、敏感词/图像风控、未成年人保护词库命中处理。
数据运营 / 客服
看板与报表、家庭/孩子工单协助、通知下发统计；只读为主，可有限写。
合规 / 隐私专员
监护人同意留痕核验、数据导出/删除工单处理、合规清单检查，独立留痕。
只读审计员
仅查看操作日志、审计与看板，无写权限，用于外部审计/巡检。
权限原则：最小权限 + 职责分离。合规/隐私操作与运营写操作分离；所有写操作强制进入操作审计日志；敏感操作（删家庭、导出数据、改额度上限）需二次确认或审批。

四、各模块职责与相互关联

M1 · 数据看板与报表

  • 运营总览：家庭/孩子/活跃、虚拟币发放与消耗、确认单量与通过率、内容风险与隐私工单积压。
  • 业务域看板：餐食（想吃热度、确认单、超额）、零花钱（余额分布、额度使用）、家务/健康（完成率、连续天数）、勋章（发放与获得率）。
  • 自定义报表：按时间/家庭/学校维度筛选，支持导出（受数据权限与脱敏约束）。

关联：数据来自 M4 各域 + M8 告警汇总；导出受 M2 数据权限与 M5 脱敏约束；看板指标驱动 M8 告警阈值设定。

M2 · 用户与权限管理

  • 后台账号：运营人员 CRUD、状态（启用/禁用）、密码与登录策略。
  • 角色与权限（RBAC）：预置角色（见第二节）+ 自定义角色，按模块/操作粒度授权。
  • C端用户与家庭：家庭查询、成员关系、绑定与监护人委托关系查看；异常账号冻结/解绑协助。
  • 账号风控：异常登录、批量注册、风险家庭标记，联动 M8 告警。

关联：是所有写操作的权限闸门；每次变更写入 M6 审计；风控事件推送 M8；C端家庭数据查看/干预落到 M4。

M3 · 内容管理（CMS）

  • 菜品库：菜品增删改、图文、虚拟价格、热量、标签、过敏原声明（关联 R5 过敏原治理）。
  • 菜品分类：分类树维护。
  • 菜单编排：按日/按餐编排（FAMILY 可提报 / SCHOOL 仅展示收藏，对应 F-014/F-015）；周食谱模板。
  • 任务库 / 书单库：家务与学习任务模板（关联 V0.0.2 家务域）。
  • 奖励兑换库：奖励项与履约配置。
  • 勋章 / 活动配置：勋章定义（life_medal_definition）、成就规则、运营活动。
  • 心愿菜单与派生：爱吃/常点派生视图配置、心愿菜单（P3）管理。
  • 内容风控：UGC（家庭私有菜 life_family_dish、心愿）机审+人审、敏感词/图像审核、未成年人保护词库。

关联：发布的内容进入 M4 业务数据被孩子端消费；UGC 审核流见第六节；风控命中推送 M8 与内容审核员待办；过敏原声明是合规项，关联 M5。

M4 · 业务数据管理

  • 餐食业务：每日想吃(usr_child_want_eat)、确认单(life_menu_confirm)+审批态、确认单项与心愿菜单查询/导出。
  • 零花钱：钱包(life_wallet)、额度规则(life_allowance_rule)、流水(life_allowance_log) 查询与异常流水人工干预。
  • 家务 / 健康 / 日程：任务实例(life_chore_instance)、打卡记录(life_check_record)、连续记录(life_chore_streak)、日程(life_schedule)。
  • 勋章发放：发放记录(life_medal_award) 查询与补发。
  • 家庭设置：usr_family_setting 等配置查看与有限修改。

关联：只读为主，写操作（补发、干预）需 M2 权限并写入 M6；数据来自 M3 内容；异常数据（超额/异常流水）触发 M8。所有导出受 M5 脱敏与 M2 数据范围约束。

M5 · 合规与隐私中心

  • 监护人同意留痕：usr_consent_log 查看与核验，确保未成年账户合规。
  • 隐私工单：数据导出(sys_privacy_request)/删除申请、核验(sys_privacy_verification) 全流程闭环。
  • 合规清单：未成年人保护检查项、数据保留策略、审计就绪状态。

关联：工单由 C端发起，在 M5 闭环并写入 M6；超时/积压触发 M8 告警；导出内容受 M9 脱敏策略约束。

M6 · 操作日志与审计

  • 后台操作日志：sys_audit_log，记录谁/何时/在哪个模块/做了什么/影响对象，支持查询、回放、导出。
  • C端关键操作：监护人委托、解绑、额度变更、数据出口等高风险动作留痕。
  • 登录与会话：后台登录、会话、权限变更日志。

关联：由 M2/M3/M4/M5 所有写操作自动写入（不可绕过）；是合规(M5)与告警(M8)的取证来源；只读审计员专看此模块。

M7 · 消息与通知中心（P1）

  • 通知模板：sys_notice 模板管理（站内/订阅消息）。
  • 订阅管理：sys_notice_subscription 配置与统计。
  • 触达统计：下发量、到达、红点/打开率。

关联：运营公告、审核结果通知、告警(M8)触达均经此模块；模板被 M3/M5/M8 复用。

M8 · 监控与告警（P1）

  • 业务异常告警：超额确认单、异常大额虚拟发放、内容风险堆积、隐私工单超时。
  • 规则配置：阈值、触发条件、静默期。
  • 告警通道：站内(M7)、企微/邮件（通道接入方式不在此文档范围）。

关联：数据源为 M1 指标、M4 异常、M5 工单、M6；告警处置形成工单回流对应模块；规则可由 M9 功能开关控制。

M9 · 系统配置（P1）　M10 · 帮助与运营手册（P2）

  • M9：虚拟币名称/默认额度上限、学校目录（校名目录化治理）、枚举字典、功能开关与灰度。
  • M10：运营 SOP、FAQ、版本公告，降低培训成本。
模块关联总览： M2 是权限闸门 → 所有写操作经 M2 授权并落 M6 审计；M3 生产内容、M4 承载与处置业务数据；M5 负责合规闭环；M1 汇总可视、M8 基于异常触发告警并经 M7 触达；M9 提供全局参数。数据流向：内容(M3) → 业务数据(M4) → 指标(M1) → 异常(M8) → 告警(M7) → 处置(回流各模块)。

六、关键业务流程说明

流程 1 · 内容生产主链路（菜品→菜单→想吃→确认单）

运营(M3) 配置菜品库(图文/价格/热量/过敏原) → 编排每日/每周菜单(FAMILY可提报·SCHOOL仅展示) │ ▼ 家长/学校(C端) 发布当日菜单 / 孩子标记每日想吃(usr_child_want_eat) 与心愿 │ ▼ 孩子 选菜 → 生成确认单(life_menu_confirm) → 家长审批(状态机) │ ▼ 后台(M4) 可查确认单/超额复核(M8告警) · 异常人工干预(写M6审计) └─ 数据回流 M1看板(想吃热度/确认单量/超额率)

流程 2 · UGC 内容审核流（机审 + 人审）

用户提报 家庭私有菜(life_family_dish) / 心愿菜单 │ ▼ 机审 敏感词 + 图像风控 + 未成年人保护词库 ├─ 命中高危 → 自动拦截 + 进M8告警 + 通知(M7) └─ 待定/低危 → 进内容审核员待办(M3) │ ▼ 人审 通过(上架) / 驳回(原因回写+M7通知用户) │ ▼ 全部动作写入 M6审计

流程 3 · 隐私数据出口工单流（合规闭环）

C端申请 导出(sys_privacy_request) / 删除 本人数据 │ ▼ M5合规专员 核验监护人身份(sys_privacy_verification) + 同意留痕(usr_consent_log) ├─ 超时 → M8告警(工单积压) + M7提醒 └─ 通过 → 执行导出/删除(受M9脱敏) → 工单完结 │ ▼ 全流程写入 M6审计 · 仅合规专员与只读审计员可见明细

流程 4 · 异常监控告警闭环

M8规则引擎 监听 M1指标 / M4异常流水 / M5工单 / M6 │ 例：超额确认单 · 异常大额发放 · 内容风险堆积 · 隐私工单超时 ▼ 触发告警 → 经M7通道(站内/企微/邮件)推送责任人 │ ▼ 责任人处置 → 跳转对应模块处理(审批/冻结/核验) │ ▼ 闭环 告警标记已处理 · 处置动作写M6 · 指标回落

流程 5 · 后台权限与审计（横切所有写操作）

运营登录(M0) → M2鉴权(RBAC) 判定模块/操作权限 │ 无权限 → 拒绝 + 记录尝试(M6) ▼ 有权限 执行写操作(M3/M4/M5…) → 敏感操作二次确认(L4) │ ▼ M6审计 自动落库(谁/何时/何模块/何对象/前后值) → 不可绕过 └─ 只读审计员可查不可改，满足外部审计

七、优先级建议与实施里程碑

优先级范围理由建议里程碑
P0M0+M1(总览)+M2+M3(基础)+M4(查询导出)+M5+M6合规与风控是上线前提；无后台则内容靠直改、审计缺失、隐私工单无法闭环里程碑 A（基础可用）
P1M1高级报表 + M3内容风控 + M7 + M8 + M9增长期需要主动风控、通知触达与可配置化，降低人工成本里程碑 B（运营增强）
P2M10 + AI洞察看板 + UGC深度运营成熟期提效与智能化，非阻塞项里程碑 C（智能运营）

分期建议

  • 里程碑 A（MVP·必交付）：账号权限、内容基础配置、业务数据查询导出、合规隐私闭环、操作审计。先解决"能管、能审、能合规"。
  • 里程碑 B（增强）：内容风控人审台、告警引擎、通知中心、系统配置。解决"主动防风险、可配置"。
  • 里程碑 C（进阶）：运营手册、AI 数据洞察与异常预测。解决"提效与智能化"。

八、范围、边界与后续

明确边界

  • 不做：具体技术选型、前端框架、后端语言、数据库与部署方案（本文档不涉及实现）。
  • 不做：C 端业务功能本身（点餐/打卡/兑换逻辑由小程序侧实现），后台仅做管理与观测。
  • 不做：以家长身份替用户操作；后台对 C 端数据以查询/导出/有限人工干预为主，写操作须最小化并全审计。
  • 关联但独立：成长树/AI 推荐(P4)、学习域/教师家校互通(P3) 的后台配置可后续在 M3 扩展，本规划预留接入位。

后续可细化

  • 各模块页面字段与交互原型（进入 UIUX 阶段）。
  • RBAC 权限矩阵细表（模块 × 操作 × 角色）。
  • 数据脱敏与字段级权限规则。
  • 与现有表（sys_audit_log / usr_consent_log / sys_privacy_* 等）的字段映射核对。
本规划已对照现有数据库实体（usr_*/life_*/sys_* 表）与 V0.0.1/V0.0.2 功能域，确保模块划分落在真实功能之上，而非凭空设计。
