引言与设计范围

本详细设计承接《运营后台_功能规划方案.html》，在 10 个模块（M0–M10）基础上细化到页面层级、列表/详情/表单字段、操作与校验、状态机、权限矩阵、审计与脱敏规则、指标口径，使研发与 UI 可据此进入实现与高保真设计。

字段来源标注：正文中标注 DDL 的字段来自现有数据库表（已抽取核对）；标注 设计建议 的枚举/字段为本次设计新增或待确认，实现前需与产品对齐。

范围边界（重申）

  • 后台只做管理与观测；C 端业务逻辑（点餐/打卡/兑换）由小程序实现，后台以查询/导出/有限人工干预为主。
  • 所有对 C 端数据的写操作须最小化、带二次确认、并写入审计（M6）。
  • 不含：技术栈、前后端框架、部署、具体接口契约（进入研发阶段再定）。

总体设计原则

2.1 设计原则

  • 最小权限：角色默认无权限，按需授予；敏感操作分离（运营≠合规）。
  • 审计不可绕过：写操作统一经审计中间件落 sys_audit_log，无白名单。
  • 数据脱敏：手机号/姓名/孩子信息按角色与场景脱敏展示。
  • 合规优先：未成年人保护、监护人同意、数据出口优先于运营便利。
  • 读写分离：列表只读，写走抽屉+确认，降误操作。

2.2 交互与导航规范

  • L1 模块导航：左侧模块树，按角色权限动态渲染。
  • L2 列表/看板页：表格+筛选+批量，分页默认 20 条。
  • L3 详情/表单/审批：右侧抽屉或独立页，字段分组。
  • L4 操作确认：敏感写操作弹确认框，附影响范围。
  • 审计回执：写成功后提示"已记录，审计编号 #id"。
  • 全局顶部：搜索（家庭/孩子/工单号）、待办小红点、角色切换 Guard。

2.3 状态字段统一约定

各表已有 status 字段（如 life_dish.status、sys_notice.status、usr_user.status）。后台统一语义：ACTIVE/ONLINE=启用上架、OFFLINE/DISABLED=停用下架、PENDING=待处理、DONE/COMPLETED=完成。设计建议 对缺失状态（确认单、隐私工单）补齐枚举，详见各模块状态机。

3.3 数据权限与字段级脱敏

  • 范围权限：SA=全部；DC=被授权的学校/家庭子集；CP=隐私域隔离（仅本人处理的工单及关联家庭）；其余为全局只读或受限写。
  • 字段脱敏：usr_user.phone、孩子昵称、usr_child_profile.allergies 等敏感字段，对 OP/CR/DC 默认脱敏（如 138****0000），仅 CP 在处理隐私工单时按场景解密查看。
  • 导出脱敏：报表导出默认脱敏；含明文导出需 CP 审批并记审计（M6）。

3.4 细粒度权限点矩阵（资源 × 操作 × 角色）

关键业务流程详细

流程1 · 内容主链路（菜品→菜单→想吃→确认单）

[OP] M3 配置菜品(life_dish) + 编排菜单(life_menu_daily, FAMILY可提报/SCHOOL仅展示) │ 写操作 → 落 sys_audit_log ▼ [家长/学校 C端] 发布当日菜单 → 孩子标记 usr_child_want_eat(每日想吃) + life_wish_menu(心愿) ▼ [孩子 C端] 选菜 → 生成 life_menu_confirm(status=PENDING, is_over_limit 计算) │ ▼ [家长 C端] 审批 → life_confirm_approval(before→after, reason) ├─ 超额 → M8告警 + 异步复核 └─ 通过 → 虚拟记账(life_wallet/allowance_log) ▼ [OP] M4 可查确认单/明细/超额复核；异常人工干预(△审批) → 落审计 └─ 指标回流 M1看板
确认单状态机(建议)：PENDING → APPROVED / REJECTED → (APPROVED) COMPLETED；CANCELLED 任意可撤。

流程2 · UGC 内容审核（机审+人审）

[用户] 提报家庭私有菜(life_family_dish, status=PENDING, visibility=私有) ▼ 机审 敏感词 + 图像风控 + 未成年人保护词库 ├─ 高危命中 → 自动 REJECTED + M8告警 + M7通知用户 └─ 待定/低危 → 进 [CR] 审核队列 ▼ [CR] 人审 △：APPROVED(上架, visibility可转公开) / REJECTED(原因回写 + M7通知) ▼ 全部动作 → sys_audit_log（含前后值）

流程3 · 隐私数据出口工单闭环

[C端申请] sys_privacy_request(request_type=EXPORT/DELETE, status=PENDING, due_at=时限) ▼ [CP] 核验 → sys_privacy_verification(code_hash) + 查 usr_consent_log(guardian_status) ├─ 超时(due_at) → M8告警(工单积压) + M7提醒 ├─ 核验不通过 → REJECTED(写 reason) └─ 通过 → status=VERIFIED → 执行导出/删除(受M9脱敏) ▼ status=DONE + operator_id + evidence_ref + 落 sys_audit_log └─ 仅 CP 与 RA 可见明细（隐私隔离）
隐私工单状态机(建议)：PENDING → VERIFYING → VERIFIED → PROCESSING → DONE / REJECTED / EXPIRED。

流程4 · 异常监控告警闭环　流程5 · 权限审计横切

[M8] 规则监听 M1指标/M4异常流水/M5工单/M6 → 触发 → 告警 经 M7 推送责任人 → 处置 跳转模块 → 闭环(标记已处理+落审计) [任意写操作] M2鉴权(RBAC) → 无权限拒绝(记尝试) → 有权限执行 → L4二次确认(敏感) → sys_audit_log(actor/action/target/detail/ip/result) 不可绕过 → RA 可查不可改
