3.4 用户故事与可测试验收要点（US-1..9，精简引用 PRD 六）

US-1（儿童） 微信一键登录并创建档案。AC：弹授权建匿名会话；选「我是孩子」进分步档案；保存后状态"待家长绑定"，写操作灰显。

US-2（家长） 创建家庭并邀请孩子。AC：生成 6 位码/二维码，24h 有效；儿童提交申请提示"等爸妈确认"；审批后双方收"家庭已连通"通知 + 入学勋章。

US-3（家长） 确认监护人并同意信息处理。AC：《同意书》可展开、独立勾选；通过写 guardian_status=VERIFIED；失败给原因不静默；撤回即时降级。

US-4（家长） 设零花钱额度上限。AC：可设单笔/每日/每周并写入 life_allowance_rule；未设用默认 30/30/150；变更后下一张确认单即按新规则。

US-5（儿童） 浏览今日菜单并标记想吃。AC：按餐段折叠 + 大图卡（虚拟价格/热量/忌口）；支持筛选；可标记"今天想吃"。

US-6（儿童） 向爸妈确认今日菜单。AC：勾选菜品+份量±1+备注 chip；预览合计虚拟额与预计余额；点"告诉爸妈"生成确认单 status=PENDING。

US-7（家长） 审批菜单确认单。AC：卡片看明细；额度内一键同意；超额强制说明须显式放行；同意后扣减并通知孩子"已完成"；拒绝给温和说明可重提。

US-8（后台） 配置每日菜单。AC：维护菜品库（图文/虚拟价格/热量/标签）；按学校+日期+餐段发布当日菜单，发布后儿童端可见。

US-9（家长/合规） 撤回同意或导出/删除数据。AC：设置-安全与权限可撤回某类采集，即时降级留痕；数据出口入口可触发生成儿童数据包（V0.0.1 入口+基础导出，完整 P4）。

四、角色与权限模型

4.1 三角色与 JWT 分权

角色标识核心能力（V0.0.1）数据可见范围
儿童ROLE_CHILD建档、加入家庭、浏览菜单、确认菜单、看本人状态/流水仅本人档案、本人确认单与流水
家长ROLE_PARENT建家庭、邀绑定、设额度、审批确认单、看消费看板、撤回同意/数据出口所绑定家庭的成员及其数据
后台运营ROLE_ADMIN菜品库、当日菜单配置、内容/风控（P1 起）全量运营数据（脱敏）
鉴权实现（引用 PRD 十）：JWT 区分 child / parent / admin；token 含 user_id + role + family_id[]；敏感接口签名/防重放；token 失效与刷新机制。

4.2 数据隔离规则（family_id + child_id）

  • 查询强制过滤：所有业务查询按 family_id 过滤；儿童仅能访问 child_id = 本人 的记录（写入/读取均以 JWT 中身份为准，不得客户端传参越权）。
  • 家长维度：家长仅能访问其 usr_family_member 关联家庭下的成员数据；审批/记账以家长身份留痕。
  • 后台维度：运营访问儿童数据须脱敏，且操作写 sys_audit_log。
  • 越权处理：访问非本家庭数据 → 统一 401/403（E-009）+ 安全日志。
  • 同设备双账号（引用交互评审 3.1）：家长端「一键切换到儿童视图/代操作」；代操作视同家长本人行为，审批/记账以家长身份留痕。

五、数据结构（DDL 就绪）

本版共 16 张表，按 usr_ 账户/家庭/成长基础、life_ 生活域组织（edu_ 学习域本期不建表，仅占位）。通用字段：create_time DATETIME / update_time DATETIME / delete_at BIGINT DEFAULT 0；delete_at 为逻辑删除时间戳（0 = 未删除，非 0 = 删除时刻的 long 时间戳），替代布尔 deleted，用于支撑"删了还能重建"的唯一键语义（见下）；枚举用 VARCHAR 在 Java 控制。金额字段均为虚拟消耗额（非真实货币），统一 DECIMAL(10,2)；钱包表含 version INT 乐观锁防并发超扣。

逻辑删除与唯一键（delete_at 替代 deleted）：物理删除会破坏审计且不可恢复；布尔 deleted 软删会在业务唯一键（如 openid、invite_code）上"占坑"，导致同名记录无法重建。改为 delete_at BIGINT 后，业务唯一约束应设计为 UNIQUE(biz_col, delete_at)：有效行 delete_at = 0，软删行 delete_at = 删除时间戳(≠0)；删除后该 biz_col 的"有效位(0)"被释放，可再次插入 delete_at = 0 的同名有效记录，实现"删了还能重建"。所有查询一律以 delete_at = 0 作为有效过滤条件。

六、接口定义（RESTful + JWT）

按域分 8 组 接口；统一响应结构 {code, data, message}（code=0 成功，非 0 见错误码）；请求头带 Authorization: Bearer <JWT>；错误码复用 PRD E-001..E-010（映射下方）。所有写接口强制按 JWT 中 family_id/child_id 做数据隔离。

错误码PRDHTTP含义
E-001无微信授权401未登录访问写操作（仅可浏览）
E-002档案未补全200/warn启动且档案缺失，引导补全
E-003邀请码过期400邀请码 24h 失效
E-004监护人核验失败400非监护人/信息不符
E-005提交超时409网络失败/重试
E-006虚拟余额不足409扣减时余额<金额
E-007并发扣减冲突409乐观锁版本冲突
E-008通知发送失败200/warn三通道降级，站内保底
E-009越权访问403访问非本家庭数据
E-010家长撤回同意409相应能力已降级

七、核心流程设计

7.1 菜单确认状态机（权威 · F-019）

stateDiagram-v2 [*] --> DRAFT: 儿童编辑 DRAFT --> PENDING: 提交「告诉爸妈」 PENDING --> APPROVED: 家长同意（额度内一键 / 超额显式放行） PENDING --> REJECTED: 家长拒绝 / 改一改 APPROVED --> COMPLETED: 扣减虚拟零花钱成功 REJECTED --> DRAFT: 儿童改后重提 COMPLETED --> [*] note right of PENDING 系统做额度预校验 置 is_over_limit 不立即扣减 end note note right of APPROVED 扣减动作发生于 家长「同意」之后 end note
状态含义儿童端可见文案触发
PENDING 待家长确认已提交，家长未处理「已告诉爸妈，等确认」提交
复核中（超预算）超额，需家长显式放行「爸妈在看，马上就好」额度校验超额
COMPLETED 已完成家长同意且扣减成功「已记账 ✅ + 零花钱 −X 动画」家长同意
REJECTED 已驳回家长拒绝/改一改温和说明（不现"拒绝/拦截"负面词）家长拒绝

7.2 端到端：儿童确认 → 额度预校验 → 家长审批 → 扣减 → 通知

sequenceDiagram participant C as 儿童端(CHILD) participant S as 确认单服务 participant W as 钱包服务 participant P as 家长端(PARENT) participant N as 通知服务 C->>S: 提交确认单(选菜/份量/备注) S->>S: 额度预校验 is_over_limit(单笔/日/周) S->>S: 生成确认单 status=PENDING(不扣减) S->>N: 发站内+订阅通知家长 N-->>P: 审批提醒(订阅/站内) P->>S: 查看审批卡(confirmId) alt 额度内 P->>S: 一键同意(explicitConfirm=false) else 超额 P->>S: 强制额度说明后显式放行(explicitConfirm=true) end S->>W: 家长同意后 扣减虚拟零花钱 W->>W: 乐观锁 version++ 余额-=金额 S->>S: status=COMPLETED S->>N: 通知双方「已记账✅」 N-->>C: 状态更新+勋章动画 Note over C: 撤回分支: PENDING 期间儿童可撤回 → DRAFT/取消

7.4 虚拟钱包扣减并发安全（事务 + 乐观锁 + "家长同意后扣减"）

sequenceDiagram participant P as 家长端 participant AP as 审批服务 participant W as 钱包服务 participant L as 流水日志 P->>AP: 同意 approve confirmId AP->>AP: 校验 confirm.status 为 PENDING AP->>W: 开启事务 查询 balance 与 version W-->>AP: 返回 balance 与 version 值 v0 AP->>W: 校验 balance 是否大于等于 amount alt 余额充足 AP->>W: 扣减金额并将 version 加 1 条件为 version 等于 v0 W-->>AP: 扣减成功 AP->>L: 写入 life_allowance_log 类型为 DEDUCT 含快照 AP->>AP: 提交事务 并将 confirm.status 置为 COMPLETED else 并发版本冲突 AP->>W: 回滚事务 AP-->>P: 返回 E-007 并发冲突需重试 end Note over W: 乐观锁 version 防止同一余额多笔同时扣减导致超扣

7.5 通知下发（站内 + 订阅消息 + 短信兜底降级）

八、非功能与合规要点

性能 / 安全（引用 PRD 十一）

  • 性能：菜单首屏 ≤1s（骨架屏）；接口 P95 ≤300ms；通知触达 ≥99%；支持千级家庭同时在线。
  • 安全：JWT 分权；虚拟钱包扣减事务+乐观锁防超扣；儿童数据加密存储、最小化采集；越权统一 401/403 + 安全日志；后台操作全审计。
  • 不采集：V0.0.1 不采集儿童真实位置/人脸；OCR/位置待 P2+ 且需同意。

无障碍 / 未成年人模式（引用交互 8 / 9）

  • WCAG 2.2 AA：对比度 ≥4.5:1、组件 ≥3:1；状态配图标+文字不纯靠颜色；触控 ≥44×44px；动效仅 transform/opacity 且尊重"减少动态效果"。
  • 未成年人模式（P0 硬约束）：常驻入口；单日/单次时长上限温柔锁屏；22:00–8:00 禁服务；内容分级无公开社交；消费与额度护栏打通。
  • 儿童情绪保护（R-03）：仅见状态，不现"被拦截/拒绝"负面词；驳回原因家长温和说明。

合规审计基线（引用全局第八章）

  • 同意留痕：监护人同意书独立勾选、不与登录合并；通过写 usr_consent_log（VERIFIED + 时间戳）；撤回即时降级 + 留痕（E-010）。
  • 虚拟消费合规：仅虚拟记账 + 额度护栏，儿童端无真实支付；超额异步复核非实时拦截。
  • 可验证监护人核验：Q-01 MVP 用微信绑定+明示同意+自报年龄；实名/三要素 P1+ 增强。
  • 虚拟兑换：奖励兑换中心 P2 仅限虚拟权益，规避经营资质风险。
  • 审计：同意/记账/审批/越权均写入 sys_audit_log（采纳 R-12），满足儿童数据强合规。
