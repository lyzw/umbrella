二、产品定位与愿景

2.1 一句话定位

「成长星球」是陪伴 6–12 岁儿童的生活与学习自主力养成平台：以「孩子自主决策 + 家长虚拟额度护栏」的模拟记账模式，在零真实支付风险的前提下，培养孩子自我管理、理财意识与学习习惯。

2.2 愿景 · 使命 · 首期 Mission

维度内容
愿景让每个孩子在"安全的试错空间"里，长出自驱力与责任感。
使命用游戏化激励 + 家长护栏，把"吃饭/家务/作业"等日常小事，变成孩子可感知的成长里程碑。
首期 Mission（V0.0.1）跑通"孩子确认今日菜单 → 家长额度护栏 → 虚拟记账 → 正向反馈"的最小闭环，验证三角色模型。引用产品规划方案 · 3.2

2.3 价值主张（三方）

角色核心价值
儿童（主角 · 11 岁）能自己做主（选菜/任务），每完成一件事获得勋章与动画正反馈，成就感强、操作门槛低（大字号 + 强图标 + 语音）。
家长（监护人）零真实资金风险地了解孩子偏好与消费；额度护栏 + 异步复核掌握全局；成长看板一目了然。
后台运营配置菜单/任务/勋章、内容审核与风控，支撑多家庭规模化运营。
首阶段锚定（关键结论）：全局规划的首个可落地实现阶段被定义为 第一阶段 = V0.0.1 = P0 地基 + P1 小当家·点餐 MVP。本文档所有模块、架构、技术选型、风险合规均以"支撑 V0.0.1 落地，并预留 P2–P4 演进空间"为约束（采纳 PRD 三、范围与产品规划八、路线图）。

三、整体架构

系统采用「表现层 → 网关与鉴权 → 业务服务层 + 能力中台 → 数据层 → 基础设施」五层分层架构。三角色入口共享同一技术底座，能力中台下沉为各业务域复用（账号家庭、虚拟钱包、通知、数据看板、AI），避免重复建设。家长端与儿童端为同一微信小程序，登录后按 JWT 角色路由（child / parent / admin），数据按 family_id 隔离。

3.2 三角色与鉴权模型

儿童（ROLE_CHILD）

  • 建档、加入家庭、浏览菜单、确认菜单、看本人状态/流水
  • 数据可见：仅本人档案、本人确认单与流水
  • 端：小程序儿童视图（5 Tab）

家长（ROLE_PARENT）

  • 建家庭、邀绑定、设额度、审批确认单、看消费看板、撤回同意/数据出口
  • 数据可见：所绑定家庭成员及其数据
  • 端：同一小程序按角色路由 + 只读预览

后台运营（ROLE_ADMIN）

  • 菜品库、当日菜单配置、内容/风控（P1 起）
  • 数据可见：全量运营数据（脱敏）+ 审计日志
  • 端：Web 管理台（不在小程序内）
鉴权要点（引用 PRD 十、权限设计）：JWT 区分 child / parent / admin；所有接口按 family_id + child_id 做数据隔离，禁止越权访问他人家庭数据；儿童端不做裸露聊天/社交/定位；敏感动作统一走家长授权或审批流。

五、技术选型

层 / 域选型说明与口径
后端框架Java 21 LTS + Spring Boot 4.1.1Spring Framework 7 · Jakarta EE 11（jakarta.* 命名空间）· 虚拟线程。属全新代际，与旧 Java 11 / 2.7.18 工程隔离（引用功能规划六）。
ORMMyBatis-Plus复杂报表/统计友好；通用字段 create_time / update_time / delete_at（delete_at 为 BIGINT 删除时间戳，默认 0，替代布尔 deleted；身份及流水键不可复用，配置唯一约束逐表设计）；枚举用 VARCHAR 在 Java 控制。
数据库MySQL 8.0业务库按 usr_ / life_ / edu_ 三主域组织。
缓存 / 会话Redis仅会话、热点缓存、限流；审批在MySQL内按关系→确认单→钱包→规则加行锁，version额外校验，不依赖Redis保证记账一致性。
鉴权JWT 分权child / parent / admin 三角色；访问token有效30分钟，过期重新wx-login，不提供长期refresh token；服务端重查账号及权限，退出/禁用使会话失效；敏感接口防重放。
通知微信订阅消息 + 站内通知中心 + 短信兜底（后置）双通道兜底，站内保底（F-010/F-011 · 采纳 R-04）。
解耦可选 MQ（后置）首版数据库outbox任务投递通知；钱包、额度、流水、审批、完成状态与通知事件同事务。MQ只能解耦提交后的外部投递，不能异步补记账。
小程序端微信小程序原生 或 Taro / uni-app（Vue/React 跨端）前端独立工程，非 Java；家长端/儿童端同一小程序按角色路由。
后台Web 管理台（独立工程）不在小程序内；菜单/任务/勋章/审核/风控。
Q-06 技术栈版本闸门：Java 21 LTS + Spring Boot 4.1.1为候选组合，不代表本次已核实GA或兼容性。发布前须验证GA、MyBatis-Plus等依赖兼容并通过集成测试（R-10）；候选组合不通过时，替代版本也须重新验证，未通过仍阻断发布。架构层面通过分层与接口契约降低对具体版本的耦合。

6.2 为何从「点餐」起步（引用产品规划 8.2）

① 高频刚需、每天可用，快速养成习惯；② 天然需要"孩子决策 + 家长额度护栏"结构，验证三角色模型；③ 顺带建立消费记录与偏好，为零花钱、营养健康打地基；④ 正向反馈明显（孩子确认→家长确认→完成），孩子成就感强、家长接受度高。

七、关键设计原则

  1. 家长护栏优先：不做真实支付，消费走"虚拟零花钱"记账；对外联系/位置/内容发布经家长授权或审批流；儿童端不做裸露的聊天/社交/定位（引用产品规划五）。
  2. 零真实支付：结算统一走虚拟零花钱记账 + 额度护栏；儿童端无任何真实资金能力；超额动作由家长异步复核（非实时拦截）。
  3. 大字号 + 强图标 + 语音辅助：正文基准 16px（高于常规 14px），关键操作支持语音与图片，降低识字与输入门槛。
  4. 即时正反馈：每完成一件事给予勋章/动画/进度，强化自主感与成就感。
  5. 儿童情绪保护：儿童端仅见状态（"已告诉爸妈，等确认"），不显示"被拦截/拒绝"等负面词；驳回原因由家长以温和语言说明（引用交互 5 / R-03）。
  6. 隐私合规：遵循儿童个人信息保护法规，最小化采集、家长明示同意、可撤回、可导出/可删除（引用交互 9）。
  7. 无障碍 WCAG 2.2 AA：对比度 ≥4.5:1、UI 组件 ≥3:1；状态配图标+文字不纯靠颜色；触控目标 ≥44×44px；动效仅 transform/opacity，尊重系统「减少动态效果」（引用交互 8 / PRD 11.4）。
  8. 能力中台复用：底座前置、业务轻量，避免重复造轮子，支撑快速演进（见 4.2）。

八、风险与合规

风险

  • 虚拟消费合规：仅虚拟记账 + 额度护栏，儿童端无真实支付能力；超额异步复核（非实时拦截）。
  • 儿童个人信息保护：位置/人脸/OCR 需家长同意，可撤回；儿童数据单独存储、加密。
  • 未成年人模式：须满足《移动互联网未成年人模式建设指南》与微信平台口径（时长/时段/内容分级/消费约束）。
  • 内容安全：AI 与 UGC（读后感/对话）需机审+人审，防不良信息。
  • 沉迷防控：游戏化适度，设使用时长提醒；夜间保护候选22:00–08:00，仅儿童侧；具体配置待产品/合规确认。
  • 越权与审计：跨家庭数据访问须拒绝并留安全日志（E-009）。

应对

  • 审批流 + 额度双控，家长全可见；扣减统一发生在家长「同意」之后（F-019 状态机）。
  • 可验证监护人同意 + 年龄识别；儿童数据最小化采集 + 明示同意留痕 + 可导出/可删除（F-007/F-012）。
  • 未成年人模式常驻入口，与额度护栏打通（交互 9）。
  • 后台内容审核 + 敏感词/图像风控 + 未成年人保护词库。
  • 成长类激励替代纯消耗型玩法；兑换中心 P2 仅限虚拟权益，规避经营资质风险。
  • 操作日志与审计：同意/记账/审批/越权均写入可追溯日志（采纳 R-12）。
发布闸门：首版不采集儿童位置/人脸，OCR后置；同意独立勾选。自报不等于核验，Q-01最低强度未批准不采集真实儿童数据。夜间/时长限制是待评审产品策略，不作法定义务断言；官方法规适用须另行核验。

九、假设与待确认（含 6 项裁定）

设计假设：微信小程序（非原生 App）；三角色；通用场景（不限定城市）；不做真实支付、食堂非真实营运；学校菜单仅展示/收藏，家庭菜单由孩子提报并经家长审批后虚拟记账，任务奖励属P2。下述Q-01至Q-06为待联合确认的设计口径，Q-07账号边界与Q-08菜单来源补充见修订基线；不得将默认方案视为发布闸门已通过。

9.2 补充合理假设（架构师补充）

  • A-单孩优先：V0.0.1 限制为单孩以简化链路；若支持多孩，家长端/看板顶部提供「孩子选择器」，数据按 child_id 隔离（引用交互 R-14 / U-Q-03）。

  • A-扣减口径：严格遵循 F-019 权威状态机——扣减统一发生在家长「同意」之后，提交时不扣减；超额不实时拦截，转异步复核（引用 PRD F-018/F-019、交互 3.8、采纳 R-01）。
  • A-数据模型去冗余：V0.0.1 以 life_menu_daily 替代 life_restaurant；按source_type、owner_key、日期、餐段唯一，分别支持SCHOOL学校菜单与FAMILY家庭菜单；字段、权限与迁移约束见修订基线第4节。
  • A-二级监护人：V0.0.1 不做，入口置灰标"即将推出"（引用 U-Q-01 / U-G-02）。
