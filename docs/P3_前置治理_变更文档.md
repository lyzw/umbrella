## 二、实现偏差（设计与最终实现的差异，逐条）

**偏差 1（需你决策）：D7 只覆盖预置菜品，家庭私有菜品路径未纳入。**
`FamilyDishReq` 不含 `status`，且创建时强制 `ON_SALE`（`FamilyDishService:65`），因此若把 D7 一并套到 `validateFamilyDish`，家长将**无法保存任何未声明过敏原的私有菜品** —— 这是明显的产品行为变更，且超出已确认的 D7 文本（原文只点名 `applyDish` / `validateDish`，均为预置菜品路径）。
⇒ 现状：家庭私有菜品仍可 `ON_SALE + UNKNOWN`，孩子端显示「未登记过敏信息，暂不可选择」。**是否对齐请你定。**

**偏差 2：D7 生效后，测试无法再经 API 构造 `ON_SALE + UNKNOWN`。**
`CatalogFlowIT` 原有 3 处（展示用例、下单校验用例、想吃用例）依赖该组合来覆盖孩子端 UNKNOWN 路径。改为新增 `unknownDish()`：先以 `OFF_SALE` 合法创建，再直接用 mapper 把 `status` 翻成 `ON_SALE`（该文件已有 `dishes.updateById(...)` 直改库的既有惯例，见 `:305-307`）。语义上是模拟「历史行 / 发布目录漂移」，与 D7 的「只管 API 入口」边界一致。

**偏差 3：R5(b) 的实际缺口与设计稿措辞不同。**
设计稿写「`UNKNOWN` 时孩子端仅表现为按钮不出现，**无文案**」—— 核查发现孩子端**已有** badge（`pages/menu/index.js` 原内联文案 '过敏信息待确认'），真正缺的是**文案不区分原因**（菜品未登记 vs 档案过敏原失配）且不说明「不影响标想吃、只影响点菜」。故实现落在「一句拆五态」，未新增任何接口（与设计稿「后端无需新增接口」一致）。设计稿 §2.2 已同步标更正。

**偏差 4：D8 的体检范围由「过敏原目录」扩为六项。**
设计稿只点了 `allergens`；实现覆盖 `approval-reference / agreement-text / catalog-reference / grades / allergens / schools`。理由：这六项任一缺失都会让采集链静默不可用（如 `validAllergens` 依赖 `catalogReference`，年级/学校目录缺失会让档案整体提交失败），既然要做启动体检就一次做全。

**偏差 5（文档口径更正，非代码偏差）：设计稿 §2.2 原写「写路径 `markFavorite` 同样硬要求 `DECLARED`」。**
实为 `validateOrder`（`:1053`）；`markFavorite` **不校验** `safetyStatus`，`CatalogFlowIT:418` 就是「UNKNOWN 菜品可成功标记想吃」。⇒ 过敏原只拦「点菜下单」，不拦「想吃」，与 D9a（学校菜可标想吃）是一致的方向。设计稿已标更正。

**偏差 6：`schools` 目录的取值。**
dev 与小程序 `config.js` 用同一组合成校名（`合成第一/二/三小学`）；test 目录额外含 `合成学校`，因为 `BaseIT.profileJson()` 与 `CatalogFlowIT` 的学校菜单用例都用它。

### 三.1 并发构建污染（本次全量回归为何无效）

**事实**：发起全量回归时，工作区里**另有一个 Maven 测试进程在同时运行**（`ps` 可见两个 surefire JVM：本轮的与并行工作流的，共用同一个 `target/`）。`target/classes` 的类文件在本轮测试运行中途被对方重编译覆盖（实测 `WishMenuResp.class` 等写入时间为运行中的 11:29）。

**症状（全是"类文件被中途替换"的典型特征，与业务逻辑无关）**：

- `java.lang.NoClassDefFoundError: cn/studykid/growthplanet/dto/response/ChildPreferencesResp$ChildPreferencesRespBuilder`
- `java.lang.NoSuchMethodError: 'void cn.studykid.growthplanet.dto.response.WishDishResp.<init>(...15 参数...)'`
- 由此产生多处 `Status expected:<200> but was:<500>`：`CatalogFlowIT`（1 条：`displayExplainsUnknownAllergyDislikeAndMissingDishes`，单独跑时该用例**通过**）、`Sprint1ClosureIT`、`TransactionRegressionIT`
- 另有一次 `Wait strategy failed. Container exited with code 2`（Docker 争用）

**结论**：该次全量运行的失败**不能归因于任何一方的代码**，本轮**已主动终止**该运行（避免继续污染对方的运行）。**若要全量结论，必须在工作区无其他并行 Maven 构建时重跑。** 单类验证不受影响，本轮已按类单独跑绿（见上表）。

**教训**：本项目 IT 每个类各起一个 MySQL 容器、总耗时 6 分钟以上，两条工作流同时 `mvn test` 时不仅资源争用，还会因共用 `target/` 互相破坏字节码 ⇒ **同一工作区同一时间只应有一个 Maven 测试进程**。

## 六、回滚点

| 维度 | 说明 |
|---|---|
| 迁移 | **无**。不新增 SQL、不改 `chk_*`、不改唯一键、不改 `schema-locations`（本工作流未新增迁移文件） |
| 数据 | **无破坏性操作**：不删列、不改存量行。回滚 = 还原代码与配置，不需要数据恢复 |

| 另一处收紧 | D7 生效后，**存量 `ON_SALE + UNKNOWN` 菜品**只要被编辑保存就会被拒（需先补声明或先下架）。存量行本身不被主动改写 ⇒ 线上不会突然消失，但编辑时会遇到提示 |
