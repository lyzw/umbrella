## 二、迁移脚本（`sql/v007_wish_menu.sql`）

1. `CREATE TABLE usr_family_setting`（`family_id` 唯一含 `delete_at`、`wish_menu_max_dishes TINYINT DEFAULT 5` + `CHECK BETWEEN 1 AND 10`、`wish_menu_enabled` + `CHECK IN (0,1)`、`version`、FK → `usr_family`）。
2. `CREATE TABLE life_wish_menu`（`status IN ('SUBMITTED','WITHDRAWN')`、`max_dishes` 快照、`dish_count`、`submit_version`、`submit_time`、`version`、`UNIQUE (child_id, menu_date, delete_at)`、FK → `usr_family`）。
3. `ALTER TABLE usr_child_want_eat ADD COLUMN wish_id BIGINT NOT NULL DEFAULT 0` + `ADD KEY idx_want_eat_wish (wish_id)`。

**登记**：`src/main/resources/application-test.yml` 的 `schema-locations` 追加 `classpath:v007_wish_menu.sql`（**漏登记 → 相关用例整片 500**）。

**回滚点**：
```sql
DROP TABLE life_wish_menu;
DROP TABLE usr_family_setting;
ALTER TABLE usr_child_want_eat DROP KEY idx_want_eat_wish, DROP COLUMN wish_id;
```
`wish_id` 是"默认 0"的增量列，回滚后既有想吃逻辑无感知。

## 四、接口契约冻结（9 端点）

```
儿童（CHILD）
1  GET  /api/child/wish-catalog?menuDate&sourceType&categoryId&keyword&page&pageSize
2  GET  /api/child/wish-menu?menuDate
3  POST /api/child/wish-mark              { menuDate, type, id, selected }
4  POST /api/child/wish-menu/submit       { menuDate, refs:[{type,id}], expectedVersion }
5  POST /api/child/wish-menu/withdraw     { menuDate, expectedVersion }

家长（PARENT）
6  GET  /api/parent/wish-menu?childId&menuDate
7  GET  /api/parent/wish-menu/list?childId&from&to     （跨度 ≤ 31 天）
8  GET  /api/parent/wish-setting
9  PUT  /api/parent/wish-setting          { maxDishes, enabled, expectedVersion }
```

- 儿童侧 `childId` 一律取登录上下文；家长侧由 `childId` + `boundChild` + `requireParent` 派生家庭。
- `familyId` / `ownerKey` / `sourceType`（菜单上下文）**客户端禁传**。
- 读接口全程不加行锁（R6）；写接口用 `lockBoundChild` + `requireConsent`。

| 场景 | 码 | HTTP |
|---|---|---|

## 八、实现偏差与最终定稿（编码后回填）

> 编码完成后逐条记录与本文档的偏差、原因与最终口径。**凡与本文档上文冲突处，以本章为准。**

### 1. 超上限：`E400` → 新增独立错误码 `E-014`

`GlobalExceptionHandler.handleBizException()` 只调 `Result.fail(rc)`，**丢弃 `BizException` 的自定义 detail 文案**（`BizException(rc, detail)` 的 detail 只进日志）。因此"超限带明确文案"无法实现——客户端只会看到 `参数不合法`。

| 动作 | 内容 |
|---|---|
| 新增 | `common/result/ResultCode.java`：`E014_WISH_LIMIT_REACHED(1014, BAD_REQUEST, "已选菜品数量超出家长设置的心愿菜单上限")` |
| 使用 | `WishMenuService.submit()` 超限分支抛 `E-014`（detail 仍带「已选 3 道，超过上限 2 道」供日志/审计） |
| 测试 | IT 断言由 `$.message contains 上限` 改为 `$.code == "E-014"` |

HTTP 仍取 400（客户端可自助修正），与 `E013_DAILY_LIMIT_REACHED`(409) 的差异记录在此：打卡上限是"当日额度已消耗"的状态冲突，心愿上限是"本次选菜数"的入参问题。
**遗留建议（本次不做）**：若要让 detail 直达客户端，需改 `GlobalExceptionHandler` 的响应组装，属跨模块契约变更，应独立立项。

### 2. 乐观锁版本语义统一为「已成功写入次数；0 = 行不存在」

原稿把两张表的首次写入都定为 `version=0`（沿用 `ChoreService`/`FamilyDishService` 的"插入即 0"惯例）。实测会破坏首写保护：

- `expectedVersion=0` 已被"我还认为这行不存在"占用；若首次写入也落 0，则"无行"与"已保存一次"**同版本**，客户端拿着默认值视图(0)重提交不会被拦；
- `submit()` 的 `menu == null && expectedVersion != 0 → E007` 这条判定本身就依赖 **0 ⇔ 不存在**。

最终：`usr_family_setting` 首次 PUT 落 **1**；`life_wish_menu` 首次提交落 **1**；此后每次成功写入 +1。
`submit_version`（通知幂等键第二段）语义不变，仍是"第几次提交"，从 1 起 —— 与 `version` 解耦，须勿混用。

### 3. `submit()` 判定顺序：先乐观锁，后状态机

原实现先判"已 SUBMITTED → E400"，会**掩盖真正的版本冲突**（陈旧客户端重复提交拿到的是"请先撤回"而不是"版本过期"）。定稿：

```
锁住头行 → ① expectedVersion 与行版本不符（或行不存在却传了非 0）→ E007(409)
         → ② 版本一致但状态为 SUBMITTED → E400「已提交，请先撤回再调整」
         → ③ 版本一致且 WITHDRAWN / 首次 → 落 SUBMITTED，version+1、submit_version+1
```
`mark`（请求无版本号）仍直接 `requireUnlocked` → E400；`withdraw` 保留"已 WITHDRAWN → 幂等 200"在最前（WITHDRAWN 是吸收态，重试应视为成功）。
实现上把原 `requireEditable(childId, date, familyId)` 拆为 `requireWritable(date, familyId)`（开关 + 可编辑窗口）与 `requireUnlocked(childId, date)`。

### 4. 提交时新增"二次安全校验"（fail closed）

标记 → 提交之间菜品可能下架或补录过敏原（P3 前置治理的 R5-c 只挡"上架时刻就未声明"）。提交是给家长看的最终口径，故在窗口/上限/候选池校验之后，按与目录**同一套** `safetyStatus(dish, profile)` 再判一次，不可安全提交 → E400「心愿菜单中有菜品已下架或过敏信息待确认」。
覆盖用例：`submitRejectsDishesThatBecameUnsafeAfterMarking`（用 Mapper 直接改 `allergen_status='UNKNOWN'` 模拟竞态，见偏差 11）。

### 5. 目录/候选池响应新增 `status`、`safetyStatus`

`WishDishResp` 增 `status` + `safetyStatus`；`WishMenuResp.Item` 增 `status`。
原因：儿童端统一安全提示已收敛到 `miniprogram/utils/domain.js` 的 `safetyLabel()`（前置治理引入，**必须区分**"菜品未登记过敏信息 → 找管理员"与"档案过敏信息需更新 → 找家长"）。心愿区块原来自造文案（`过敏信息待确认`）与之冲突，现改为复用同一函数，候选池 chip 的置灰原因也走该函数。

### 6. 家长端菜单页新增一次 `/family/children`（**既有用例契约变更**）

家长菜单维护本身是家庭级、与孩子无关，但「孩子的心愿菜单」卡需要 `childId`（多孩要能切换），故 `loadParent()` 增加一次绑定儿童列表请求：

- 失败**静默降级**（`children=[]`、心愿卡不渲染，目录/发布流程照常）；`cancelled`（会话/页面已换）必须继续冒泡给 `ui.run`，不吞。
- 受影响的既有用例：`tests/pages.test.js`「家长加载当前家庭菜单并仅提交服务端允许的维护字段」原断言"不请求 `/family/children`"，改为"恰好请求 1 次，且失败不阻断菜单维护"（`children` 为空、`wish` 为 null，其后目录/发布断言全部保留）。
- 被删/改的处理器：`child()` **保留**（既有用例「处理中不允许菜单来源或儿童选择变化」依赖它），心愿卡的选孩子 picker 直接绑 `child()`；设计稿里的 `wishChildSwitch` 未实现。

### 7. 家长端心愿卡只展示"已提交"的菜

候选池明细留在孩子端；家长端 `renderWish()` 过滤 `submitted`，撤回后仍回显上次提交集合（`wish_id` 不解绑），并显示状态与提交时间。

### 8. 想吃看板标签联动（原 §五 承诺，已落实）

`pages/want-eat/index.js`：`MEAL_LABELS` 增 `ALL: '未指定餐次'`；`sourceLabel` 增 `WISH → 心愿菜谱`。
不补的话，心愿目录标记（`meal_type='ALL'` + `source_type='WISH'`）会被家长读成"今天家庭菜单里的菜"。新增用例「家长想吃看板：心愿菜谱标记单独标注，不冒充家庭菜单」。

### 9. 方法名与设计稿不符的收口

`pages/menu/index.js` 实际新增：`loadWish / renderWish / loadWishCatalog / wishToggle / wishSubmit / wishWithdraw / wishMark / wishCatalogTab / wishSearch / wishPageDelta / wishMax / wishEnabled / wishSettingSave`；数据项 `wish / wishSelected / wishDishes / wishTab / wishKeyword / wishPage / wishPageSize / wishTotal / wishSettings / wishMaxDraft / wishEnabledDraft / wishDishRange`。
**目录 v1 未做分类筛选**（关键词 + 家庭/预置双 Tab + 分页已够用），设计稿提到的 `wishCategory()`、`wishCategories` 状态已删除，不留死状态。

### 10. 通知入口

`pages/notices`：`titles` 增 `WISH_SUBMIT: '孩子提交了心愿菜单'`；条目级新增「查看心愿菜单」按钮（`data-child-id`）→ `navigateTo /pages/menu/index?childId=…`；`pages/menu.onLoad` 读 `query.childId` 选中该孩子（不在已绑定列表则退回第一个）。
设计稿写的 `data-page` 通用跳转无法携带 childId，故改为专用处理器 `viewWish`。

### 11. 集成测试用 Mapper 造历史数据

`ON_SALE + UNKNOWN` 的预置菜**已无法用管理端接口造出**（前置治理 R5-c「上架必须先声明过敏原」）。目录置灰分支改用 `legacyUnknownDish()` 直接落行（模拟 R5-c 之前的存量数据），并在注释里写明原因；其余权限/窗口/越权断言不变。

### 12. 本次明确不做

- 目录分类筛选、心愿菜单历史归档页、家长端"一键采纳为孩子明日菜单"（属后续阶段）；
- `SUBSCRIBE` 通道的实际授权引导（沿用 `NoticeService` 既有行为：未授权时该通道行照常登记、由既有投递逻辑决定）；
- 多孩心愿菜单汇总视图（`/parent/wish-menu/list` 已按 childId 返回，未做跨孩聚合）。

### 13. 心愿区块在页面中的位置（相对设计稿上移一屏）

设计稿写的是"「每日想吃」区**下方**"，而「每日想吃」区在 `pages/menu` 里包含"推荐/常吃快捷区 + 菜品行 ♥"两段。实现把心愿卡插在**快捷区之后、菜品行列表之前**：

- 理由：菜品列表在家庭餐单下最多 50 行，放在其后会被埋到屏底，孩子几乎发现不了（而这是 R1 的核心诉求）；
- 卡片自带标题「今天的心愿菜单」+ 状态提示，与上方快捷区、下方菜品行都能区分；
- **如需严格贴在设计稿位置，只需把 `pages/menu/index.wxml` 的两段 `wish-section` 整体移到菜品 `wx:for`（约 141 行）之后**，无逻辑改动。
